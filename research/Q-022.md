# Research question — Q-022

*Copied by the Orchestrator from intake/requests/Q-022.toml (model S-012 AC2).*

## The question

Groundwork map: how one owner who oversees several projects, worked on mostly by AI agents, follows what the agents are doing and have done, and which steps are waiting on the owner.

The setup. Work in each project moves through a fixed sequence of phases and stages run by a script, the Orchestrator, which dispatches agent sessions with distinct roles (for example builder, check author, reviewer, critic, researcher) and routes each result by a fixed table: a pass moves the work on, a fail sends it back, and a third fail goes to Triage, which stops the work and asks the owner (shumpmaster/Personal-Org-Operating-Model, OPERATING_MODEL.md §4 and §5; Service-Desk governance/ROUTING.toml). The Orchestrator also retries stalled sessions, pauses on budgets and usage limits, and raises failure cards (OPERATING_MODEL.md §5). The work leaves records in two kinds of place: GitHub objects (branches, commits, pull requests, checks run by GitHub Actions, reviews, merges, deploys), and files in each project repository and in one portfolio repository that spans them (status files, an append-only dispatch log, decision cards in queue/, the owner's answers in decisions/, review verdicts in reviews/, research memos, gate cases). Every agent commit names its session, and builder commits also name their spec; where the environment can push only one branch, builder branches stay local and reach GitHub only through merge commits; reviewer-role agents never commit, and their verdicts are filed by the Orchestrator (Service-Desk AGENTS.md §1; CLAUDE.md). Some steps wait on the owner: answering a card, ruling a phase gate, merging a pull request that needs the owner's approval, and approving every production deploy (OPERATING_MODEL.md §2, §3 "Graduation and re-entry", §5). The owner already has a status page, the desk (shumpmaster/Service-Desk; docs/PROJECT.md and docs/handover/ describe what it shows), whose "Waiting" screen today lists items in groups (questions for the owner, with the agents, answer being recorded, kicked back, waiting on the owner, done in the last 24 hours). The owner reads mostly on a phone.

Ways of following the work that are in view include: the desk's Waiting screen as it is; GitHub's own pages and notifications; a chronological history of events across the work; one pipeline-style view per piece of work; a table of roles against kinds of work; a periodic digest; and doing nothing new. The map should cover all of them.

Map the ground an expert would cover before deciding whether the owner needs anything beyond what exists, and if so what form it takes:
- how the owner follows the agents' work today, what that costs in time, what gets missed, and what doing nothing new would leave unsolved;
- what the owner needs to know about the work, and when: where a piece of work is, who holds it, what it is waiting on, what failed and why, and what is the owner's to do;
- what should interrupt the owner and what can wait until they look;
- which events matter to the owner, including the Orchestrator's own (stalls and retries, budget and usage-limit pauses, malformed returns, failure cards); whether and how they could be classified (a fixed closed set, open labels, free text, or none), what each gains or loses for following the work, and whether events with no GitHub equivalent (phase gates, decision cards, research, stops) fit one scheme or need their own;
- how each event can be read from the records alone, which records are missing, ambiguous or reconstructed (local branches seen only through merge commits, verdicts filed by another role, steps grouped by session), how a view shows what is not recorded without guessing, and how the reader moves from an event to the record behind it;
- how far the view can be trusted: records written by the Orchestrator against records written by the agents themselves, how a wrong or stale view would be noticed, and what the owner relies on it for;
- freshness: how current the view is, how it updates, how the reader sees its as-of time, and how half-finished states show;
- how many events arrive per day across the projects, how far back the view reaches, how finished work ages out, and how grouping, collapsing and filtering (by branch, milestone, project, agent or state) affect what stays readable;
- one view across all projects or one per project, and how a user moves between them;
- whether a new view replaces the current Waiting screen or sits beside it, and what is lost or duplicated either way;
- whether and how the steps waiting on the owner stand out without making waiting look like a fault; whether the owner acts from the view at all, and if so how that action stays the owner's own;
- how the view relates to other work on the same screens: a proposed check-status mark on each desk card (an idea the owner logged on 2026-11-04), the pull-request briefing work in its own Discovery (research/Q-016.md), and pending desk follow-ups and later work (Service-Desk intake/later-work.md; shumpmaster/Model-Lab decisions/questions/P-001-desk-follow-ups.md);
- what read access across private repositories it needs, which keys are involved, and whether any data leaves the repositories;
- reading on a small screen: density, layout, colour as a signal, and accessibility without it;
- the owner's time to use it, the cost to build and keep it, and how its value could be measured or tried cheaply;
- what other fields do to show one decision-maker the flow of many parallel pieces of work (for example continuous-integration run views, version-control history graphs, kanban and workflow boards, air-traffic, logistics or operations control displays), including where such displays were found to mislead, overload or be ignored.

## The decision it serves

The shape of the Discovery for how the owner follows the agents' work and what waits on them: which questions go to the owner, which go to research, and which need an experiment, before its value target, scope and plan are set.

## What each answer would change

Each area found to be unknown becomes a research request or a registered experiment; each found to be the owner's call goes on the owner's shortlist; each design trap found shapes the scope.
