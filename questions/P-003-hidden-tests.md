# Ruling needed: Should the card fix have hidden tests, or go to its Build gate with the two checklist lines that need them marked as skipped?

Milestone: Build-1, Build-3

WHY: Before the card fix is built, its checklist for the Build phase goes to you with its Build gate. Two of its lines, "tests written before the work" and "independently reviewed and passing", as the operating model defines them, include hidden tests: tests written by the Check author that the Builder never sees, kept outside the repository and run only by the automated checks, so the work cannot be shaped to pass them. The desk has no hidden tests, and nothing in its automated checks can run them today. So either a set is made for the fix before building starts, or both lines go to the gate as skipped, with that reason. Skipping them drops only the hidden tests: the Check author still locks the visible tests before any work exists, the Reviewer still tries to break the work, and the design reviewer still checks the page, before it is accepted. The choice has to be made before building starts: hidden tests written after that can no longer count as written before the work. The Build gate's case cannot be finished until this is settled, so leaving it unruled holds the fix at its gate. If you do not answer within 72 hours, I write option A in, as for any reversible question.
OPTIONS:
  A. Skip both lines, with the reason — the two lines go to the Build gate as skipped, each saying the desk has no hidden tests and what still happens instead: the visible tests, locked before the work, and the two reviews. You rule them with the gate.
     Cost: no test the Builder cannot see, so a fix shaped to its visible tests is caught only by the reviews. Read at a glance, "tests written before the work: skipped" can look as if no tests were locked, though they will be; the reason beside it says so. Rules out: hidden tests written before the work, once building starts; a set added later could count only towards "independently reviewed and passing", and only until the Reviewer passes the work; the record itself can be changed later with the Critic's check. Reversible: yes.
  B. Make a hidden set for the fix first — the Check author also writes hidden tests; they are stored outside the repository, readable only by the automated checks, and a short code for the set is logged so any change to it shows; a new step in the automated checks runs them; both lines go to the gate as taken on. No lighter route meets the model's rule: the hidden tests must be kept outside the repository and run by the automated checks, and today those checks strip them out rather than run them.
     Cost: a change to the desk's automated checks and governance files, which are in the highest risk class and need your approval, and a place to store the tests outside the repository, none of which exists today. The plan says the fix leaves the Orchestrator and the operating model unchanged, so this would be its own piece of work, done first, and the Build gate waits for it. Rules out: nothing. Reversible: yes.
  C. Keep both lines as taken on, each saying the hidden tests are left out — the same work as A, recorded as taken on with that note.
     Cost: read at a glance, the checklist looks as if the model's hidden tests were met. Rules out: the same as A. Reversible: yes.
RECOMMENDATION: A — a fix this small does not justify building the hidden-test machinery first, the locked visible tests and both reviews still happen, and the reason beside each line says exactly what was and was not done. For the desk itself you chose skipped, with reasons, over taken on with a note; that case differed, since the desk was built outside the pipeline with no tests locked at all, while here the visible tests will be locked. Confidence: high; it would change if you want the desk to have hidden tests from now on (then B, as its own piece of work).
