# Ruling needed: should the timeline read your projects through a new read-only GitHub App, or keep the desk's read-only key?

Milestone: Discovery-7, M7, M8, M9

WHY: The timeline shows checks, and alerts your phone to any single thing that needs you in every project (your answers 2 and 9). The desk's read-only key cannot read check results on your private repositories, and the desk has no single feed of events from every project. A read-only GitHub App can do both, but it is a new credential, which only you can approve. The answer sets what the timeline reads with, and so which ways alerts from every project can take; nothing is created by this answer.
How to answer: one letter.
If you don't answer: at the timeout the recommendation, A, is adopted and logged as a default, which creates nothing and keeps the desk as it is; the plan's limits come back to you at the Design gate either way.

Background:
- The key today reads files, pull requests and automated runs (builds and checks GitHub runs on each change). It holds no permission for deploys or for the pass-or-fail marks posted on each change; those can be added to the same key, with no new key. GitHub says this kind of key cannot use its check-results service; the desk's own trial found it refused on your private operating-model repository, and no record names a refusal on Service-Desk.
- Alerts today come only from Service-Desk. An App gets one stream of events from every repository it is installed on; without one, alerts from every project need a copy of the alert sender in each repository, one program on your Cloudflare account checking every project on a timer, or a separate event stream set up on each repository.

OPTIONS:
  A. Keep the read-only key — the timeline reads with the key the desk has today, with read permissions added for deploys and pass-or-fail marks, and shows CI from automated runs and those marks. Gain: no new credential; the project stays at T1, the desk's trust level; nothing new to guard; adding a project still means adding it to the one key. Cost: no check results on the private repositories; whether they show anything runs and marks miss is not known, and the records experiment (E2) can show it; until then a missing result shows as not recorded. The alert route stays open, chosen in Design and put to you if it needs a new service: a sender in each repository, which the research estimates needs the sender's keys in each, a program on a Cloudflare timer, holding the read key, or a separate event stream on each repository, each to be received at Cloudflare; GitHub's own schedules run at most every 5 minutes and can be late or skipped, which puts the plan's draft 5-minute alert target at risk. You keep renewing the key when it expires, as today. Reversible: you can choose B at any time. It rules out check results on private repositories and the App's single stream of events, until you choose B.
  B. Read through a read-only GitHub App — you create a private App on your own account with read permissions only, check results included, install it on the repositories you choose, and its key is held by the desk's server code on your Cloudflare account, never by an agent. Gain: check results on every repository; one stream of events from every installed project, so alerts can arrive in minutes; GitHub's deploy-review events, which only Apps receive; a request allowance at least as large as the key's. Cost: the App's private key never expires and can read every repository the App is installed on, your two private ones included, so it becomes the desk's most valuable secret, which the research advises keeping in a vault where it can only sign, a kind of store Cloudflare offers only as a trial; a receiver for the stream on your Cloudflare account, with a checking timer as backup, since GitHub's events can take minutes, arrive out of order and are not sent again on their own; each event's full contents sent to that receiver, which holds them only as long as the lasting-copies question allows; a new credential, so the tier is put to you again by the tier rules before the Build gate; no cost figure in the research, so your plan's $0 ceiling holds unless you approve more. Making the App and its key is your own click. Reversible: the App and its key can be deleted. It rules out staying with the one renewable key alone.
RECOMMENDATION: A, with low-to-moderate confidence — it needs no new credential and keeps the project at T1, and what A misses is not yet known: the records experiment can show whether check results add anything, and B stays open as its own change. Its weak point is alerts from every project within 5 minutes, which a timer may miss. What would change it: if alerts from every project must arrive within minutes, or if the records experiment shows check results matter, choose B.
RISK CLASS: R0 (records only: the plan is redrafted to match; no credential is made by this answer)   REVERSIBILITY: reversible   BLAST RADIUS: the timeline's draft plan: what it reads with, the ways alerts can reach you from every project, its limits and tier; nothing on the desk changes now
DEFAULT: A   TIMEOUT: 72 hours

Checked by: the Critic, reading this card cold in fresh sessions on a different model from the writer's; its rounds are listed in the pull request that files the card.

Not offered: a classic personal key, the only kind that can read GitHub's own notifications inbox; one that reads private repositories can also write to them, which your ruling on acting rules out. An App that also writes, which your ruling on acting left for later as its own change.

Also not settled here, and put to you as its own question: how far back the timeline must show GitHub's run results, now that GitHub deletes them after 90 days by default, and where any lasting copies of them are kept.
