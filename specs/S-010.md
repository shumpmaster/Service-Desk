## Acceptance criteria (scenarios; owner-approved)

**Words used throughout.** A **connected project** is a repository on the desk's list, with the portfolio repository added (plan §8, "All projects", line 200). **The records** are, for each connected project, GitHub's objects that the desk's read key can read (branches, commits, pull requests, reviews, workflow runs, commit statuses, deployments and their reviews) and the operating model's files on its main branch (queue/, decisions/, questions/, research/, specs/, the dispatch log, status files, docs/projects/ and docs/PROJECT.md). **The waiting list** is the one list of steps waiting on the owner (J4). A step is **due** at the moment the desk's rules first put it on the waiting list, which for a decision card is when the S-009 rule shows it (plan §8, line 211). **The record writer** of an event is the party that wrote the record a field comes from: `GitHub` for an object GitHub makes (a pull request, review, merge, workflow run, deployment or its review), `the Orchestrator` for a file the Orchestrator writes, `agent <role>` for a file or commit an agent session writes, `the owner` for a commit the owner makes, and `not recorded` when no record says (J1).

A **reading of src/** comes before freeze: a Reviewer's return, recorded verbatim by the session as `reviews/S-010/_src-reading.md`, naming the desk's read path (server and page), the card-making code's entry points, the sender's entry points, the generated copies, the path of the desk's server code, and what today's five core screens draw. J1, J4, J5 and the areas touched are checked against it before freeze; a difference is a revision of this draft, not a build decision.

### The event record (D1; M6, M7)
- **AC1** [trace: V9 → AC1] — When the timeline shows an event, then its kind, state, who, time, project and piece of work each come from a record, and opening the event names that record (a GitHub link, or a path at a commit). A field that no record holds shows the words "not recorded"; the desk never fills it with a guess, a default or the value of a neighbouring event.
- **AC2** [trace: V9 → AC2] — When a step is not stated by any record but other records support it (for example a branch seen only through its merge commit), then it is shown only with the mark "reconstructed", and opening it lists the records that support it. When no record supports a step, it is not shown at all.
- **AC3** [trace: V9 → AC3] — When an event is shown, then it says who wrote its record (`GitHub`, `the Orchestrator`, `agent <role>`, `the owner` or `not recorded`), beside who acted. An agent's own record of its work (for example "done" in its return) is shown as the agent's, never in GitHub's or the Orchestrator's style, so the owner can tell a self-report from the platform's record (plan line 40).
- **AC4** [trace: V9 → AC4] — When an event's kind is one of the key's eleven (branch, commit, pull request, check, review, merge, deploy on the first row; gate, decision, research, stop on the second), then it is drawn with that kind's own shape. A recorded event outside the eleven (for example a tag) is drawn with the `other` shape and its record's own name for it. Colour never marks a kind (plan line 153). The key, with each shape and its name, opens from the timeline in one tap.
- **AC5** [trace: V9 → AC5] — When an event's state is shown, then it shows its colour and its word side by side, from the closed set of J2. A record whose state is outside J2's mapping shows `other` with the record's own word, and a record that holds no state shows `unknown`. Every colour carries one meaning in every view.
- **AC6** [trace: V9 → AC6] — When a record gives both when a thing happened and when it was recorded, then the event shows when it happened. When it gives only when it was recorded, the time is shown marked "recorded at". When a time's offset is unknown, it is shown as such and never moved into the owner's time zone as if known (J1).
- **AC7** [trace: V9 → AC7] — When an event's record is one GitHub no longer keeps (for example a workflow run past its repository's retention setting), then the event shows "no longer kept", never as missing work, a failure or "not recorded". Once a lasting copy of that result exists (J8), the event is shown from the copy, marked "from a kept copy". Until the owner approves the records change that writes copies, none exist and this criterion's first sentence applies alone (plan line 182).
- **AC8** [trace: V9 → AC8] — When a step's record says it waits on the owner, then it is never shown in the failure colour, with the word "failed", or as "stalled" or "late". When an agent step has started (its dispatch-log entry) and has no ending record and no later record for the same piece of work for longer than the stall time (open question 4; drafted at 2 hours), then it shows `stalled` (plan line 39).

### The timeline (D2; M7)
- **AC9** [trace: V8 → AC9] — When the owner opens the timeline, then by default it shows the events of every connected project on one line in time order, newest at the top, each labelled with its project, led by the waiting list (AC17).
- **AC10** [trace: V8 → AC10] — When the owner puts one or more projects in focus, then their events are shown in full and every other project condenses to one line giving its name, its newest event's time and how many steps it has waiting on the owner. A condensed project with a step waiting on the owner still shows that step, by name, in the waiting list. Taking focus off shows every project again. The focus is kept on the device across a reload.
- **AC11** [trace: V9 → AC11] — When the owner scrolls back, then earlier events load in pages, back to the first record of each connected project, and never all at once on opening. Each page shows its as-of time (AC14). An event past GitHub's keeping follows AC7.
- **AC12** [trace: V9 → AC12] — When a piece of work is shown, then it shows which milestones it feeds, from the `milestones:` line of its spec header, or of its plan's milestone lines (` · for:` or the item's own plan), and `not recorded` if neither names one. There is no milestone filter row (plan line 27).
- **AC13** [trace: V9 → AC13] — When the owner opens an event, then it offers each link its records give: the commit and its changes, the pull request, the research question and its memo and sources, the approval or ruling record, the design mockup file, the gate case. Each link opens the record's own page on GitHub or its file. A link to a record GitHub no longer keeps says "no longer kept" instead of opening a page that is gone (AC7).
- **AC14** [trace: V8 → AC14] — When the timeline is shown, then it shows its as-of time (when it last read each project successfully) and, apart from it, the age of the newest record it holds for each project, or "age unknown". "No data" (a project never yet read) and "late" (a project not read successfully for longer than twice the read interval) each have their own state, word and colour, and neither is drawn as "nothing waiting" (plan line 43; library/facts/F-asof-age-label-01.md:4).
- **AC15** [trace: V8 → AC15] — When the outside check (J7) finds that the timeline's feed has stopped, then the timeline shows "Stopped since <time>: what waits on you may not be shown" above the waiting list, and the phone gets one notice saying the same. If the owner has approved no outside check (plan line 186, fallback), then the timeline instead shows, beside its as-of time, "This view cannot tell a stopped feed from a quiet one", and never shows "Nothing waits on you" without its as-of time and age.
- **AC16** [trace: V8 → AC16] — When a read of one project fails, then that project's events stay shown as last read, marked with their as-of time, its line says it cannot be read just now, and its waiting steps stay on the waiting list as last read with that mark. A failed read never empties the waiting list to "Nothing waits on you".
- **AC17** [trace: V8 → AC17] — When the timeline is shown on a screen 390 CSS pixels wide, then it is one line of events read top to bottom with no sideways scrolling, every control is at least 44 by 44 points, text has at least 4.5:1 contrast and each shape and state colour at least 3:1 against its background, and colour is never the only sign of anything (library/facts/F-wcag22-01.md:4; library/facts/F-platform-targets-contrast-01.md:4). On a computer it is the same view, wider.

### What needs the owner (D3; M8)
- **AC18** [trace: V7 → AC18] — When steps wait on the owner, then they lead the timeline, above every other event, across all projects, in the waiting list's order (J4). Each shows its kind, project, what is asked and how long it has waited.
- **AC19** [trace: V7 → AC19] — When the owner looks at a waiting step, then it is shown in its context: the events of the same piece of work just before and after it (its branch, pull request, commits, checks and earlier steps) are shown with it, or one tap away in place, without leaving the timeline.
- **AC20** [trace: V8 → AC20] — When the timeline and any core screen it has not yet replaced are given the same records and moment, then both show the same waiting steps, with the same states and the same count, because both take the one waiting list (J4; plan line 44). A test hands both the same sample records and one moment and compares them.
- **AC21** [trace: V7 → AC21] — When the owner chooses to answer, approve or merge a waiting step, then one tap opens GitHub's own page for that action (J6): an answer opens GitHub's new-file page with the answer filled in, as the desk does today; a deploy approval opens the run's page where GitHub offers "Review deployments"; a merge or a review opens the pull request's page. The owner finishes there, as their own GitHub action. The desk writes nothing to any repository and holds no key that can write; a production deploy stays the owner's own approval on GitHub (plan lines 22, 42).
- **AC22** [trace: V7 → AC22] — When the record of the owner's action reaches GitHub (the answer committed, the deploy approved, the pull request merged), then on the timeline's next read the step leaves the waiting list and shows as done, by the owner, at the record's time. An action begun from the timeline but not finished on GitHub leaves the step waiting.
- **AC23** [trace: V8 → AC23] — When a step becomes due, then the owner's phone gets a notice naming it within 5 minutes of its due time, whichever route the Design chooses for alerts from every project (plan line 180; J5). Each step is named in its own notice, or by name in a notice that groups steps due within the same run; none is only counted. A step is notified once; it is notified again only when its state changes (library/patterns/P-repeat-on-change-01.md:4). A step that is answered before its notice would go is not notified. If the Design finds no route that meets 5 minutes within section 5's limits, this criterion's figure goes back to the owner at the Design gate, and Build starts no alert work until the owner rules (plan line 180).
- **AC24** [trace: V8 → AC24] — When the owner opens a notice, then the timeline opens at that step in its context (AC19). If the step is no longer waiting, the timeline says so and shows it as done, or as no longer on the list, with its record.
- **AC25** [trace: V8 → AC25] — When the owner's phone allows a Home Screen web app's notice to be marked Time Sensitive (tested in Design on the owner's phone, plan line 183), then notices for waiting steps are marked Time Sensitive; otherwise they arrive at the normal level and nothing else changes (library/facts/F-ios-interruption-levels-01.md:4).
- **AC26** [trace: V8 → AC26] — When the timeline is open and visible on a device, then it keeps on that device a log of when it was open and visible, and when it first showed each waiting step; once a week it offers a prefilled link that commits that week's log to the owner's private portfolio repository, as V1's log was (docs/PROJECT.md:205-209; J9). Nothing of it is kept on Cloudflare.

## Join sheets
- **J1 —** the records → the event reader (D1). The reader is handed, per connected project, the records a read got, keyed by GitHub object id or by path at a commit, and which it did not get. It hands on a list of event records of this exact form (UTF-8 JSON):
  `{ "id": "<project>/<kind>/<source id>", "project": "<repo>", "kind": "branch|commit|pull request|check|review|merge|deploy|gate|decision|research|stop|other", "kind_name": "<record's own name, for other>" | null, "state": "<J2 state>", "state_word": "<word shown>", "who": "<login or role>" | "not recorded", "on_behalf_of": "<login or role>" | null, "writer": "GitHub|the Orchestrator|agent <role>|the owner|not recorded", "occurred_at": "<RFC 3339>" | "not recorded", "recorded_at": "<RFC 3339>" | "not recorded", "offset_known": bool, "piece": "<item id>" | "not recorded", "milestones": ["M<n>", …] | "not recorded", "source": "<GitHub URL, or path@sha>", "links": ["<URL or path@sha>", …], "reconstructed": bool, "supported_by": ["<source>", …], "kept": "kept|no longer kept|from a kept copy", "waits_on_owner": bool, "follows": ["<event id>", …] }`.
  Where each kind's fields come from, to be confirmed or marked `not recorded` by E2 (experiments/P-005-E2.md) before freeze: branch: the ref and the pull request that names it; commit: the commit (author, committer, both dates with offset, `Agent-Session:` and `Spec:` trailers); pull request: the pull request (opened, ready for review, closed, merged); check: workflow runs and commit statuses (check runs are not readable with the key, library/facts/F-gh-fgpat-limits-01.md:4); review: the pull request's reviews (library/facts/F-rec-pr-review-fields-01.md:4); merge: the pull request's merge fields and merge commit; deploy: deployments, their statuses and the run's review history (library/facts/F-rec-deploy-review-01.md:4); gate: a `dor`, `criteria` or `launch` card, its gate case and its ruling record; decision: a `dor-fail` or `failure` card and its answer record, and an owner question and its answer; research: an intake request, its memo and its source check; stop: a `stop` card and its answer. The piece of work comes from the item id in the record's path or trailer; the project from the repository.
  Awkward cases:
  - A commit's author and committer dates are set by whoever commits (library/facts/F-git-dates-settable-01.md:4), so a commit's time has the commit's writer, not `GitHub`.
  - A re-run keeps its run id and raises its attempt (library/facts/F-rec-actions-actor-attempt-01.md:4): each attempt is one event, `follows` the one before, and `who` is the run's triggering actor with `on_behalf_of` its actor where they differ.
  - A time written with `-00:00` has an unknown offset (library/facts/F-rec-rfc3339-unknown-offset-01.md:4): `offset_known` is false.
  - An object GitHub has deleted under its retention setting: `kept` is `no longer kept` when another record (a commit status, a pull request's checks summary, a dispatch-log entry) shows it existed; otherwise no event.
  - A card with two dispatch-log `card` entries: the S-009 rule's pick (the earliest), so the timeline and the desk agree.
  - A record in a form the reader does not know: `kind` `other` with its own name if it is a GitHub object; nothing if it is a file outside the model's forms.
  A test marked `join-test: S-010/J1` covers it, with one sample record of each of the eleven kinds and each awkward case.
- **J2 —** event record → state set (D1, D2). The closed set, each with one colour and one word: `queued`, `running`, `waiting on you`, `passed`, `failed`, `stalled`, `cancelled`, `done`, `unknown`, `other`. GitHub's check and run values map so: queued, requested, pending → `queued`; in_progress → `running`; waiting (a deployment awaiting review) → `waiting on you` only when the owner is a required reviewer, otherwise `queued`; success → `passed`; failure, timed_out, startup_failure → `failed`; cancelled → `cancelled`; neutral, skipped, stale, action_required → `other` with GitHub's word (library/facts/F-gh-check-states-01.md:4). Commit statuses: pending → `running`, success → `passed`, failure and error → `failed`. A model step: started → `running`; waiting on the owner → `waiting on you`; ended by its answer or ruling → `done`; AC8's stall → `stalled`. `waiting on you` never shares a colour with `failed` or `stalled`. Awkward cases: a value not listed → `other` with its word; no value → `unknown`. A test marked `join-test: S-010/J2` covers every listed value.
- **J3 —** event records → the timeline view (D2). The view draws only what the records hand it: shape by `kind`, colour and word by `state`, the writer by `writer`, a "reconstructed" mark by `reconstructed`, "no longer kept" or "from a kept copy" by `kept`. It works out no field. Awkward cases: an event whose `occurred_at` is `not recorded` is placed by `recorded_at`, marked "recorded at"; with neither, it is placed after the event it `follows` and shows "time not recorded"; with none of these it is listed at the end of its piece of work, "time not recorded". A test marked `join-test: S-010/J3` covers it.
- **J4 —** the waiting list → the timeline's lead, every core screen not yet replaced, the notification route and the counts (D3). One list, made once per read by the desk's card-making code from the records and a moment it is handed: each entry `{ "id", "project", "kind": "card|question|gate|pull request|deploy", "title", "due_at": "<RFC 3339>", "open_key": "<the notice key>", "order": int }`. Decision cards come from S-009's one rule unchanged; gate cards, owner questions and pull-request cards as the desk lists them today; deploys awaiting the owner's review are added. `order` keeps the desk's published order (docs/PROJECT.md:116). Awkward cases: a read that did not get a project's records keeps that project's entries as last read, marked with their as-of time (AC16), and S-009's flags pass through unchanged; a deploy on a private repository whose plan has no required reviewers is not a waiting step (library/facts/F-gh-env-01.md:4). A test marked `join-test: S-010/J4` covers it.
- **J5 —** the waiting list → the alert route → the owner's phone (D3). What is handed: each entry newly due since the route's last run, with `id`, `project`, `title` and `open_key`, and each entry whose state changed. The route keeps the last list it sent from, so it sends once per entry and again only on a change (AC23). The notice opens `open_key` (AC24). Whichever route the Design chooses (a sender in each repository, a program on a Cloudflare timer, or a webhook on each repository, plan line 180), it takes this list from the card-making code, as today's sender does (docs/PROJECT.md:588), and does not make its own. A change to the sender's own files (src/notify/**) needs the owner's approval (plan line 108). Awkward cases: a route run that cannot read a project sends nothing for that project and says nothing for it until a read succeeds; a run delayed or dropped by GitHub's schedule (library/facts/F-gh-12b.md:4) is caught by the outside check (J7); a notice already sent for a step answered since is not withdrawn. A test marked `join-test: S-010/J5` covers it.
