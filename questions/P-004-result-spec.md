# Ruling needed: How should the widget test's result be filed, so it passes the desk's scope check?

Milestone: none (the widget's milestone, M5, is still only a proposal in its plan, so nothing here serves a milestone yet)
Asked in session: session_01QBwHGJ3UVJ6HY4SS92w7UW

WHY: The widget test's plan says the Builder writes up its result and files it beside the desk's other test results. One of the desk's checks needs every Builder commit to carry a label naming a written spec with its own file. The widget project, P-004, has no spec, and can't get one before its Design gate: the desk gives a project a spec only when you pass that gate, and a spec must name a milestone you have approved, while the widget's is still a proposal. A label naming the project itself fails the check, and so does no label. The nine commits you exempted last time failed for that first reason: they named the project, by my mistake. So the result needs a way through before the Builder files it. If you choose a second test in the other question, its written plan and its result need the same answer as this result; a repeat's result does too. Until you rule, the result isn't filed. The test's plan deletes the test data only after the result is filed: both the copy on its branch of your private portfolio repository and the copy on your phone. The two test keys are another matter: no option needs them, so you can delete both on GitHub now, earlier than the test's plan says. That is safe because the judging is done and a new test would make new keys, and it ends the send key's ability to change portfolio's main branch before its 7-day expiry. The widget on your home screen will then just fail to refresh until you remove it. Nothing the desk does or shows changes, whichever you choose.
OPTIONS:
  A. "Exempt each such commit (Recommended)" — "The Builder files the result where the test's plan says, in a commit with no spec label, on purpose, since P-004 can't have a spec before its Design gate. That commit is then added to the desk's list of commits its scope and surface checks skip, with an entry in the decision log saying why. If you choose a second test, its written plan's commits and its result's are handled the same way, and a repeat's result too; last time's plan took nine commits. The list so far holds the desk's founding commit and last time's nine, which were a mistake already on GitHub; these would be its first planned entries, each shown to you first and checked by the Reviewer. Your merging each pull request is your approval. Quick."
  B. "Keep the Reviewer's record as the result" — "No result file is written. The Reviewer's verdict, already on the desk word for word with a plain summary written for the result, stands as the result, and the desk's notes record that the test's plan named a file that was not written. No exemption and no check change, and the test data can be deleted as soon as you rule. The folder of the desk's test results has a gap where this one would be, and it covers only this result: a second test's plan would still need A or D."
  C. "Wait for P-004's spec" — "The result is filed once P-004 has a spec, after its Design gate. Any widget P-004 goes on to build, a fallback included, gets one there. No exemption, but the test data and the phone's copy wait, perhaps for weeks, and if P-004 is dropped the result is never filed. A second test's plan or a repeat's result would wait for the gate too."
  D. "Change the check" — "The check is changed so a Builder commit may name a project like P-004 when it changes only a test result file. Fixes this for every later project, but the desk's checks come from its operating model, so a change made only here could be undone at the next update: the lasting fix is a change to the model, with its own written plan, the Critic's check, the Reviewer's and your approval. Days to weeks; the result waits."
RECOMMENDATION: A, whichever you choose in the other question, because it files the result as the test's plan says, uses the desk's own way of letting a known commit past a rule, shows you each commit before you approve it, and lets the test data be deleted within days; with a second test it is also the only option that lets that test start within about a week. My confidence is medium. It would change if other projects will soon need Builder records before their Design gate: then D is the lasting fix, and A still covers P-004 while D is made, which you can ask for under Other; or if you'd rather never exempt a commit on purpose and choose no second test: then B.
