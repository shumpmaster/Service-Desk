only. While the page is open it calls the function every 60 seconds per connected project; the
function holds a read-only fine-grained GitHub token, makes conditional GitHub REST reads and hands

holds no write credential.

scrolling Claude Code sessions, so waits are missed or slow and "quiet" can't be trusted

## Terms used in this spec
- **Connected project:** an entry in `src/config/projects.json` (J7) that the read token can read.
  At launch there are two: Service-Desk (operating model v3: `status/`, `queue/`, `dispatch-log/`)
  and Personal-Org-Operating-Model (governed under v2.5.1, with `docs/sprints/` and
  `docs/LEDGER.md`, and no `status/`, `queue/` or `dispatch-log/`; checked 2026-10-06 at 677fe5a).
  The design is sized for up to 5.
- **Model of a project:** `v3` or `v2.5`, set in J7. It decides which records J9 reads.
  - v3 projects get the full pipeline view.
  - v2.5 projects get the **reduced view** (J9): sprint, headline and "next" from the ledger, with
    PRs, questions and CI. They have no per-item stages and no "running now", because v2.5.1
    records neither.
- **Card:** a file `queue/<item>-<gate>-<n>.md` directly under `queue/` in a v3 project, written by
  the Orchestrator. Its **answer** is `decisions/<item>/<gate>-<n>.md`, which is also the path the
  card names on its own `answer:` line (J2). Card files are kept after answering: on 2026-10-06 all
  12 cards in Service-Desk `queue/` have answer files.
- **Owner question:** a file `questions/<name>.md` (`<name>` holds no `/`) other than
  `questions/_TEMPLATE.md`, in either model, in the form of `questions/_TEMPLATE.md`
  (`# Ruling needed:`, `WHY:`, `OPTIONS:`, `RECOMMENDATION:`, `RISK CLASS:`, `DEFAULT:` and
  `TIMEOUT:`; J2).
  - **Its answer (v3 projects):** `decisions/questions/<name>.md`, whose first line is
    `Ruling: <choice>`. That is how questions are answered today:
    - Service-Desk e012edb added `decisions/questions/Q-005-sources.md`, whose line 1 is
      `Ruling: A`, and deleted `questions/Q-005-sources.md` in the same commit;
    - f45d10e did the same for `P-001-acting-route` and `P-001-planning-scope`.
  - **When it is open:** while the question file exists and no answer file exists.
  - **v2.5 projects:** there the ruling goes to the ledger, and the file is deleted
    (Personal-Org-Operating-Model f2ac482 recorded the rulings on Q-005 to Q-014 as L-0017 to L-0026
    and deleted `questions/Q-005-…` to `questions/Q-014-…`). So in v2.5 a question is open while its
    file exists.
- **Needs the owner (flagged):** exactly these four things, in a connected project.
  - An open card: a card with no answer file on the default branch.
  - An open owner question (above).
  - An open, non-draft pull request whose base is the project's default branch, except one the
    Orchestrator merges itself (head branch `item/<id>` in a v3 project: the merge gate merges item
    branches, model S-013 AC3). The owner's own PRs count: agents push under the owner's account,
    and GitHub won't let them request the owner's review (P-001-build-path.md, question 1).
    - **What the repositories show (2026-10-06, REST `pulls?state=all` and `pulls/<n>`; observed,
      C):** the two repositories hold 53 PRs (33 in Service-Desk, 20 in
      Personal-Org-Operating-Model).
      - Every one was opened by the owner's account (`shumpmaster`) against `main`, with no
        requested reviewers.
      - Every one has been merged, each by `shumpmaster`. None was merged by the Orchestrator.
      - None came from an `item/` branch.
    - So in practice every such PR waits on the owner's approval or merge.
  - A v3 status file in state `waiting-owner` whose card file is not yet on the default branch. This
    is a safety net against a missed decision, worded "waiting on you: card <gate>-<n> (card file
    not found)".
- **Activity:** anything shown but not flagged. That covers:
  - CI results.
  - Draft PRs, PRs whose base is not the default branch, and `item/` PRs in v3 projects.
  - Dispatch-log events: dispatches, outcomes, errors, retries and anomalies.
  - Sessions that run past their time limit.
  - Queue files that can't be parsed.
  - The Chief of Staff's `-notes.md` files.

  "A gate catching a problem, or an agent retrying, is activity" (PROJECT.md Part 2).
- **Open window:** a span during which the desk page is visible in the foreground on a device (the
  browser's page-visibility state is "visible").
- **Read successfully:** both of these hold.
  - The project's last poll call (J6) returned `state` `ok` or `unchanged`.
  - Every blob call that the poll's tree change needed has returned `ok`.

  An `unchanged` answer (every steady-poll request returned 304) counts: GitHub answered and
  nothing was new. These do not count: `partial`, `cant-read`, a 403 from the function, a Cloudflare
  error and a network failure.
- **Quiet:** no flagged item in any connected project, **and** every connected project read
  successfully within the last 3 minutes.
- **Milestone accepted:** four steps, in order (P-001-build-path.md, question 0; the deploy route
  in "Toolchain and deploy route").
  1. The Reviewer's verdict on the milestone's pull request is PASS.
  2. The owner has merged it.
  3. The owner has approved desk-deploy's `preview` job for that merge, and it has deployed `main`
     to the preview.
  4. The owner has tried the preview and accepted the milestone.

  Problems found on the preview are fixed forward, in a new pull request, which also needs the
  Reviewer's PASS.

## Acceptance criteria (scenarios; draft — the owner approves them by merging each milestone)
Each criterion is a plain scenario. "Within 5 minutes" is V1's figure. A "phone" screen is 360 CSS
pixels wide and a "desktop" one is 1280. The tests named in J1–J10 use the real samples quoted in J2
and J9.

### M1 — Read-only status page, behind Access, on the preview (as early as possible)
*Covers D2 and D2.2, D3.1, D3.2 (reading only), D3.3, D5 and D6.1 (preview). EXP-001, EXP-002 and
EXP-004 run on the preview after M1's merge.*

**What waits on the owner**
- AC1 [trace: V1 → AC1] — When a card is committed to a connected project's default branch while
  the desk is open on the owner's phone, then within 5 minutes the project's box shows it as
  waiting on the owner and the box moves to the top of the Universe screen.
- AC2 [trace: V1 → AC2] — When an open, non-draft pull request into a connected project's default
  branch exists, whoever opened it (the owner's own included), then within 5 minutes of it opening,
  or of a draft being marked ready, the desk flags it with its title and a link to it on GitHub.
  Within 5 minutes of it being merged, closed or turned back into a draft, it is no longer flagged.
  A draft PR, or a PR into any other branch, is shown as activity only.
- AC3 [trace: V1 → AC3] — When an owner question file (`questions/<name>.md`, not `_TEMPLATE.md`)
  is on a connected project's default branch, then within 5 minutes the desk flags it with its
  title (the text after `# Ruling needed: `). It is no longer flagged within 5 minutes of either
  of two things: its answer file `decisions/questions/<name>.md` being committed (v3), or the
  question file being deleted (either model).
- AC4 [trace: V1 → AC4] — When the owner opens the desk after it was closed, then the screen says
  "Checking…" and never "Quiet" until every connected project has been read successfully since
  opening. Once they all have, every flagged item in every connected project is shown.
- AC5 [trace: V1 → AC5] — When a connected project can't be read, then its box says "Can't read
  since HH:MM" with the reason in words, sorts above every box except those with flagged items, and
  the screen as a whole does not say "Quiet". The causes are:
  - token rejected or expired;
  - GitHub rate limit;
  - GitHub, Cloudflare or network error;
  - configured default branch not found;
  - more open PRs, check runs or tree entries than one read can page through (`partial`, J1);
  - no successful read for 3 minutes.
- AC6 [trace: V2 → AC6] — When a connected project has any of the following, then the desk shows it
  as activity in that project's box and does **not** flag it, count it as waiting, or move the box
  up for it. A failing default branch still orders the box by AC8's third rank; that is not a flag.
  - a failing CI result on its default-branch head (J1's reduction rule);
  - a draft PR;
  - a new dispatch-log event, including an agent's retry and an Orchestrator anomaly (J9);
  - a session running past its time limit;
  - a queue file that can't be parsed.
- AC7 [trace: V2 → AC7] — When a card's answer file is committed by any route, then within 5
  minutes the desk stops flagging that card while open, and on next opening it is not flagged.

**Seeing each project**
- AC8 [trace: V4 → AC8] — When the owner looks at the Universe screen, then each connected project
  has one box, ordered worst first: flagged, then can't-read, then default branch failing, then the
  rest by name. Each box shows:
  - its state: the flagged count, or "Can't read", or quiet;
  - its headline (J9);
  - its sprint (v2.5), or for v3 its open items with their stage names;
  - its default-branch CI result (J1).
- AC9 [trace: V4 → AC9] — When the owner opens a v3 project's pipeline view, then it lists every
  item that has a status file (J9). For each item it shows:
  - its id and kind;
  - **its stage**, by name: 2 Shape, 3 Define, 4 Lock the checks, 5 Produce, 6 Launch, 8 Evidence;
  - **what is running now**: for `dispatched`, the role and how long it has run;
  - **what waits on the owner**: for `waiting-owner`, the card, flagged and linked;
  - **what is next**: for `ready`, the role the Orchestrator dispatches next; for `returned`, "the
    Orchestrator routes the <role>'s return (verdict <v>)";
  - "as of", the time of the item's latest dispatch-log entry.

  Finished items (`done`, `closed`) are folded into one line each, showing their outcome. A field
  the records don't give is shown as "not recorded", never guessed.
- AC10 [trace: V4 → AC10] — When the owner opens a v2.5 project, then the desk shows the reduced
  view (J9). It shows:
  - the open sprint's title;
  - the headline, the latest ledger entry's title;
  - "next", that entry's `licenses_next:` text;
  - the project's flagged PRs and questions, and its CI.

  "Items" and "running now" say "not recorded in this repository's records (operating model
  v2.5.1)".
- AC11 [trace: V1 → AC11] — When the owner taps a flagged card on the phone, then its full text is
  shown with every option it offers, rendered from its markdown, without sideways scrolling, plus
  the answer path the card names. (In M1 the desk links to the card on GitHub; answering from the
  desk is M2.)
- AC12 [trace: V1 → AC12] — When the owner taps a flagged owner question on the phone, then its
  full text is shown, rendered from its markdown, without sideways scrolling (J2). The view shows:
  - its title;
  - WHY;
  - every option under OPTIONS, with its letter and text;
  - the RECOMMENDATION, marked on its option;
  - RISK CLASS, REVERSIBILITY and BLAST RADIUS;
  - the DEFAULT, labelled "per the question file: defaults to <letter> at <raised time + TIMEOUT
    hours>" when the question is reversible, and "per the question file: never defaults" when it
    is irreversible (AGENTS.md §5).
    - The label only reports what the file says. Service-Desk does not enforce question timeouts:
      no script adopts a default. The desk must not imply that one will.

  A field the file lacks is shown as "not given". The question is still flagged.

**Trust, budget and the first deploy**
- AC13 [trace: V4 → AC13] — When any request reaches the desk's function without a valid
  `Cf-Access-Jwt-Assertion` for the owner's email address, then it answers 403 and makes no GitHub
  call. "Not valid" covers a JWT that is missing, expired, for the wrong audience, wrongly signed, or
  for another email. A `POST` without `Content-Type: application/json`, or with a foreign `Origin`,
  is refused (J6's request checks). The preview's `pages.dev` address and its preview deployments
  prompt for Access login before anything is served. The Reviewer's security review of the login and of the
  read token's handling (D5.2) has passed before M1 is accepted.
- AC14 [trace: V4 → AC14] — *Limit: the hosting spend ceiling of $0 a month (PROJECT.md §5,
  decisions/questions/P-001-move-to-build-values.md). The trace checker accepts only V targets, so
  the formal trace is to V4, the replacement within its limits.* When the desk's open windows add
  up to 16 hours in a day across all devices, with 5 connected projects, then the function stays
  within the Free plan:
  - fewer than 10,000 function requests that day (our own margin, a tenth of Free's 100,000);
  - no Error 1027;
  - no Error 1102 on any call.

  The arithmetic and its assumptions are in "Facts relied on". A day with more than 16 window-hours
  is outside this scenario: only staying under Free's 100,000 is promised for it.
  - **Test:** a test marked `ac-test: S-001/AC14` drives the page's real poll scheduler with a fake
    clock and a fake function. It simulates 5 connected projects for 16 window-hours, with 10
    openings and 100 head changes. It asserts that fewer than 10,000 function calls are made and
    that none is a retry sooner than the next poll.
  - **Live check:** EXP-001 checks the 1027 and 1102 parts on the preview. After M1, the Chief of
    Staff reads the preview's daily request count from Cloudflare's dashboard.
- AC15 [trace: V4 → AC15] — When M1's pull request has passed the Reviewer and the owner has
  merged it, then:
  - once the owner approves it in the `preview` environment, desk-deploy's `preview` job deploys
    `main` to `https://service-desk-preview.pages.dev`, behind Access. The Builder never deploys and
    holds no secret.
  - EXP-001, EXP-002 and EXP-004 run on that deployed preview, and their results are recorded.
  - M1 is accepted only when the owner has tried the preview and the results are applied, each in a
    fix-forward pull request where code or config must change: J1's batch size, the launch route
    for M3, and the J7 values.

### M2 — Answering cards, time asked, agent usage and context windows
*Covers D3.2 and D4.1 (answering), D3.5, V5 and D3.6. EXP-003 runs at M2's start.*

- AC16 [trace: V4 → AC16] — When the owner picks an option on an open card (and optionally types a
  note), then the desk opens GitHub's new-file page for that card's repository and default branch.
  The page has the file name `decisions/<item>/<gate>-<n>.md` and J3's content filled in, and the
  owner commits it there; the desk itself writes nothing to GitHub. If the answer file already
  exists, the desk shows "already answered: <verdict>" and offers no link.
- AC17 [trace: V4 → AC17] — When the prefilled link would be longer than the cap
  (`linkCap` in J7, 6,000 characters unless EXP-004 records less), or that repository's
  `contentPrefill` is `false` (J7), then the desk instead shows the answer text with a "Copy" button
  and opens the new-file page with only the file name filled in.
- AC18 [trace: V4 → AC18] — When a connected project's `webCommitsToDefault` is `false` (J7), then,
  before opening the link, the desk shows: "This repository doesn't take commits to <default
  branch> from the web. On GitHub, choose 'Create a new branch' and then open the pull request
  GitHub offers; the card stays flagged until that pull request is merged."
  - The link itself is J3's URL, unchanged.
  - The desk creates no branch and opens no pull request.
  - The card stops being flagged only when the answer file is on the default branch (AC7). Until
    then the open pull request is flagged too (AC2).
- AC19 [trace: V4 → AC19] — When the owner picks an option on an open owner question in a v3
  project (and optionally types a note), then the desk opens GitHub's new-file page for that
  repository's default branch.
  - The page has the file name `decisions/questions/<name>.md` and J3's question content filled in:
    `Ruling: <letter>`, then `Question: questions/<name>.md`, then the note if there is one. The
    owner commits it there.
  - AC17's and AC18's fallbacks apply to it as to cards.
  - If the answer file already exists, the desk shows "already answered: <ruling>" and offers no
    link.
  - The question stops being flagged once the answer file is on the default branch (AC3).
  - Deleting the question file stays with the Chief of Staff, as today. That is a step in the
    operating notes (AC27), not the desk's.
  - **For a v2.5 project,** whose rulings go to its ledger, the desk shows the ruling text
    (`Ruling: <letter>` and the note) with a "Copy" button and the note "this repository records
    rulings in its ledger; give this to your session". The desk opens no link.
- AC20 [trace: V5 → AC20] — When the owner opens "Time asked of you" for a v3 project, then it
  lists each card raised in the last 30 days, with:
  - the time it was raised;
  - the time it was answered;
  - the wait between them;
  - whether the answer was a proxy (J2).

  Open cards show their wait so far. A summary line gives the count and median wait for the last
  14 days.
  - **Owner questions:** the view also lists every owner question raised in the last 30 days, open
    and answered, with the same four columns. "Raised" is the oldest commit of
    `questions/<name>.md`. "Answered" is the oldest commit of `decisions/questions/<name>.md`
    (v3 only, J2).
  - **Rulings with no question file** (asked in a session, like most of
    `decisions/questions/P-001-*.md`) have no raised time. They are not listed.
  - **A v2.5 project** shows "no cards in operating model v2.5.1" and its open questions only, with
    their wait so far. Its answered questions show as "answered questions: not recorded (operating
    model v2.5.1 records rulings in the ledger)", exactly as J2 says.
- AC21 [trace: V5 → AC21] — When the owner looks at the Universe screen, then a footer line shows
  V5 against its goal: "Median answer time, weekday cards, last 14 days: <h>h <m>m (goal under 4h;
  <k> cards)".
  - It covers every v3 project, computed as J2 says. An open card counts with its wait so far.
  - When no weekday card falls in the window, it says "no weekday cards in the last 14 days".
- AC22 [trace: V4 → AC22] — When the owner opens a v3 project's "Agents" view, then it lists every
  agent session of the last 14 days (J10), with:
  - the item and role;
  - the start (dispatch time) and end (outcome time);
  - the run time;
  - the result and verdict;
  - "retry" when it re-dispatches a role whose previous session ended in `error`.

  A session still running shows its elapsed time. Each item has a timeline: its sessions and its
  card waits on one time axis, in time order, readable on the phone.
- AC23 [trace: V4 → AC23] — When a session's record carries usage figures (J10), then the Agents
  view shows, for that session:
  - its tokens by kind (input, output, cache read, cache write);
  - its turns;
  - its peak context-window use as tokens and as a percentage of the window.

  A figure the record lacks is shown as "not recorded" for sessions that ran before D7.2 was

- AC25 [trace: V1 → AC25] [trace: V2 → AC25] [trace: V5 → AC25] — When the desk is used during a week, then on the

- AC26 [trace: V3 → AC26] — When the owner wants to add a connected project, then the operating

- AC27 [trace: V3 → AC27] — When the owner or Chief of Staff needs to run the desk, then the

  - renewing the read token;

  - adding a project (AC26);

  - questions answered from the desk: `review_check.py questions` counts a question as open until

  - checking the deploy gate (Setup CS9): at each milestone acceptance, both environments'

  - approving a deploy: approve only when the run's SHA equals the merge-commit SHA of a pull
    request the Reviewer passed; production only for a SHA already accepted on the preview.

  Each step is written so that it can be done in under 10 minutes (V3).
- AC28 [trace: V4 → AC28] — When M3 is accepted and the owner approves launch, then:
  - **production:** the `needs-you` production deployment serves the desk at its `pages.dev`
    address and custom domains. It is deployed only by the Chief of Staff's workflow job in the
    GitHub environment `production`, which needs the owner's approval.

## Join sheets

- **J1 — GitHub REST → desk function (reader).**
  - **Every request:** each `GET` goes to `https://api.github.com` with
    `Authorization: Bearer <read token>`, `Accept: application/vnd.github+json` and
    `X-GitHub-Api-Version: 2022-11-28`. When the page holds an ETag for the URL, it also carries
    `If-None-Match: <etag>`.
    - `{o}/{r}` and `{default}` come from J7 (`repo`, `defaultBranch`). Nothing is looked up to
      learn the default branch, so a steady poll needs no fourth request.
  - **Poll call** (one per project per 60 s, J6). It makes these requests in this order:
    1. `GET /repos/{o}/{r}/branches/{default}`. From the body the function takes the head commit
       `commit.sha`, `commit.commit.tree.sha` and `commit.commit.committer.date`. This is the only
       response body the function parses; every other body it passes on as text (below).
    2. `GET /repos/{o}/{r}/pulls?state=open&per_page=100`.
    3. `GET /repos/{o}/{r}/commits/{head}/check-runs?per_page=100`.
    4. Only when the head differs from the head the page sent (or the page sent none):
       `GET /repos/{o}/{r}/git/trees/{treeSha}?recursive=1`.

    With one page each, a steady poll is exactly three requests.
  - **Paging.** When a list response carries `Link: <…>; rel="next"`, the function follows it, up
    to 3 pages per list (300 PRs or 300 check runs).
    - Each page is one request with its own ETag.
    - If a 4th page would be needed, the function returns `state: partial`, reason `too-many`. It
      can tell from the `Link` header alone, without parsing a body.
    - A tree whose JSON has `truncated: true` is detected by **the page**, which parses the tree. The
      page sets the same `partial` / `too-many` on its own record of the project. The function
      doesn't parse the tree.
    - Either way, the project is not read successfully (AC5), so a missed PR or check run can never
      show as "Quiet".
    - Every page is requested on every poll, because a change on page 2 doesn't change page 1.
  - **Blob call** (J6): up to 25 requests, of two kinds.
    - `GET /repos/{o}/{r}/git/blobs/{sha}` with `Accept: application/vnd.github.raw+json`. If that
      returns JSON instead, the function decodes `content` from base64.
    - For owner questions and their rulings only (J2), a history request:
      `GET /repos/{o}/{r}/commits?path=<path>&sha={default}&per_page=100`.
      - **Oldest commit** (the path's creation): if the response's `Link` header has `rel="last"`,
        the function also fetches that page, and the page takes its last entry's
        `commit.committer.date`. That is at most 2 requests per path, with no limit on history
        length.
      - **Newest commit:** the first entry of page 1.
      - The function returns the raw pages, and the page reads them.
    - Blobs are fetched by their sha, so they never change and carry no ETag. The page keeps each
      parsed result keyed by blob sha (J6).
  - **Limits per invocation.**
    - A poll call makes at most 8 GitHub requests (3 + 2 extra pages per list + 1 tree); a blob
      call makes at most 25. Both sit inside the 30 that J1 allows per invocation.
    - J8's key fetch adds at most 1, and redirect hops count too (F-cf-workers-02). The 50 on Free
      are never approached.
    - At most six requests wait for headers at once, and a seventh queues (F-cf-workers-03 for the
      six, A; F-cf-workers-07 for the queuing, B). So a full blob call runs in about five waves of
      six. Whether its wall time and CPU fit Free is EXP-001's measurement. If not, the blob batch
      size (one constant, `BLOB_BATCH = 25`) is lowered.
  - **The function parses no record content.**
    - It returns the PR pages, check-run pages, tree and blobs to the page as raw text (J6), and
      the page does all record parsing (J2, J9, J10).
    - The function's own work is J8's check, the branch body, the response headers (`ETag`,
      `Link`, `X-RateLimit-*`, `Retry-After`), J6's request checks, and assembling the response.
      Base64 decoding happens only if GitHub ignores the raw media type.
    - This keeps CPU per call small and independent of repository size; EXP-001 measures it anyway.
  - **CI reduction rule** (one result per head, computed on the page from all check-run pages; the
    words are GitHub's `status` and `conclusion` values):
    - `failing` if any run has `status: completed` and a conclusion of `failure`, `timed_out`,
      `action_required` or `startup_failure`;
    - otherwise `running` if any run's `status` is not `completed`;
    - otherwise `passing` if at least one run concluded `success`, and every other run concluded
      `success`, `neutral`, `skipped`, `cancelled` or `stale`;
    - otherwise `none`: no check runs, or all of them skipped, neutral, cancelled or stale.
    - Real sample: Service-Desk `main` on 2026-10-06 has 8 runs: `commit`, `record`,
      `prepare (0)`, `owner-signal`, `governance` and `decide` concluded `success`, and `collect` and
      `session` concluded `skipped`. That reduces to `passing`.
    - `cancelled` counts as not failing because the Orchestrator's own runs are cancelled and
      skipped by design (model S-018). That is my choice (C), and it is easy to change.
  - **Awkward cases:**
    - **304 on every steady-poll request:** returns `unchanged` with nothing re-sent.
    - **401, or 403 without rate-limit headers:** `cant-read`, reason `token`.
    - **403 or 429 with `X-RateLimit-Remaining: 0` or `Retry-After`:** reason `rate-limit`, and
      `retryAfter` is set from the reset header. The page doesn't poll that project again before
      then.
    - **404 on the branch:** reason `config`, "default branch <name> not found".
    - **403 on check-runs only:** CI shows "can't read checks", and the project stays readable.
      This is the case where the token lacks a checks permission (EXP-004 Q4).
    - **GitHub 5xx or a network failure reaching GitHub:** reason `github`.
    - **Too many pages:** `partial`, reason `too-many`, set by the function. **A truncated tree:**
      the same, set by the page.
    - **Retries:** a failed or rate-limited read is never retried within an invocation, or sooner
      than the next scheduled poll.
  - A test marked `join-test: S-001/J1` covers it, with recorded GitHub responses including a
    two-page PR list and the 8-run check-run sample above.

- **J2 — Cards, answers and owner questions → read model (page side).**

      S-013 AC5, shown as activity), and any other path under `queue/` that doesn't match (activity,

      - Line 1: `# Decision card — P-001 stop-6`.

    - What the desk takes from it:
      - the title, which is the first line under `## 1. The decision`;
      - the options, each the backquoted word at the start of a line under `## 4. Options`;
      - the answer path, which is the first backquoted path on the `answer:` line.

      "can't parse" note and is still flagged while unanswered. A misparse never hides a card.
  - **Answers.** An answer is a path matching `^decisions/([A-Z]+-[0-9]+)/([^/]+)-([0-9]+)\.md$`.

      exists.

      answer blob only when the dispatch log has no `decision` entry for it (J6), for example in
      the minute before the Orchestrator logs it, or for AC16's "already answered". Sample: `decisions/P-001/stop-6.md` line 1 reads
      `Decision: re-scope`. Later lines such as `Proxy:` are ignored.
  - **Raised and answered times (v3), from the dispatch log** (J9's source, with no extra requests).
    - Raised: the `time` of the entry with `"action":"card"` and matching `item`, `gate` and `card`.
      Sample: `{"action":"card","card":6,"gate":"stop","item":"P-001",…,"time":"2026-10-06T18:51:54Z"}`.
    - Answered: the `time` of the entry with `"trigger":"decision"` and `"record"` equal to the
      answer path. That entry also gives `word` (the verdict) and `proxy`. Sample:
      `{"card":6,…,"proxy":false,"record":"decisions/P-001/stop-6.md",…,"time":"2026-10-06T21:31:02Z",…,"word":"re-scope"}`.
    - Checked against git (C): the Orchestrator logs a card 33–40 s before its commit, and logs an
      answer 13–42 s after the owner's commit, in the three cases checked (P-001 stop-6, P-001
      failure-5, Q-003 failure-1). That is well inside V5's hour scale.
    - Two months are read, the current one and the one before (`dispatch-log/<YYYY-MM>.jsonl`), so
      AC20's 30 days are covered across a month boundary.
  - **Owner questions** (both models). Paths `^questions/([^/]+)\.md$`, except
    `questions/_TEMPLATE.md`.
    - **The form**, from `questions/_TEMPLATE.md` lines 1–9 and the real sample

      - Line 1: `# Ruling needed: <title>`.
      - Then labelled lines `WHY:`, then `OPTIONS:`, followed by option lines `  A. <choice> —
        <text>`.
      - Then `RECOMMENDATION: <letter> — <reason>`, then

        `DEFAULT: <letter>   TIMEOUT: <hours>`.
    - **What the desk takes from it** (AC12):
      - the title;
      - each option, from a line matching `^\s+([A-Z])\. (.+)$` between `OPTIONS:` and the next
        line starting with a capital label and `:`;
      - the recommendation letter, the first `[A-Z]` after `RECOMMENDATION:`;

        label up to the next label or the end of the line.
      - Sample Q-005-sources gives options `A` (Accept) and `B` (Strict), recommendation `A`,

      `decisions/questions/Q-005-sources.md` (`Ruling: A`) and

        still exists. The Chief of Staff deletes it later, as in e012edb.
    - **Raised time:** the oldest commit of `questions/<name>.md` (J1's history request). That
      works for a deleted path too; GitHub REST listing a deleted path's history is C.
    - **Answered time:** the oldest commit of `decisions/questions/<name>.md` (v3).
    - **Cost:** both are fixed once known, so the page keeps them by path and never asks again.
      - For a ruling, the page first reads the answer's time, then the question's only if the
        answer falls within AC20's 30 days.
      - A ruling whose question path has no history was asked in a session, not by file. It is not
        a desk question and isn't listed (AC20).

      not recorded (operating model v2.5.1 records rulings in the ledger)".
  - **Pull requests.** From the raw PR pages (J1), the page reads `number`, `title`, `html_url`,
    `draft`, `base.ref`, `head.ref`, `user.login` and `created_at`.
    - The raised time shown for a flagged PR is `created_at`.
    - A PR that was a draft and later marked ready is shown with its `created_at` too; the list
      doesn't give the ready time (C).
  - **Time asked, and V5.**
    - Each card's wait is answered minus raised. An open card's wait is now minus raised.
    - AC20's median is over cards raised in the last 14 days, open ones included with their wait so
      far.
    - V5 (AC21) uses counted time across all v3 projects, not elapsed time. A card's counted wait is
      the total length of the overlap between [raised, answered) (or [raised, now) while open) and
      the `v5Clock` windows.
      - Launch values, pending the owner (see V5): 07:00–22:00, Monday to Friday, in
        `ownerTimeZone`, America/Chicago.
      - Daylight-saving changes are handled by computing window edges in that zone (C: this relies
        on the browser's `Intl` time-zone data).
      - Every card raised in the last 14 days counts, and an open card counts with its counted wait
        so far. With an even count, the median is the mean of the two middle values.
      - Example: a card raised Friday 21:00 and answered Monday 08:00 counts 1 h (Friday 21:00–22:00)

- **J6 — Desk page ↔ desk function.** Both calls are `POST` with a JSON body, so the ETags travel in
  the body, not in a header.
  - **Request checks (D5.2, before J8's work is used for anything):**
    - **Content type:** the function answers 415 unless `Content-Type` is `application/json`. A
      JSON content type is not a "simple" request, so a cross-site page can't send one without a
      CORS preflight (C, browser behaviour).
    - **Origin:** the function answers 403 when an `Origin` header is present and differs from the
      origin of the request's own URL (scheme, host and port of `request.url`). That covers the
      preview, `needs-you` and each custom domain without a list.
    - **No CORS:** the function sends no CORS headers, so no other origin can read a response.
    - **Methods:** any method other than `POST` on `/api/*` gets 405.
  - **Poll call:** `POST /api/poll`.
    - Request body:
      `{ "project": "<name>", "head": "<sha>" | null, "etags": { "<GitHub URL>": "<etag>" } }`.
    - `etags` holds only the poll's own list URLs: the branch, up to 3 PR pages and up to 3
      check-run pages, so **at most 7 entries, under 2 KB**.
    - Blobs need no ETags (J1), so the ETag state no longer grows with the repository. That
      resolves the plan review's finding 6.
  - **Poll response:**
    - `{ "project", "readAt": "<ISO UTC>",`
    - `"state": "ok" | "unchanged" | "partial" | "cant-read",`
    - `"reason": null | "token" | "rate-limit" | "github" | "config" | "too-many",`
    - `"retryAfter": <seconds> | null,`
    - `"head": { "sha", "treeSha", "committedAt" },`
    - `"etags": { url: etag },`
    - `"pulls": [ "<raw page>" | null ], "checks": [ "<raw page>" | null ],`
    - `"tree": "<raw>" | null }`

    A `null` page means 304: the page reuses what it parsed last time for that URL. `tree` is
    present only when the head changed or `head` was null.
  - **Blob call:** `POST /api/blobs`.
    - Request: `{ "project", "blobs": ["<40-hex sha>", …], "history": ["<path>", …] }`.
    - **Budget:** each blob counts 1 against `BLOB_BATCH` (25), and each history path counts 2,
      because J1 may fetch its last page.
    - Response: `{ "project", "readAt", "state", "reason", "retryAfter",
      "blobs": { sha: "<raw text>" | null }, "history": { path: ["<raw page 1>", "<raw last page>"?] } }`.
    - **Refusals (400):**
      - a project name not in J7;
      - a sha that isn't 40 hex digits;
      - a history path that doesn't match `^(decisions/)?questions/[^/]+\.md$`;
      - a budget over 25.
    - The function only ever issues J1's request forms against configured repositories.
  - **The page's side.**
    - **Parsed cache:** the page keeps parsed results keyed by blob sha in local storage, and fetches
      only blobs whose sha it lacks. If storage is unavailable, it holds them in memory for the
      open window.
    - **Diffing:** it compares each new tree with the cached one to find changed paths.
    - **Which blobs it fetches:**
      - **For v3:**
        - every `status/<item>.toml`, and `governance/ROUTING.toml` (time limits, J9);
        - the two dispatch-log months, and `status/outcomes.jsonl` (M2);
        - open cards;
        - each card answer blob that has no `decision` log entry yet (J2);
        - each `decisions/questions/<name>.md` whose question is listed in AC20 (for its

## Toolchain and deploy route
- **Layout.** Everything the Builder writes for the desk lives under `src/`, and deploys run from
  `src/`.
  - `src/package.json`: Node 20 or later, ES modules. Wrangler is a devDependency pinned to an exact
    version.
  - **No runtime dependencies (decided here; the Reviewer's round-2 non-blocking 2):**
    - `src/package.json` has no `dependencies` block, and the build fails if one appears.
    - The Functions and the page import only from `src/functions/`, `src/lib/` and `src/public/`.
    - So the bundle wrangler makes of `src/functions/` at deploy time contains only reviewed
      repository code. No separate `wrangler pages functions build` step is needed.
    - The deploy job installs nothing under `src/`. A package import in a Function would therefore
      fail the deploy-time bundle, which enforces the rule a second time.
  - **No lifecycle scripts:** `src/package.json` has no `preinstall`, `install`, `postinstall`,
    `preprepare`, `prepare`, `postprepare`, `prepack`, `postpack`, `prepublish`,
    `prepublishOnly`, `publish` or `postpublish` script. desk-build fails the PR otherwise.
  - `src/package-lock.json`.
  - `src/wrangler.toml`: only the keys `name`, `pages_build_output_dir = "public"` and
    `compatibility_date`; desk-build fails the PR on any other key. The
    project name is passed on the command line (below).
  - `src/functions/api/poll.js` and `src/functions/api/blobs.js`: Pages Functions, by file-based
    routing (C).
  - `src/lib/`: the record parsers, shared by the page and the tests.
  - `src/public/`: the page.
  - `src/config/projects.json` (J7).
- **Tests.** They live in `tests/desk/`, with fixtures in `tests/desk/fixtures/`, using Node's
  built-in runner.
  - **Build command:** `npm --prefix src ci && npm --prefix src run build`. The build also checks
    J7.
  - **Test command:** `npm --prefix src test`, which runs `node --test ../tests/desk/`.
  - **No live access:** the tests use the real samples quoted in J2, J9 and J10 and a fake `fetch`.
    No test needs a token or the network.
- **Who holds secrets: nobody but the owner and GitHub/Cloudflare** (PROJECT.md §4 line 115;
  AGENTS.md §1).
  - **The Builder** holds neither the Cloudflare API token nor the read token. It never deploys,
    and it never calls the live function.
  - **The read token** exists only as a Pages secret.
  - **The Cloudflare API token** exists only as a secret of the GitHub environments `preview` and
    `production`.
  - The owner sets each by hand (Setup).
- **Workflow 1, `.github/workflows/desk-build.yml`** (the Chief of Staff's).
  - **Trigger:** `pull_request`, and pushes to `main` that touch `src/**` or `tests/**`.
  - **Access:** `permissions: contents: read`, and no secrets. It uses no environment.
  - **Steps:**
    - `npm --prefix src ci --ignore-scripts`, then the build and test commands.
    - A config check (a script in the Chief of Staff's lane, `.github/scripts/`). It fails the PR if
      `src/wrangler.toml` holds any key other than `name`, `pages_build_output_dir` and
      `compatibility_date`. It also fails if `src/package.json` has any lifecycle script (listed
      under Layout) or a `dependencies` block.
    - It uploads no artifact and hands nothing on to any other workflow.
  - **Workflow files:** a change to `.github/**` outside the Chief of Staff's lane already fails CI
    through `surface_guard.py diff --range`, because `.github/**` is the Chief of Staff's surface in
    governance/SURFACES.md. desk-build doesn't repeat that check.
  - **Branches:** the Builder's milestone branch, `build/builder/<task>`, is pushed to origin,
    which the pull request needs. desk-build is the only desk workflow that runs on it.
- **Workflow 2, `.github/workflows/desk-deploy.yml`** (the Chief of Staff's).
  - **Trigger:** only `push` to `main` with paths `src/**`, and `workflow_dispatch`. It never runs
    on `pull_request` or `workflow_run`. No pull-request branch name or artifact is ever used.
  - **Access:** `permissions: contents: read` for the whole workflow.
  - **Why `main` alone isn't enough (the Reviewer's round-3 R3-B1):**
    - `main` is unprotected, and agents push under the owner's admin account. So "code on `main`
      is reviewed" isn't enforced by GitHub.
    - So **every deploy job runs in an environment whose required reviewer is the owner.** That
      covers `preview` and `production`, and `exp-002` too.
    - GitHub holds each job until the owner presses Approve, which the GitHub mobile app offers.
  - **Each approval is tied to the commit it deploys (R4-B1).**
    - **Push runs** check out exactly `${{ github.sha }}`, never "the tip of `main`".
    - **`workflow_dispatch` runs** require an input `sha`.
      - The first step receives it through `env:`, never interpolated into the shell.
      - It fails unless the input matches `^[0-9a-f]{40}$` and equals `git rev-parse origin/main`
        at run start, so a dispatched run can't deploy a commit behind or past the reviewed tip.
      - It then checks out that SHA.
    - **`run-name`** is `deploy ${{ github.event_name == 'push' && github.sha || inputs.sha }} —
      ${{ github.event.head_commit.message || inputs.note }}`.
      - The approval screen shows the full SHA. GitHub expressions have no substring function, but
        its first 7 characters are the short SHA on the PR page.
      - On a push from a merge, it also shows the merge commit's message, which begins
        `Merge pull request #<n>`. A dispatch carries a `note` input, in which the Chief of Staff
        names the PR.
  - **The owner's approval rule:**
    - Approve only when the run's SHA equals the merge-commit SHA shown on the page of a pull
      request that the Reviewer passed. Fix-forward PRs need the Reviewer's PASS too.
    - Reject every other run.
    - The actor name can't separate the owner's runs from an agent's: agents act under the owner's
      account, so both show as `shumpmaster`. The SHA is the only thing to check.
    - **Production:** approve only a SHA that the preview has already deployed and that the owner
      has accepted on the preview.
    - **`exp-002`:** the owner approves it when he or the Chief of Staff asked for it. It deploys
      nothing.
  - **Concurrency:** each job has its own `concurrency` group, `desk-deploy-preview`,
    `desk-deploy-production` or `desk-deploy-exp-002`, with `cancel-in-progress: false`. So two
    approved runs never deploy over each other, and a waiting run is not silently cancelled.
  - **Every deploy job:**
    - checks out the approved SHA, as above;
    - runs no tests (desk-build already ran them on the same commit);
    - re-runs the `.github/scripts/` config check on that checkout before wrangler: the
      `wrangler.toml` keys, and no lifecycle scripts or `dependencies` in `src/package.json`;
    - installs nothing under `src/`.
  - **The wrangler install step:**
    - It installs the deploy tool in a clean directory outside `src/`, from the Chief of Staff's
      pinned `.github/deploy-tools/package.json` and its lockfile. The command is
      `npm ci --ignore-scripts --prefix .github/deploy-tools`, which pins wrangler at `<x.y.z>`
      and its transitive dependencies.
    - The registry is pinned by a committed `.github/deploy-tools/.npmrc` holding
      `registry=https://registry.npmjs.org/`, so no other registry setting can redirect the
      install.
    - Whether wrangler runs fully without its packages' install scripts is C. The first deploy
      shows it. If it doesn't, the Chief of Staff names the one package whose script must run, in
      a reviewed change to that directory.
  - **The deploy step:**
    - Its `working-directory` is `src`. It calls
      `"$GITHUB_WORKSPACE/.github/deploy-tools/node_modules/.bin/wrangler" pages deploy public
      --project-name <project> --branch <branch>`. Nothing from `src/node_modules` exists or runs.
      wrangler reads `src/wrangler.toml`, whose keys are limited as above, and bundles
      `src/functions/`.
    - `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` are in that step's `env:` only, not the
      job's.
  - **Job `preview`:**
    - It runs on every push to `main` touching `src/**`, and on dispatch, in environment `preview`.
    - It deploys to `service-desk-preview` with `--branch main`.
    - `main` is the preview project's production branch (Setup C1). So each approved deploy
      updates `https://service-desk-preview.pages.dev`, a fixed URL, behind its Access application
      (F-cf-04, A).
    - The job writes the URL to its summary. There is no pull-request comment step.
  - **Job `production`:**
    - It runs on `workflow_dispatch` only, from `main`, in environment `production`, with the owner
      as required reviewer.
    - Beyond the dispatch check above, it fails unless the most recent successful `preview` job of
      desk-deploy ran on the same SHA. It reads that with `GITHUB_TOKEN` and
      `permissions: actions: read`, granted to this job only.
    - It deploys to `needs-you`, or to the O5 fallback project, with `--branch` set to that
      project's production branch as EXP-002 records.
    - It is used at M3 and never run before AC28.
  - **Job `exp-002`:** it runs on `workflow_dispatch` only, in environment `preview` (owner
    approval). It runs the same pinned wrangler's `pages project list`, read-only, with the token in
    the step's `env:` only.
  - **Possible later hardening, not relied on — option (b):** a ruleset on `main` blocking direct
    pushes to `src/**` and `.github/**`. Whether rulesets are available on this repository's plan
    is C. The owner's approval gate above is the control.
  - **What is still trusted, stated plainly:**
    - **The Reviewer's check:** the Reviewer's reading of `src/package.json`, `src/wrangler.toml`
      and `src/package-lock.json` on each pull request is a security control, not just a quality
      check. desk-build's config check backs it up for the keys and scripts it knows.
    - **wrangler's own dependencies:** wrangler and its transitive dependencies are trusted by
      pinning only, through the Chief of Staff's lockfile. Nobody reviews their code.
    - **The approval click:** the owner's click is the last gate. A mistaken approval of an
      unreviewed push would deploy it.

## Facts relied on (each with evidence)
- Pages Functions run on Workers, and their requests count against the Workers quota. Identical
  runtime limits are not documented. Workers Logs and Tail Workers are marked Workers-only. —
  evidence: library/facts/F-cf-06.md:4 (A; the compatibility matrix is one page, B). So EXP-001
  runs on a Pages project, and it may have no per-request CPU log.
- Free plan: 100,000 requests a day, and Error 1027 beyond that — evidence:
  library/F-cf-workers-05.md:8 (A).
- Free plan: 10 ms CPU per request, with network waits excluded, and Error 1102 beyond that —
  evidence: library/F-cf-workers-01.md:8 (A). Occasional overages are tolerated — evidence:
  library/F-cf-workers-08.md:9 (B).
- 50 external subrequests per invocation on Free, and redirect hops count — evidence:
  library/F-cf-workers-02.md:8 (A).
- Six connections may wait for headers at once — evidence: library/F-cf-workers-03.md:8 (A). A
  seventh queues — evidence: library/F-cf-workers-07.md:9 (B). F-cf-workers-03 lists the seventh
  as NOT filed, so it supports only the six.
- No wall-time limit for an HTTP request on Free is filed — evidence: library/F-cf-workers-03.md:8
  (it files Paid's only). EXP-001 measures it.
- A 304 sent with an Authorization header doesn't count against GitHub's primary limit, and a PAT's
  limit is 5,000 an hour — evidence: library/Q-004-facts.md:9 and :8 (A).
- Webhooks can be minutes late and aren't redelivered, so the design polls — evidence:
  library/Q-004-facts.md:6, :14, :15 (A, B).
- `?filename=` prefills the new-file name, and no content parameter is documented — evidence:
  library/F-gh-05.md:8 (B). The owner has used content-prefilled links from the phone's browser and
  the app — evidence: docs/PROJECT.md:318-320 (C, observed by the owner).

  new-file page — evidence: library/F-gh-06.md:8 (A). AC17's 6,000 cap is our own margin (E),
  checked in EXP-004.
- The commit step offers the current branch or a new one. Push rulesets may block creating a file,
  and protected branches block web edits — evidence: library/F-gh-07.md:8 (A), library/F-gh-10.md:9
  (A).
