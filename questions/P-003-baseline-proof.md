# Ruling needed: the card fix is blocked by a third fault, in its own spec, so which way should it go?

Milestone: M4

WHY: The fix for the decision cards still has not been built, and the plan you approved last time has not cleared the way. You ruled to fix two faults in the desk's machinery and then build. Both fixes worked: the Builder now has its tools, and the checks after a build now pass. But a third fault was hiding behind them, in the fix's own spec. Its tests need a record of how the desk behaves today, made before any code changes, so the new behaviour can be compared with the old. The spec asks for proof of that order from the history of saved changes on the work's branch. The pipeline cannot give that proof. Its Builder works on a plain copy of the files with no saved history, all its work comes back as one batch, and the checks run on a fresh copy that also has no history. So no Builder can pass those tests, however good its work. After you answered `rebuild`, the Builder rightly refused to fake the record. The checks then passed on an empty build, and the Reviewer failed it because nothing was built. Sent back, the Builder used up its turns without changing a file, and the session ended in an error. The pipeline will try again on its next scheduled start. After two more failed rounds and a triage, a stop card comes. If two tries in a row end in errors, a failure card comes instead. Your word can only go on one of those cards, so I am asking now which way you want to go, before either card arrives.
OPTIONS:
  A. Fix only how the old behaviour is recorded, in a new spec. The Check author records the old behaviour from the unchanged code before anything is built. The record is kept with the locked tests, which the Builder cannot change, so it is protected without needing history. The history test goes, and every other criterion carries over unchanged. Your word on the card: `criteria-wrong` on a stop card, which is not a strike. A failure card does not offer that word, so there it is `re-specify`, which counts as a strike. Cost: a new spec, a criteria card for you, freezing and new locked tests (owner-approved work), then the build again. My estimate is one to two days of the pipeline's time, not a measured figure, and it depends on its timer. One risk: the Builder has 50 turns a session, and this fix has nineteen criteria. With the record fixed it should spend its turns building, but it could still run out. Rules out: nothing; B can still follow.
  B. Change the pipeline instead. Builders would get a full copy of their branch with its history and could save in steps, and the checks would keep that history. That is a change to the operating model, which every project uses, not to this desk. Cost: a model spec, its build and reviews, then the desk's update. My unmeasured estimate is weeks, and the card fix waits throughout. Rules out: building the card fix before then.
  C. Build the card fix outside the pipeline, in a working session with full history and tools, as the desk itself was first built. Cost: one working session for the build, plus first working out how the result rejoins the pipeline's records (its rounds, the merge gate) and who reviews it, since the builder never judges its own work. Rules out: the pipeline's own record of this build.
  D. Keep going as it is: answer `rebuild` again at the card. Cost: more rounds at about the same price as the last ones. Nothing about the fault changes, so the next rounds would most likely end the same way.
  Whichever you choose, the next scheduled starts keep sending the work back to the Builder until a card comes: up to two more failed rounds, or one more error. A manual start only brings the card sooner.
RECOMMENDATION: A, because the fault is one definition in the spec, and A fixes just that inside the pipeline's normal path.
RISK CLASS: R0 (the question); A leads to R3 work (new locked tests), B to a change in the operating model, C to work outside the pipeline   REVERSIBILITY: reversible   BLAST RADIUS: A, C and D: the card fix only, with nothing on the live desk changed until it lands; B: the operating model and every project on it
DEFAULT: A (at timeout I recommend A's word in my notes on the card; only you answer the card)   TIMEOUT: 48 hours
