# Research question — Q-017

*Drafted by the Chief of Staff; checked by the Critic for gaps and neutral phrasing (D-032, D-055).*

## The question

How accurate and complete are the descriptions of Service-Desk's pull requests, compared with what each change did?

Every pull request in this setup must open with a plain-English paragraph headed "What this means for you" (shumpmaster/Personal-Org-Operating-Model, OPERATING_MODEL.md §2 "Plain English first", S-026). In v3 projects it must also carry a line naming the milestone it serves, a "Context" section of facts each with its source, a "Why" section (§3 "Why and context", S-032) and a "Tasks" section of tick boxes (§3 "Tasks and steps", S-034). shumpmaster/Service-Desk is a v3 project (src/config/projects.json). Each rule binds from the model version that introduced it, and older pull requests were not rewritten (research/Q-016-memo.md, area E3), so count a section as left out only where the rule required it on that pull request's date. CI checks the form, not the content. Nothing in this question assumes the descriptions are accurate, inaccurate, complete or incomplete.

Scope and reading:
- Service-Desk only: it is public and v3. The other repositories are outside this sample: shumpmaster/Personal-Org-Operating-Model and shumpmaster/portfolio are private and cannot be fetched, and shumpmaster/Model-Lab's contents are not to be read (research/Q-016-memo.md, "Not opened").
- The sample, fixed before any description is read: pull requests #5, #18, #31 and every 13th number after, up to #252 (20 numbers); where a number was closed without merging, take the next number that merged, skipping any number already in the sample. Add every pull request open at 2026-11-02 12:00 UTC. Say how many open ones there were; if few, the sample is mostly merged, and say so.
- Read each pull request from its own GitHub pages: the description, the diff (the `.diff` form of the pull-request URL), the commits, the checks and the reviews, plus any review records it adds to the repository (reviews/). Do not use a summary of a page in place of the page. Say for each how it was read. If the fetch tool returns only a summary of a page, say so, and mark the item "could not be determined" rather than judging from the summary.
- If the sample cannot be finished, say how many were done and which.

For each pull request in the sample, record:
- what the description says the change does;
- what the change did that the description leaves out, and anything the description says that the change does not bear out;
- any risk, failed check, review finding or irreversible step the change carries, and whether the description names it;
- whether the description was edited after later commits, or "cannot tell" where the pages do not show it;
- whether the opening paragraph alone gives a correct account of the change;
- whether the description says how the change relates to other pull requests or to the milestone it names, and whether that is right;
- for each item, "checked" or "could not be determined".

Then give counts of each kind of omission and mismatch, the rule used to judge each kind, and two or three worked examples with their pull-request numbers, so another reader could repeat the judgement.

## The decision it serves

Whether a change can be described to the owner from what its author wrote, would need another source, or would need checking first; and what a description of a change must hold, or say is unknown, to be reliable.

## What each answer would change

Descriptions found mostly accurate and complete make the author's text a candidate source; frequent omissions or mismatches rule it out as a sole source, or set what a check must look for; the kinds of error found become design traps and test cases.
