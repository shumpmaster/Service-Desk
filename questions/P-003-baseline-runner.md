# Ruling needed: the card fix's new spec needs someone to run today's code and keep the record, and no one in the pipeline may do that, so which way now?

Milestone: M4

WHY: You chose to fix only how the record of today's behaviour is made, in a new spec. The Definer wrote it, and the Critic has failed it twice. The reason is the same both times, and another rewrite cannot remove it. Someone other than the Builder has to run the old code and keep what it gives, beside the locked tests. The Check author may not see the code. The Reviewer may see it, but may not save anything. No other role has that job. The pipeline also has no step where the Builder stops after writing the run's helper, someone else makes the record, and then the Builder builds: after a Builder session the checks run at once, and the Reviewer comes only after they pass. The Critic found a second gap too. The Builder writes the helper the run uses, so a helper that only pretends to call the desk's code would pass every check. And the last two Builder sessions ran out of their 50 turns on this same amount of work. The Definer is now on its third and last round. If that fails too, the work goes to Triage and a stop card comes to you. Your word can only go on that card, so I am asking now which way to go before it arrives.
OPTIONS:
  A. Let the check run make the comparison itself. The checks already run in a sealed copy after each Builder session, and the Builder cannot touch them. They would run the Builder's helper twice, once on the unchanged code from the main branch and once on the built code, and compare the two. No record is stored, no history is needed and no role needs a new job. A check would also confirm that the helper really calls the desk's code. Cost: a change to the check run, which is the operating model's tooling that every project shares (R3), then a revised spec, a criteria card for you and new locked tests. My unmeasured estimate is several days to two weeks, and the card fix waits throughout. Rules out: nothing; C can still follow.
  B. Give the Reviewer the job: a duty to run the old code, a place where its record is saved, and a new pipeline step that pauses the Builder for it. Cost: changes to the roles, the file ownership and the routing, all R3, in the operating model. It is larger than A, my unmeasured estimate is weeks, and it leaves the Critic's "pretend helper" gap to a check like A's anyway. Rules out: nothing.
  C. Build the card fix outside the pipeline, in a working session with full history and tools, as the desk itself was first built (P-001). There the old code can be run and recorded before any change, with the history to prove it, and there is no 50-turn limit. A separate reviewer still judges the build, and it lands through the normal merge with its reviews recorded. Cost: one working session for the build (my estimate, not measured), plus closing the pipeline's own item for it. Rules out: the pipeline's own record of this build. A can still be done for later work.
  D. Let the loop go on: the Definer's third round, then Triage, then a stop card. Nothing about the gap changes, so most likely the third round fails like the first two. Cost: about two more paid sessions, then the same question on a card. Rules out: nothing.
RECOMMENDATION: C, because the gap is in the pipeline, not in the fix. C builds a small fix (about 90 to 130 lines) now, while A, which is worth doing for every project, need not hold it up.
RISK CLASS: R0 (the question); A and B lead to R3 changes in the operating model, C to a build outside the pipeline   REVERSIBILITY: reversible   BLAST RADIUS: C and D: the card fix only, with nothing on the live desk changed until it lands; A and B: the operating model and every project on it
