## Acceptance criteria (scenarios; owner-approved at the scenario card, which this draft has not yet reached)

**Words used throughout.** A **connected project** is a repository on the desk's list, with the portfolio repository added (plan §8, "All projects", line 200). **The records** are, for each connected project, GitHub's objects that the desk's read key can read (branches, commits, pull requests, reviews, workflow runs, commit statuses, deployments and their reviews) and the operating model's files on its main branch (queue/, decisions/, questions/, research/, specs/, the dispatch log, status files, docs/projects/ and docs/PROJECT.md). **The waiting list** is the one list of steps waiting on the owner (J4). A step is **due** at the moment the desk's rules first put it on the waiting list, which for a decision card is when the S-009 rule shows it (plan §8, line 211). **The record writer** of an event is the party that wrote the record a field comes from. It is one of the plan's three (plan line 40), or `not recorded`: `GitHub` for an object GitHub makes (a pull request, review, merge, workflow run, deployment or its review); `the Orchestrator` for a file or commit the Orchestrator writes; `agent <role>` for a file or commit that carries an agent session's `Agent-Session:` trailer or lies in that agent's write lane on its build branch; and `not recorded` for anything else. That includes a commit the owner makes: no record beyond its settable author fields says who wrote it (library/facts/F-git-dates-settable-01.md:4). Its `who` still shows the owner's login from the commit or pull request (J1). **The read interval** is how often the open timeline reads each connected project: every 2 minutes while the timeline is open and visible, the upper end of the desk's page-driven poll (docs/PROJECT.md:286-287, :394). Nothing is read while it is closed.

**A reading of src/** is a Reviewer's return naming the desk's read path, the card-making code's entry points, the sender's entry points, the generated copies and the path of the desk's server code. It is the Builder's first step in Build, and it is not needed to freeze or check this spec: the criteria and join sheets say what is handed over, not where the code lies. If the reading shows that a join's form cannot be met where the plan and docs/PROJECT.md place it, that is a stop and a revision of this spec (stop rule), not a build decision.

### The event record (D1; M6, M7)
- **AC1** [trace: V9 → AC1] — When the timeline shows an event, then its kind, state, who, time, project and piece of work each come from a record, and opening the event names that record (a GitHub link, or a path at a commit). A field that no record holds shows the words "not recorded"; the desk never fills it with a guess, a default or the value of a neighbouring event.
- **AC2** [trace: V9 → AC2] — When a step is not stated by any record but other records support it (for example a branch seen only through its merge commit), then it is shown only with the mark "reconstructed", and opening it lists the records that support it. When no record supports a step, it is not shown at all.
- **AC3** [trace: V9 → AC3] — When an event is shown, then it says who wrote its record (`GitHub`, `the Orchestrator`, `agent <role>` or `not recorded`), beside who acted. A commit the owner makes shows the owner as who acted and `not recorded` as its writer. An agent's own record of its work (for example "done" in its return) is shown as the agent's, never in GitHub's or the Orchestrator's style, so the owner can tell a self-report from the platform's record (plan line 40). There is no fourth writer, by the owner's answer "Keep the three (Recommended)" (decisions/P-005/stop-4.md, answer 4).
- **AC4** [trace: V9 → AC4] — When an event's kind is one of the key's eleven (branch, commit, pull request, check, review, merge, deploy on the first row; gate, decision, research, stop on the second), then it is drawn with that kind's own shape. A recorded event outside the eleven (for example a tag) is drawn with the `other` shape and its record's own name for it. Colour never marks a kind (plan line 153). The key, with each shape and its name, opens from the timeline in one tap.
- **AC5** [trace: V9 → AC5] — When an event's state is shown, then it shows its colour and its word side by side, from the closed set of J2. A record whose state is outside J2's mapping shows `other` with the record's own word, and a record that holds no state shows `unknown`. Every colour carries one meaning in every view.
- **AC6** [trace: V9 → AC6] — When a record gives both when a thing happened and when it was recorded, then the event shows when it happened. When it gives only when it was recorded, the time is shown marked "recorded at". When a time's offset is unknown, it is shown as such and never moved into the owner's time zone as if known (J1).
- **AC7** [trace: V9 → AC7] — When an event's record is one GitHub no longer keeps (for example a workflow run past its repository's retention setting), then the event shows "no longer kept", never as missing work, a failure or "not recorded". Once a lasting copy of that result exists (J8), the event is shown from the copy, marked "from a kept copy". Until the owner approves the records change that writes copies, none exist and this criterion's first sentence applies alone (plan line 182).
- **AC8** [trace: V9 → AC8] — When a step's record says it waits on the owner, then it is never shown in the failure colour, with the word "failed", or as "stalled" or "late". When an agent step has started (its dispatch-log entry) and has no ending record and no later record for the same piece of work for more than 2 hours, then it shows `stalled` (plan line 39). At 2 hours or less it shows `running`. No record sets this figure; the owner set it, "2 hours (Recommended)" (decisions/P-005/stop-4.md, answer 2).

### What needs the owner (D3; M8)
*How this spec reads M8, and where it is narrower than M8's words. M8 is done when, among other things, "each single thing that needs them reaches their phone" (plan line 74). These criteria read that as follows: every step on the waiting list (J4), of every one of its five kinds, is sent to the phone by name (AC23), and a notice opens the step (AC24). This is narrower than M8's words in four ways, chosen on purpose and not hidden: (1) no number of minutes is promised, because no route the plan names can promise one (AC23); (2) a step that is answered before any run of the route reads it is not sent, and AC41 counts it as a miss unless an open timeline showed it in time. Every other waiting step is sent, including one whose record shows up after its due time; at worst a notice is sent twice, and AC41 counts that too (J5); (3) a notice may arrive at the normal level and not interrupt, if Time Sensitive marking is not available to a Home Screen web app (AC25); (4) the number of notices is not capped, since no daily limit was found in the sources read (plan line 171), and steps are grouped only by name within one run. What the spec can test is that the route sent the notice; that the phone shows it is Apple's delivery, which the spec does not test. Whether this reading is enough for M8 is the owner's to rule at the scenario card (open question 2); if not, it is a revision of this spec.*

- **AC19** [trace: V7 → AC19] — When the owner looks at a waiting step, then it is shown in its context: the events of the same piece of work just before and after it (its branch, pull request, commits, checks and earlier steps) are shown with it, or one tap away in place, without leaving the timeline.
- **AC20** [trace: V8 → AC20] — When the timeline and any core screen it has not yet replaced are given the same records and moment, then both show the same waiting steps, with the same states and the same count, because both take the one waiting list (J4; plan line 44). That change to the screens is part of this spec and lies in its areas touched (src/public/**, src/lib/**). A test hands both the same sample records, holding at least one deploy awaiting the owner's review, and one moment, and compares them.
- **AC21** [trace: V7 → AC21] — When the owner chooses to answer, approve or merge a waiting step, then one tap opens GitHub's own page for that action (J6): an answer opens GitHub's new-file page with the answer filled in, as the desk does today; a deploy approval opens the run's page where GitHub offers "Review deployments"; a merge or a review opens the pull request's page. An action begun from the timeline but not finished on GitHub leaves the step waiting.
- **AC23** [trace: V8 → AC23] — When a step is on the waiting list, then the first run of the alert route (J5) that reads the step's project successfully and finds the step waiting sends the owner's phone a notice naming it, whichever route the Design chooses for alerts from every project (plan line 180). This holds whatever the step's due time: a step whose record shows up after its due time (for example a commit whose time its writer set earlier, J1) is sent by the first run that reads it. A run that cannot read the step's project does not count for it, and the next run that reads that project sends it (J5). Each step is named in its own notice, or by name in a notice that groups steps found in the same run; none is only counted. A step is notified once; it is notified again only when its entry's `changed_at` moves, or when it leaves the waiting list and comes back (J4; library/patterns/P-repeat-on-change-01.md:4). A step that is answered before any run reads it is not notified. Every waiting step a run reads is notified; there is no exception that leaves one out. There are two exceptions to "once", both repeats on J5's paths, and AC41 lists each: (a) when the route finds no earlier log of what it notified for the project (its first run, or its logs past their keeping or missing), it sends every waiting step of that project, so a step notified before may be sent again; (b) a step whose notice was sent by a run that stopped before logging the project (J5) is sent again by the next run. The Design states, for the route it chooses, how late its notices can be by its facts, and the route and V8's 5-minute target go to the owner at the Design gate with that delay (plan lines 136, 180). Build starts no alert work until the owner rules on them (plan line 180).

### After graduation: running, monitoring, feedback and value review
*The owner owns these after the Launch gate, so they are built in Build like the rest (OPERATING_MODEL.md §3, "Graduation and re-entry", outside this pack). The weekly checks, the reports of misses and the review card are the Chief of Staff's to run (plan §4, line 106); this section covers what the product and its handover must give so that they can be run.*
- **AC39** [trace: V8 → AC39] — Running: when the timeline is live, then it needs no setting, schedule or step from the owner beyond the two read permissions added once (AC38) and the weekly commit of the device log (AC26), and no step from any agent beyond the alert route and outside check the owner approved in Design.
- **AC40** [trace: V7 → AC40] — Monitoring V7: when anyone runs the wait count, handing it a window's start and its end, then from the records on GitHub and the main branches dated no later than the window's end it gives every wait that started in that window, with its kind, project, start record and time, end record and time (or "still open" and its wait so far, measured to the window's end), and whether the owner or the Chief of Staff as proxy acted, and the median of the owner's waits and, apart, the proxy's. The window's end is the count's "now": it is handed in, as J4's list is handed its moment, and the count reads no clock of its own and nothing stored on a device. A record dated after the window's end is not read, so a wait that ended after it is "still open". It uses this rule, which is V7's rule as the plan states it (plan line 135) and which E1 is registered to measure by (plan line 158); it is stated here in full, so this criterion rests on no section of E1's registration:
  - A decision card waits from when P-003's rule (spec S-009) first shows it, found by rerunning that rule on the dispatch log and notes as they stood on the main branch, to the commit on the main branch that adds its answer record. With two dispatch-log entries, the earliest counts.
  - An owner question waits from its file's pull request's `created_at` to the commit on the main branch that adds its answer record.
  - A gate waits from the commit on the main branch that adds its case to the commit that adds its ruling record.
  - A pull request that needs the owner waits from `ready_for_review` (or `created_at` if it was never a draft) to `merged_at`, or to `closed_at` if the owner closed it unmerged.
  - A deploy waits from its review request to the review's approval or rejection.
  - A commit's time is its committer time with its offset. A time with an unknown offset is listed but left out of the medians, with a count.
  - A wait is the proxy's when its ending record carries a `Proxy:` line; otherwise it is the owner's, including a proxy action whose ending record has no such line. This rule replaces E1's wording (J11).

- **J5 —** the waiting list → the alert route → the owner's phone (D3). What is handed, per connected project: a run is **successful for a project** when it read that project's records and sent every notice that project called for; a run can be successful for some projects and not others, and its overall conclusion on GitHub does not decide it. The route chooses what to send by what it has already notified, not by `due_at`. For each project, a run takes the **notified set** from the latest earlier run that was successful for that project: the pairs (`id`, `changed_at`) that run logged. It hands on each of that project's entries on the waiting list whose (`id`, `changed_at`) pair is not in that set, with `id`, `project`, `title` and `open_key`. So a step is sent by the first run that reads its project and finds it waiting, whenever its due time was, including a step whose record shows up after its due time; a project a run could not read is sent for by the next run that reads it; and each entry is sent once, and again only when `changed_at` moves or it leaves the list and comes back (AC23).
