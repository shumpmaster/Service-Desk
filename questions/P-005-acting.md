# Ruling needed: when you answer, approve or merge from the timeline, should the action finish on GitHub's own page, or inside the timeline with a new key that can write as you?

Milestone: Discovery-7, M8

WHY: You chose to act from the timeline (your answer 4). The research shows that finishing an action inside the timeline needs a new key that can write to your repositories as you; today the desk can only read. Your plan says a finding like this comes back to you before any more work is done, so the decision is yours. The answer sets the plan's scope and limits, and rewords the milestone where you act (M8) to match.
How to answer: one letter.
If you don't answer: nothing that already works stops, but all work on the timeline waits: its next plan draft, the experiments question and the project request.

Three things to know first:
- The key. A key that acts would be held by the desk's own server code on your Cloudflare account, never by an agent, behind the sign-in that already admits only your email address. Writing answer files would need GitHub's "Contents" write permission, which also allows merging, and GitHub's tables also list "Workflows" write for it without saying whether both are needed; "Workflows" write would let the key change the files that tell GitHub what to run. Approving deploys alone needs only "Deployments" write, a much smaller grant. The desk's earlier card on this choice (1 October) said a key that writes makes the project's trust level T2, which means a security review and more checking of its changes.
- Reading. The timeline shows checks. The desk's read-only key sees CI through workflow runs and commit statuses but cannot read GitHub's check results; a GitHub App can, and one App connection can also carry events from every project for alerts. So the plan may well need a GitHub App for reading anyway, whatever you choose here; if it does, B and C could give that App the right to write rather than add a second one, though a write right on the App that reads everything widens what its key can do if it leaks; the research's own pattern suggests a separate App for acting. Whether to read through an App comes to you separately.
- Alerts. GitHub's phone app alerts you to deploy approvals and review requests, but not to the desk's own records (cards, questions, gates); those reach your phone through the desk's own sender under every option.

OPTIONS:
  A. Finish on GitHub's page, with no key that writes — each button on the timeline opens the exact GitHub page for that step, and you finish it there with one tap: an answer opens GitHub's new-file page with the answer filled in, as the desk's answer buttons do today; a merge opens the pull request at its merge button; a deploy approval opens the run's approval page. Every action is your own GitHub action, as today. Gain: no key that can write, the trust level stays at T1, and no new spend or data leaving your repositories is needed for acting. Cost: one extra tap per action, made on a GitHub page rather than inside the timeline. This is nearer the "only see, then go" choice you did not pick in answer 4: you use it today for answers, but for merges and approvals it may not be what you meant. GitHub does not document the part of the link that fills in an answer's text; you have used it from your phone's browser and the GitHub app, and if it stops working the timeline shows the answer to copy beside the link. Because the action happens on GitHub, the timeline learns it is done only when its feed catches up, so a finished step may show as waiting for a few minutes. In practice A is the stop rule's "acting drops out" outcome. It rules out finishing any action without leaving the timeline, until you rule for B or C later as its own change.
  B. Finish everything inside the timeline, through a GitHub App acting as you — a GitHub App you create and install yourself acts with a key that lasts 8 hours and is tied to you, with "Deployments", "Contents" and "Pull requests" write, and possibly "Workflows" write. GitHub shows each action as yours with the App's badge, and its security log records that the App made it, so the timeline can still tell your own actions from its own (the badge and the log detail rest on one GitHub page). Gain: the fullest reading of your answers: you chose to act from the view (answer 4), want the timeline to replace all the core screens (answer 6), and expect to spend "a considerable amount of time" in it (answer 8). Cost: the App's master key never expires and opens every repository the App is installed on, and with these permissions it can merge and change files there, so the key is the desk's most valuable secret. T2, with a security review. You rule that an action made this way counts as your own, a production deploy approved this way included. GitHub does not document that a commit made this way starts the Orchestrator, so a live test comes first, before anything relies on it. The research gives no cost figure; your plan's $0 ceiling holds unless you approve more. It rules out the desk holding no key that can write.
  C. Approve deploys inside the timeline; answer and merge on GitHub's page — the same GitHub App as B, but with "Deployments" write only. Deploy approvals finish in the timeline; answers and merges finish on GitHub's page as in A. Gain: the step that most often needs you right away can be done in place, with the smallest write grant; the key cannot merge or change files. Cost: the App and its never-expiring key still exist; T2, on the earlier card's reading, with a review of the deploy path; you rule that a deploy approved this way counts as your own approval; answers and merges keep A's extra tap. Today only Service-Desk has deploys, so this covers one project until another adds them. It rules out answering and merging inside the timeline.
RECOMMENDATION: A, with low-to-moderate confidence — it needs no key that can write, keeps the project at T1, and leaves B and C open as their own change later. It fits answers well, since that is how you answer today; it fits merges and approvals less well. What would change it: if "act from the view" meant that approvals must finish in the timeline, choose C; if everything must, choose B. If you later rule that the timeline reads through a GitHub App, B and C need no extra App, though they widen that App's key.
