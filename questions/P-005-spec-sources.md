# Ruling needed: can a published specification's own text be the source for what that specification requires?

Milestone: Discovery-5

WHY: The timeline's research on how events are classified (Q-026) stopped at its third source check partly on a gap in your source rule: it says how a vendor's documentation counts for its own product, but not how a published specification counts for what it requires, for example OpenTelemetry's "An event MUST have an event name that uniquely identifies the event structure" (its data model says SHOULD). One finding is held on this, and part of one already filed rests on it. Discovery's research milestone (Discovery-5) is not reached while it waits, and closing the item would leave its six filed entries off the main branch.
How to answer: one letter.
If you don't answer: nothing moves and nothing breaks; the item's stop card keeps waiting.

The held finding, `F-otel-event-name-01`, claims that an OpenTelemetry event's name identifies its structure. Two pages of the specification say so at different strengths: the events page says the name "MUST" uniquely identify the event structure, and the log data model says it "SHOULD". The already-filed entry, `F-enum-escape-values-01`, is on how event schemas name their "unknown" and "other" values, in two parts: OCSF's convention (an open schema project: "by convention every enum has 0 Unknown and 99 Other"), from two OCSF pages; and what Google's API guidelines and protobuf style guide require, from two Google pages. Each part rests on one publisher's two pages.

OPTIONS:
  A. Yes, one quoted passage is enough — a specification's text is the source for what that specification requires, and is never evidence of what others do in practice. One line is added to the source rule the checker reads (governance/standards/sources.md), a governance change you approve; once it is merged, the card's `re-specify` sends Q-026 back to the Researcher. The held finding can be filed on the MUST, with the data model's SHOULD noted, and the filed entry stands. Cost: the rule widens by one line. It rules out using a specification to show what practice does.
  B. Yes, but only with two of its pages, labelled "same publisher", as for a vendor's own documentation — one line is added to the source rule, a governance change you approve; once it is merged, `re-specify` sends Q-026 back. The held finding can be filed only as what both pages support, the weaker SHOULD, and the filed entry stands. Cost: a requirement stated on only one page cannot be filed. It rules out single-passage requirements.
  C. No: a specification's text needs two independent publishers for a load-bearing claim not about a vendor's own product — no rule changes; `re-specify` sends Q-026 back at once. The OCSF part of the filed entry is withdrawn, or re-filed as single-source and not load-bearing, by a superseding entry, and the Google part too unless the checker counts Google's guides as its documentation of its own product. Cost: Q-026 needs new sources for every load-bearing claim based on a specification; one with a single source can still be filed as single-source and not load-bearing, so it cannot carry a plan decision. It rules out citing a specification as the sole support for a load-bearing claim about its own requirements.
RECOMMENDATION: A — a specification is the authority on its own requirements, as a vendor's documentation is on its own product.
