## Acceptance criteria (scenarios; owner-approved at the scenario card, which this draft has not yet reached)

**Words used throughout.** A **connected project** is a repository on the desk's list, with the portfolio repository added (plan §8, "All projects", line 200). **The records** are, for each connected project, GitHub's objects that the desk's read key can read (branches, commits, pull requests, reviews, workflow runs, commit statuses, deployments and their reviews) and the operating model's files on its main branch (queue/, decisions/, questions/, research/, specs/, the dispatch log, status files, docs/projects/ and docs/PROJECT.md). **The waiting list** is the one list of steps waiting on the owner (J4). A step is **due** at the moment the desk's rules first put it on the waiting list, which for a decision card is when the S-009 rule shows it (plan §8, line 211). **The record writer** of an event is the party that wrote the record a field comes from. It is one of the plan's three (plan line 40), or `not recorded`: `GitHub` for an object GitHub makes (a pull request, review, merge, workflow run, deployment or its review); `the Orchestrator` for a file or commit the Orchestrator writes; `agent <role>` for a file or commit that carries an agent session's `Agent-Session:` trailer or lies in that agent's write lane on its build branch; and `not recorded` for anything else. That includes a commit the owner makes: no record beyond its settable author fields says who wrote it (library/facts/F-git-dates-settable-01.md:4). Its `who` still shows the owner's login from the commit or pull request (J1). **The read interval** is how often the open timeline reads each connected project: every 2 minutes while the timeline is open and visible, the upper end of the desk's page-driven poll (docs/PROJECT.md:286-287, :394). Nothing is read while it is closed.

**A reading of src/** is a Reviewer's return naming the desk's read path, the card-making code's entry points, the sender's entry points, the generated copies and the path of the desk's server code. It is the Builder's first step in Build, and it is not needed to freeze or check this spec: the criteria and join sheets say what is handed over, not where the code lies. If the reading shows that a join's form cannot be met where the plan and docs/PROJECT.md place it, that is a stop and a revision of this spec (stop rule), not a build decision.

### The event record (D1; M6, M7)
- **AC1** [trace: V9 → AC1] — When the timeline shows an event, then its kind, state, who, time, project and piece of work each come from a record, and opening the event names that record (a GitHub link, or a path at a commit). A field that no record holds shows the words "not recorded"; the desk never fills it with a guess, a default or the value of a neighbouring event.
- **AC2** [trace: V9 → AC2] — When a step is not stated by any record but other records support it (for example a branch seen only through its merge commit), then it is shown only with the mark "reconstructed", and opening it lists the records that support it. When no record supports a step, it is not shown at all.
- **AC3** [trace: V9 → AC3] — When an event is shown, then it says who wrote its record (`GitHub`, `the Orchestrator`, `agent <role>` or `not recorded`), beside who acted. A commit the owner makes shows the owner as who acted and `not recorded` as its writer. An agent's own record of its work (for example "done" in its return) is shown as the agent's, never in GitHub's or the Orchestrator's style, so the owner can tell a self-report from the platform's record (plan line 40). There is no fourth writer, by the owner's answer "Keep the three (Recommended)" (decisions/P-005/stop-4.md, answer 4).
- **AC4** [trace: V9 → AC4] — When an event's kind is one of the key's eleven (branch, commit, pull request, check, review, merge, deploy on the first row; gate, decision, research, stop on the second), then it is drawn with that kind's own shape. A recorded event outside the eleven (for example a tag) is drawn with the `other` shape and its record's own name for it. Colour never marks a kind (plan line 153). The key, with each shape and its name, opens from the timeline in one tap.
- **AC5** [trace: V9 → AC5] — When an event's state is shown, then it shows its colour and its word side by side, from the closed set of J2. A record whose state is outside J2's mapping shows `other` with the record's own word, and a record that holds no state shows `unknown`. Every colour carries one meaning in every view.
- **AC6** [trace: V9 → AC6] — When a record gives both when a thing happened and when it was recorded, then the event shows when it happened. When it gives only when it was recorded, the time is shown marked "recorded at". When a time's offset is unknown, it is shown as such and never moved into the owner's time zone as if known (J1).
- **AC7** [trace: V9 → AC7] — When an event's record is one GitHub no longer keeps (for example a workflow run past its repository's retention setting), then the event shows "no longer kept", never as missing work, a failure or "not recorded". Once a lasting copy of that result exists (J8), the event is shown from the copy, marked "from a kept copy". Until the owner approves the records change that writes copies, none exist and this criterion's first sentence applies alone (plan line 182).
- **AC8** [trace: V9 → AC8] — When a step's record says it waits on the owner, then it is never shown in the failure colour, with the word "failed", or as "stalled" or "late". When an agent step has started (its dispatch-log entry) and has no ending record and no later record for the same piece of work for more than 2 hours, then it shows `stalled` (plan line 39). At 2 hours or less it shows `running`. No record sets this figure; the owner set it, "2 hours (Recommended)" (decisions/P-005/stop-4.md, answer 2).

- **AC10** [trace: V8 → AC10] — When the owner puts one or more projects in focus, then their events are shown in full and every other project condenses to one line giving its name, its newest event's time and how many steps it has waiting on the owner. Each link opens the record's own page on GitHub or its file. A link to a record GitHub no longer keeps says "no longer kept" instead of opening a page that is gone (AC7).
- **AC14** [trace: V8 → AC14] — When the timeline is shown, then it shows its as-of time (when it last read each project successfully) and, apart from it, the age of the newest record it holds for each project, or "age unknown". "No data" (a project not yet read successfully since the timeline opened) and "late" (a project not read successfully for more than 4 minutes, twice the read interval, while the timeline is open and visible; the owner's answer "4 minutes (Recommended)", decisions/P-005/stop-4.md, answer 3) each have their own state, word and colour, and neither is drawn as "nothing waiting" (plan line 43; library/facts/F-asof-age-label-01.md:4).
- **AC15** [trace: V8 → AC15] — When the outside check (J7) finds that the timeline's feed has stopped, then the timeline shows "Stopped since <time>: what waits on you may not be shown" above the waiting list. - **AC16** [trace: V8 → AC16] — When a read of one project fails, then that project's events stay shown as last read, marked with their as-of time, its line says it cannot be read just now, and its waiting steps stay on the waiting list as last read with that mark. A failed read never empties the waiting list to "Nothing waits on you".
- **AC17** [trace: V8 → AC17] — When the timeline is shown on a screen 360 CSS pixels wide and on one 414 CSS pixels wide, the widths the owner set, "360 and 414 (Recommended)" (decisions/questions/P-005-s011-widths.md), then it is one line of events read top to bottom with no sideways scrolling, every control is at least 44 by 44 CSS pixels (WCAG 2.5.5's figure, which is above 2.5.8's 24 by 24 CSS pixels; Apple's default control size is 44 by 44 points, a different unit, and is not the measure here), text has at least 4.5:1 contrast and each shape and state colour at least 3:1 against its background, and colour is never the only sign of anything (library/facts/F-wcag22-01.md:4; library/facts/F-platform-targets-contrast-01.md:4). On a computer it is the same view, wider.

### What needs the owner (D3; M8)
*How this spec reads M8, and where it is narrower than M8's words. M8 is done when, among other things, "each single thing that needs them reaches their phone" (plan line 74). These criteria read that as follows: every step on the waiting list (J4), of every one of its five kinds, is sent to the phone by name (AC23), and a notice opens the step (AC24). This is narrower than M8's words in four ways, chosen on purpose and not hidden: (1) no number of minutes is promised, because no route the plan names can promise one (AC23); (2) a step that is answered before any run of the route reads it is not sent, and AC41 counts it as a miss unless an open timeline showed it in time. Every other waiting step is sent, including one whose record shows up after its due time; at worst a notice is sent twice, and AC41 counts that too (J5); (3) a notice may arrive at the normal level and not interrupt, if Time Sensitive marking is not available to a Home Screen web app (AC25); (4) the number of notices is not capped, since no daily limit was found in the sources read (plan line 171), and steps are grouped only by name within one run. What the spec can test is that the route sent the notice; that the phone shows it is Apple's delivery, which the spec does not test. The owner accepted this reading whole, "Accept the reading (Recommended)", and confirmed that it covers the normal level and the absence of a cap, "Yes, all of it (Recommended)" (decisions/questions/P-005-s011-m8-reading.md); it is reversible, and a later spec may tighten M8 if a route that can keep a time is found. One detail of repeats, below the reading, is new in this spec: a step that leaves the waiting list and comes back between two runs of the route, with its `changed_at` unchanged, is not sent a second time, since no run saw it gone; it was sent by name when first found (AC23, J5).*
- **AC18** [trace: V7 → AC18] — When steps wait on the owner, then they lead the timeline, above every other event, across all projects, in the waiting list's order (J4). Each shows its kind, project, what is asked and how long it has waited.
- **AC19** [trace: V7 → AC19] — When the owner looks at a waiting step, then it is shown in its context: the events of the same piece of work just before and after it (its branch, pull request, commits, checks and earlier steps) are shown with it, or one tap away in place, without leaving the timeline.
- **AC20** [trace: V8 → AC20] — When the timeline and any core screen it has not yet replaced are given the same records and moment, then both show the same waiting steps, with the same states and the same count, because both take the one waiting list (J4; plan line 44). This includes deploys awaiting the owner's review, which J4 adds to the list: each unreplaced core screen that lists waiting steps starts listing those deploys too, each opening the run's page (J6), drawn in the form the Design sets and Design-5 checks on the mockups. That change to the screens is part of this spec and lies in its areas touched (src/public/**, src/lib/**). A test hands both the same sample records, holding at least one deploy awaiting the owner's review, and one moment, and compares them.
- **AC21** [trace: V7 → AC21] — When the owner chooses to answer, approve or merge a waiting step, then one tap opens GitHub's own page for that action (J6): an answer opens GitHub's new-file page with the answer filled in, as the desk does today; a deploy approval opens the run's page where GitHub offers "Review deployments"; a merge or a review opens the pull request's page. The owner finishes there, as their own GitHub action. The desk writes nothing to any repository and holds no key that can write; a production deploy stays the owner's own approval on GitHub (plan lines 22, 42).
- **AC22** [trace: V7 → AC22] — When the record of the owner's action reaches GitHub (the answer committed, the deploy approved, the pull request merged), then on the timeline's next read the step leaves the waiting list and shows as done, by the owner, at the record's time. An action begun from the timeline but not finished on GitHub leaves the step waiting.
- **AC23** [trace: V8 → AC23] — When a step is on the waiting list, then the first run of the alert route (J5) that reads the step's project successfully and finds the step waiting sends the owner's phone a notice naming it, whichever route the Design chooses for alerts from every project (plan line 180). This holds whatever the step's due time: a step whose record shows up after its due time (for example a commit whose time its writer set earlier, J1) is sent by the first run that reads it. A run that cannot read the step's project does not count for it, and the next run that reads that project sends it (J5). Each step is named in its own notice, or by name in a notice that groups steps found in the same run; none is only counted. A step is notified once; it is notified again only when its entry's `changed_at` moves, or when it leaves the waiting list and comes back (J4; library/patterns/P-repeat-on-change-01.md:4). A return counts as one only if a run of the route that read the step's project successfully found the step gone from the waiting list; a step that leaves and comes back between two such runs, with its `changed_at` unchanged, is not sent again, and the notice already sent still names it and opens it (AC24; J5). A step that is answered before any run reads it is not notified. Every waiting step a run reads has been notified, by that run or an earlier one; there is no exception that leaves one never notified. There are three exceptions to "once", all repeats on J5's paths, and AC41 lists each: (a) when the route finds no earlier log of what it notified for the project (its first run, or its logs past their keeping or missing), it sends every waiting step of that project, so a step notified before may be sent again; (b) a step whose notice was sent by a run that stopped before logging the project (J5) is sent again by the next run; (c) runs of the route do not overlap for a project (J5), but if two do, the later one may take an older notified set and send a step again. A step sent again because a run saw it gone and a later run finds it back is not an exception: that resend is this criterion's rule. AC41 lists it apart as cause (d), so it is never taken for a fault of the route. This criterion sets no number of minutes, because no route the plan names can promise one: a scheduled run comes at most every 5 minutes and can be delayed or dropped (library/facts/F-gh-12.md:4; library/facts/F-gh-12b.md:4), and webhooks can take minutes and are not redelivered automatically (plan line 136). The 5 minutes are V8's: a step neither sent to the phone nor shown on an open timeline within 5 minutes of its due time is a miss, counted by AC41, not a failure of this criterion. The Design states, for the route it chooses, how late its notices can be by its facts, and the route and V8's 5-minute target go to the owner at the Design gate with that delay (plan lines 136, 180). Build starts no alert work until the owner rules on them (plan line 180).
- **AC24** [trace: V8 → AC24] — When the owner opens a notice, then the timeline opens at that step in its context (AC19). If the step is no longer waiting, the timeline says so and shows it as done, or as no longer on the list, with its record.
- **AC25** [trace: V8 → AC25] — When the owner's phone allows a Home Screen web app's notice to be marked Time Sensitive (tested in Design on the owner's phone, plan line 183), then notices for waiting steps are marked Time Sensitive; otherwise they arrive at the normal level and nothing else changes (library/facts/F-ios-interruption-levels-01.md:4). Which branch is live follows the result of the Design test, recorded in Design; until that test has run, the live branch is the normal level. A locked check covers both branches: it hands the sender each result ("allowed" and "not allowed") and checks the notice's level for each. It does not test what the phone shows, which is Apple's delivery.
- **AC26** [trace: V8 → AC26] — When the timeline is open and visible on a device, then it keeps on that device a log of when it was open and visible, when it first showed each waiting step, and when it showed and cleared AC15's "Stopped since" banner or AC16's "cannot be read just now" mark (J9); once a week it offers a prefilled link that commits that week's log to the owner's private portfolio repository under value/P-005/, the place the owner chose, "value/P-005/ (Recommended)" (decisions/P-005/stop-4.md, answer 5), as V1's log was (docs/PROJECT.md:205-209; J9). Nothing of it is kept on Cloudflare.

### After graduation: running, monitoring, feedback and value review
*The owner owns these after the Launch gate, so they are built in Build like the rest (OPERATING_MODEL.md §3, "Graduation and re-entry", outside this pack). The weekly checks, the reports of misses and the review card are the Chief of Staff's to run (plan §4, line 106); this section covers what the product and its handover must give so that they can be run.*
- **AC39** [trace: V8 → AC39] — Running: when the timeline is live, then it needs no setting, schedule or step from the owner beyond the two read permissions added once (AC38) and the weekly commit of the device log (AC26), and no step from any agent beyond the alert route and outside check the owner approved in Design.
- **AC40** [trace: V7 → AC40] — Monitoring V7: when anyone runs the wait count, handing it a window's start and its end, then from the records on GitHub and the main branches dated no later than the window's end it gives every wait that started in that window, with its kind, project, waiting-list `id` (J4's id rule for its kind, built from the wait's own records), start record and time, end record and time (or "still open" and its wait so far, measured to the window's end), and whether the owner or the Chief of Staff as proxy acted, and the median of the owner's waits and, apart, the proxy's. The window's end is the count's "now": it is handed in, as J4's list is handed its moment, and the count reads no clock of its own and nothing stored on a device. A record dated after the window's end is not read, so a wait that ended after it is "still open". It uses this rule, which is V7's rule as the plan states it (plan line 135) and which E1 is registered to measure by (plan line 158); it is stated here in full, so this criterion rests on no section of E1's registration:
  - **A main-line commit** holding a record is the first commit on the main branch's first-parent line whose tree holds that record; its time is its committer time.
  - **A decision card** is a card of kind `dor-fail`, `stop` or `failure`. It waits from when P-003's rule (spec S-009) first shows it to the main-line commit holding its answer record. That rule shows a card at the earlier of two moments: its notes with a recommended word reaching the main branch, and its `card` entry's time plus 24 hours. If the card's raise time is older than the part of the dispatch log the desk reads, the rule shows it at once. No record holds this moment, so the count works it out by rerunning the rule on the dispatch log and the notes as they stood on the main branch. With two dispatch-log `card` entries, the earliest counts.
  - **An owner question** waits from its file's pull request's `created_at` (the pull request opened) to the main-line commit holding its answer record.
  - **A gate** is a card of kind `dor`, `criteria` or `launch`. It waits from the main-line commit holding its gate case to the main-line commit holding its ruling record.
  - **A pull request that needs the owner** is one that the desk's card-making code puts on its waiting list (J4) when run on the records as they stood at the window's end, with the code on the desk's main branch at that moment. It waits from `ready_for_review` (or `created_at` if it was never a draft) to `merged_at`, or to `closed_at` if it was closed unmerged.
  - **A deploy** awaiting the owner's review waits from the deployment's review request to the review's approval or rejection, from the run's review history.
  - These five kinds are the whole of what the count times. A kind the records cannot time is listed with the reason and left out of the medians.
  - A commit's time is its committer time with its offset. A time with an unknown offset is listed but left out of the medians, with a count.
  - A wait is the proxy's when its ending record carries a `Proxy:` line; otherwise it is the owner's, including a proxy action whose ending record has no such line. E1 is registered by the same rule (experiments/P-005-E1.md line 28; J11).
  - A wait counts if it started in the window. One still open at the window's end counts at its wait so far, from its start to the window's end, as "still open".
  A test runs it on sample records holding one wait of each of the five kinds (the decision card shown by its notes in one case and by its 24 hours in another; an answer record added by a commit on a side branch and merged later, which is timed by the merge commit on the first-parent line, not by the side branch's commit), one open pull request that the card-making code does not put on the waiting list (not counted), one still open, one that ended after the window's end, one proxy action with a `Proxy:` line, one proxy action without one (counted as the owner's) and one time with an unknown offset. It checks every field, each wait's `id` included (one of each kind's form in J4), and both medians. It then runs it again on the same records and window at another clock time, and checks that every figure is the same.
- **AC41** [trace: V8 → AC41] — Monitoring V8: when anyone runs the unseen count for a window, handing it the window's start and end as AC40 is handed them, then it reads three things and nothing else:
  - **The steps and their due times:** AC40's count for the same window. Each wait it lists is a step that fell due in the window. The wait's start is the step's due time, and its `id` is the step's waiting-list id (J4's id rule).
  - **Whether a step was shown:** the device logs committed under value/P-005/ for the weeks the window touches (AC26, J9). A step was shown at the time of the first `shown` line whose `id` equals the wait's `id`, in any device's file.
  - **Whether a step was sent:** the alert route's run logs (J5): the notice lines (`run`, `at`, `project`, `id`, `changed_at`) and the `read: true` lines (`run`, `at`, `project`, `from_run`, `notified`), joined on `run` and `project`. A step was sent at the `at` of the first notice line whose `project` and `id` equal the wait's, whatever its `changed_at`.

  From these it lists each step that was neither sent to the phone nor shown on an open timeline within 5 minutes of its due time; these are the misses. Apart, it lists each such step whose 5 minutes fell while a device log shows the view's "Stopped since" banner, or the "cannot be read just now" mark for the step's project, from a `stopped` line up to the next `resumed` line for that scope (plan line 136). Such a step is not counted as a miss.

  **A week with no device log.** A week for which no device committed a file under value/P-005/ gives no evidence that anything was shown. So no step counts as shown that week. A step due that week and not sent within 5 minutes is a miss, listed with the cause "no device log for <yyyy>-W<ww>", and the count also lists every week in the window with no file. A missing log can only add a miss, never hide one. An empty file (J9) is a log of a week with no visible time: it shows nothing, and is not listed as missing.

  **Repeats.** Apart again, the count lists each step sent more than once with the same (`project`, `id`, `changed_at`), found in the notice lines of the runs that started in the window. A repeat is not a miss. For each repeat it takes the earlier notice's run (the first sender) and the later notice's run (the second sender). It gives the cause from the `read: true` lines for the step's project, trying the causes below in this order. The first one that holds is the cause, so each repeat has exactly one cause:
  - (a) no earlier log found (AC23, exception a): the second sender's `true` line has `from_run` `null`. This holds whatever else holds, since an empty notified set alone sends every waiting step;
  - (b) a run that stopped before logging (AC23, exception b): the first sender has no `true` line;
  - (c) overlapping runs (AC23, exception c): the second sender's `from_run` names a run that started before the first sender;
  - (d) a return seen by a run (AC23, J5): the second sender's `from_run` names the first sender or a run that started after it, and that run's `true` line does not hold the pair (`id`, `changed_at`), so a run found the step gone. This is a resend by AC23's rule, not a fault;
  - otherwise "unexplained", which is a fault of the route, reported to the owner with the week's misses.

  A step answered before any run read it, or whose record showed up more than 5 minutes after its due time, is a miss unless it was sent or shown on an open timeline within 5 minutes of its due time, and it is listed with that cause.

  A test runs the count on sample records and logs holding: one step shown in time; one sent in time; one missed; one missed while the view showed its banner; one missed while its project showed "cannot be read just now"; one whose record showed up after its due time and was sent late; one answered before any run read it; one due in a week with no device file and not sent in time (a miss, cause "no device log"); one due in a week whose file is empty; one sent twice for each of the causes (a), (b), (c) and (d); one sent twice where (a) and (b) both hold (listed as (a)); and one unexplained. The (d) case is a step that a run successful for its project found gone and a later run found back with its `changed_at` unchanged; the count lists it as (d) and not as unexplained. Every step in the test is matched to its `shown` and notice lines by its `id` from AC40, and the test includes a step of each of J4's five kinds.
- **AC42** [trace: V9 → AC42] — Monitoring V9: when the weekly hand check is due, then the timeline can export, for any chosen week, a sample of 20 events and every step that waited on the owner, each with every field it showed and the record it names (AC1), so a reviewer who did not build the timeline can check them by hand against the records (plan line 137). The export reads nothing but the records and the timeline's own code.
- **AC43** [trace: V7 → AC43] — Showing its own value: when the owner looks at the desk's value targets, then V7, V8 and V9 show beside the desk's others, each with its target, its figure and its state in words ("met", "missed" or "not yet measured"), never a figure that no record gives. The figures come from the weekly value record (J12), which the Chief of Staff commits after running AC40's and AC41's counts and receiving the reviewer's V9 hand check (AC42; plan line 106). The desk reads that record like any other in a connected project, and works out no figure itself. Each figure is shown with the window its entry covers, from the latest entry for that target. A target with no entry shows "not yet measured". Nothing of it is kept on Cloudflare (AC38). A test hands the view a sample record holding a met entry for one target, two entries (an older met and a newer missed) for another and none for the third, and checks each target's figure, window and words.
- **AC44** [trace: V7 → AC44] — Feedback and value review: when the Chief of Staff files the owner's feedback on the timeline as a question, or files the review card that puts V7 to V9 to the owner after the 30 days, then it shows on the timeline and the waiting list by the rules for its kind, with no change to the timeline. It has no join sheet of its own: the feedback question and the review card are files of forms the desk already reads, so they pass through J1 (a `decision` event, or a `gate` event if the review card is filed as a gate card) and J4 (the `question` or `card` kind) unchanged.
- **AC45** [trace: V9 → AC45] — Operating notes: when the timeline is handed over before the Launch gate, then the handover package's operating notes (docs/handover/P-005/) say in plain words what every state, mark and word on the timeline means ("not recorded", "reconstructed", "no longer kept", "from a kept copy", "stalled", "late", "no data", "stopped", the record writer); how the as-of time and the data's age differ; how to run the counts of AC40 and AC41 and the export of AC42; how to add a connected project; and how to roll back: redeploy the previous production deployment of the desk, then revert the merge (library/facts/F-cf-02.md:4). It has no join sheet: the notes are a document, checked by reading, and hand nothing from one piece of the product to another.

## Join sheets
- **J1 —** the records → the event reader (D1). The reader is handed, per connected project, the records a read got, keyed by GitHub object id or by path at a commit, and which it did not get. It hands on a list of event records of this exact form (UTF-8 JSON):
  `{ "id": "<project>/<kind>/<source id>", "project": "<repo>", "kind": "branch|commit|pull request|check|review|merge|deploy|gate|decision|research|stop|other", "kind_name": "<record's own name, for other>" | null, "state": "<J2 state>", "state_word": "<word shown>", "who": "<login or role>" | "not recorded", "on_behalf_of": "<login or role>" | null, "writer": "GitHub|the Orchestrator|agent <role>|not recorded", "occurred_at": "<RFC 3339>" | "not recorded", "recorded_at": "<RFC 3339>" | "not recorded", "offset_known": bool, "piece": "<item id>" | "not recorded", "milestones": ["M<n>", …] | "not recorded", "source": "<GitHub URL, or path@sha>", "links": ["<URL or path@sha>", …], "reconstructed": bool, "supported_by": ["<source>", …], "kept": "kept|no longer kept|from a kept copy", "waits_on_owner": bool, "follows": ["<event id>", …] }`.
  Where each kind's fields come from (E2, experiments/P-005-E2.md, checks this map against the records in Design. A field E2 finds missing shows `not recorded` under AC1 with no change to this sheet. A source E2 finds wrong is a revision of this spec.): branch: the ref and the pull request that names it; commit: the commit (author, committer, both dates with offset, `Agent-Session:` and `Spec:` trailers); pull request: the pull request (opened, ready for review, closed, merged); check: workflow runs and commit statuses (check runs are not readable with the key, library/facts/F-gh-fgpat-limits-01.md:4); review: the pull request's reviews (library/facts/F-rec-pr-review-fields-01.md:4); merge: the pull request's merge fields and merge commit; deploy: deployments, their statuses and the run's review history (library/facts/F-rec-deploy-review-01.md:4); gate: a `dor`, `criteria` or `launch` card, its gate case and its ruling record; decision: a `dor-fail` or `failure` card and its answer record, and an owner question and its answer; research: an intake request, its memo and its source check; stop: a `stop` card and its answer. The piece of work comes from the item id in the record's path or trailer; the project from the repository.
  Awkward cases:
  - A commit's author and committer dates are set by whoever commits (library/facts/F-git-dates-settable-01.md:4), so a commit's time has the commit's writer, not `GitHub`.
  - A re-run keeps its run id and raises its attempt (library/facts/F-rec-actions-actor-attempt-01.md:4): each attempt is one event, `follows` the one before, and `who` is the run's triggering actor with `on_behalf_of` its actor where they differ.
  - A time written with `-00:00` has an unknown offset (library/facts/F-rec-rfc3339-unknown-offset-01.md:4): `offset_known` is false.
  - An object GitHub has deleted under its retention setting: `kept` is `no longer kept` when another record (a commit status, a pull request's checks summary, a dispatch-log entry) shows it existed; otherwise no event.
  - A card with two dispatch-log `card` entries: the S-009 rule's pick (the earliest), so the timeline and the desk agree.
  - A record in a form the reader does not know: `kind` `other` with its own name if it is a GitHub object; nothing if it is a file outside the model's forms.
  A test marked `join-test: S-012/J1` covers it, with one sample record of each of the eleven kinds and each awkward case.
- **J2 —** event record → state set (D1, D2). The closed set, each with one colour and one word: `queued`, `running`, `waiting on you`, `passed`, `failed`, `stalled`, `cancelled`, `done`, `unknown`, `other`. GitHub's check and run values map so: queued, requested, pending → `queued`; in_progress → `running`; waiting (a deployment awaiting review) → `waiting on you` only when the owner is a required reviewer, otherwise `queued`; success → `passed`; failure, timed_out, startup_failure → `failed`; cancelled → `cancelled`; neutral, skipped, stale, action_required → `other` with GitHub's word (library/facts/F-gh-check-states-01.md:4). Commit statuses: pending → `running`, success → `passed`, failure and error → `failed`. A model step: started → `running`; waiting on the owner → `waiting on you`; ended by its answer or ruling → `done`; AC8's stall → `stalled`. `waiting on you` never shares a colour with `failed` or `stalled`. Awkward cases: a value not listed → `other` with its word; no value → `unknown`. A test marked `join-test: S-012/J2` covers every listed value.
- **J3 —** event records → the timeline view (D2). The view draws only what the records hand it: shape by `kind`, colour and word by `state`, the writer by `writer`, a "reconstructed" mark by `reconstructed`, "no longer kept" or "from a kept copy" by `kept`. It works out no field. Awkward cases: an event whose `occurred_at` is `not recorded` is placed by `recorded_at`, marked "recorded at"; with neither, it is placed after the event it `follows` and shows "time not recorded"; with none of these it is listed at the end of its piece of work, "time not recorded". A test marked `join-test: S-012/J3` covers it.
- **J4 —** the waiting list → the timeline's lead, every core screen not yet replaced, the notification route and the counts (D3). One list, made once per read by the desk's card-making code from the records and a moment it is handed: each entry `{ "id", "project", "kind": "card|question|gate|pull request|deploy", "title", "due_at": "<RFC 3339>", "changed_at": "<RFC 3339>", "open_key": "<the notice key>", "order": int }`. `changed_at` is the time of the latest record that changed the entry's title or S-009's flags on it, and equals `due_at` when none has. Decision cards come from S-009's one rule unchanged; gate cards, owner questions and pull-request cards as the desk lists them today; deploys awaiting the owner's review are added, and every taker of the list gets them, the unreplaced core screens included (AC20). `order` keeps the desk's published order (docs/PROJECT.md:116). **The id rule**, one per kind, so that AC40's waits, J5's notice and `true` lines and J9's `shown` lines join on one key: a card (a decision card or a gate card) is `<item>-<gate>-<n>`, its card file's name in queue/; an owner question is `question:<name>`; a pull request is `pr:<number>`. These three are the forms S-009 gives the desk's card ids (specs/S-009.md:154, which forms a notice's key from the same id, `<project>|card|queue/<id>.md`). A deploy awaiting the owner's review, which is new, is `deploy:<run id>/<run attempt>`, since a re-run raises its attempt and is a new wait (library/facts/F-rec-actions-actor-attempt-01.md:4). Since project is a field of its own, an id is unique within its project, and every join on `id` also joins on `project`. The id is built from the step's own records alone, so the wait count (AC40) builds the same id without running the list. Awkward cases: a read that did not get a project's records keeps that project's entries as last read, marked with their as-of time (AC16), and S-009's flags pass through unchanged; a deploy on a private repository whose plan has no required reviewers is not a waiting step (library/facts/F-gh-env-01.md:4). A test marked `join-test: S-012/J4` covers it, and checks one entry's `id` of each of the five kinds against the id rule, including a deploy re-run with a raised attempt.
- **J5 —** the waiting list → the alert route → the owner's phone (D3). What is handed, per connected project: a run is **successful for a project** when it read that project's records and sent every notice that project called for; a run can be successful for some projects and not others, and its overall conclusion on GitHub does not decide it. The route chooses what to send by what it has already notified, not by `due_at`. For each project, a run takes the **notified set** from the latest earlier run that was successful for that project: the pairs (`id`, `changed_at`) that run logged. It hands on each of that project's entries on the waiting list whose (`id`, `changed_at`) pair is not in that set, with `id`, `project`, `title` and `open_key`. So a step is sent by the first run that reads its project and finds it waiting, whenever its due time was, including a step whose record shows up after its due time; a project a run could not read is sent for by the next run that reads it; and each entry is sent once, and again only when `changed_at` moves or it leaves the list and comes back (AC23). A return is seen only through the notified set: a run that reads the project and finds the entry gone writes a `notified` set without it, so the next run that finds it back sends it, and AC41 lists that resend as cause (d), not as a fault; an entry that leaves and comes back between two runs successful for its project, with `changed_at` unchanged, stays in the set and is not sent again. **One run at a time:** a run does not start work on a project while an earlier run is still working on it. The Design names, for the route it chooses, the setting that makes it so; for a sender run by GitHub Actions, that is one concurrency group per project or for the whole route, with runs queued, not cancelled. If two runs overlap all the same, the repeat that follows is cause (c) in AC23 and AC41. Every line a run writes carries `"run": "<this run's id>"`. After sending for a project, a run writes one line `{ "run": "<run id>", "at": "<this run's start, RFC 3339>", "project": "<repo>", "read": true, "from_run": "<id of the run whose notified set it used>" | null, "notified": [ { "id": "<waiting-list id>", "changed_at": "<RFC 3339>" }, … ] }` to its own run log, where `notified` is every entry of that project now on the waiting list (the ones it sent and the ones already in the set); an entry no longer on the list drops out. `from_run` is `null` only under the fallback below. For a project it could not read, it writes `{ "run", "at", "project", "read": false }` with no set; a project with no `true` line is not successful in that run. A run finds, per project, the latest earlier `true` line from its runs' logs on GitHub (Actions read), or, for a route with no such record, from a record the Design names in a repository; never from a copy kept on Cloudflare (AC38; plan line 120). The route keeps no other list of what it sent. **Fallback, and only here:** with no earlier `true` line found for a project (the route's first run, or the logs past their keeping or missing), that project's notified set is empty, so the run sends every waiting step of that project. This can repeat a notice, never miss one, and AC41 lists the repeats (AC23, exception a). For each step a notice names (one line per step, also when a notice groups several), the route writes one line `{ "run": "<run id>", "at": "<RFC 3339, when sent>", "project": "<repo>", "id": "<waiting-list id>", "changed_at": "<the entry's changed_at, RFC 3339>" }` to its own run log. AC41 reads these lines and the `read: true` lines together, joined on `run` and `project` (AC41, "Repeats"). The notice opens `open_key` (AC24). Whichever route the Design chooses (a sender in each repository, a program on a Cloudflare timer, or a webhook on each repository, plan line 180), it takes this list from the card-making code, as today's sender does (docs/PROJECT.md:588), and does not make its own. A change to the sender's own files (src/notify/**) needs the owner's approval (plan line 108). Awkward cases: a route run that cannot read a project sends nothing for that project and writes its `"read": false` line; that project's steps go out with the next run that reads it, by the notified set above, so none is lost; a step whose `due_at` is earlier than the last run that read its project (its record showed up late, J1) is not in the notified set, so it is sent by the first run that reads it; a run that stops after sending some of a project's notices but before writing its `true` line is not successful for that project, so the next run sends them again (AC23, exception b; AC41 lists the repeat), since a repeat is chosen over a miss; a run delayed or dropped by GitHub's schedule (library/facts/F-gh-12b.md:4) is caught by the outside check (J7); a notice already sent for a step answered since is not withdrawn. A test marked `join-test: S-012/J5` covers it, with sample run logs holding a run that read every project, a run that could not read one project followed by one that could (the carried step is sent once), a step whose `due_at` is before the previous successful run (it is sent once, by the next run), a step whose `changed_at` moves (sent again), a step that a successful run found gone and a later run finds back (sent again), a step that leaves the list and comes back between two successful runs with its `changed_at` unchanged (not sent again), a run that stopped between sending and logging (the step is sent again), a first run with steps already waiting (every one is sent, and its `true` line has `from_run` `null`), and two runs that overlap on one project (the later one's `from_run` names the run before the first). It also checks that every line names its `run`, that each notice line carries `project` and `changed_at`, and that a notice grouping two steps writes two lines.

- **J9 —** the device log → its weekly commit → the unseen count (V8; AC26, AC41). A test marked `join-test: S-012/J9` covers it, with an empty file, a missing week, two devices, and a `stopped` line with no `resumed` line.

## Risks and mitigations
