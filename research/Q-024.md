## The question

What interrupts a single supervisor, and what waits.

In operations control, continuous-integration practice, incident response and workflow boards, how is it decided what interrupts a single supervisor of many parallel pieces of work and what waits until they look, and is there a ceiling per hour or day? Are alerts sent one per item, grouped, or at set times; what happens to an item still waiting after its first alert; and what does the supervisor see of what piled up while they were away for hours or days? Where a display shows the items that need the supervisor's action together with the surrounding work, or apart from it, and where it folds and unfolds many flows from several sources by focus, what does each gain or cost in finding the action items quickly, clutter and missed failures? What overload, misleading-display and ignored-display failures are recorded, including where displays or tools that worked alone were combined into one, how were they measured, and what fixed them?

The setup. One owner oversees several software projects worked on mostly by AI agents. In each project a script, the Orchestrator, run on GitHub Actions by repository events and a schedule, moves work through fixed phases and stages, dispatches agent sessions with distinct roles (for example builder, definer, check author, reviewer, critic, researcher, source checker) and routes each result by a fixed table (shumpmaster/Personal-Org-Operating-Model OPERATING_MODEL.md §4 and §5; Service-Desk governance/ROUTING.toml). The owner also works with a conversational agent, the Chief of Staff, which the Orchestrator does not dispatch; it writes the questions put to the owner, records the owner's rulings and writes the case at each phase gate. The work leaves records in two kinds of place: GitHub objects (branches, commits, pull requests, checks run by GitHub Actions, reviews, merges, deploys) and files in each project repository and in one portfolio repository spanning them (status files, an append-only dispatch log, decision cards in queue/, the owner's answers in decisions/, review verdicts in reviews/, research questions, memos and source checks in research/, design mockups in docs/design/, gate cases in docs/gates/). Every agent commit names its session; where only one branch can be pushed, builder branches stay local and reach GitHub only through merge commits; reviewer-role agents never commit, and their verdicts are filed by the Orchestrator (Service-Desk AGENTS.md §1; CLAUDE.md). Some steps wait on the owner: answering a card or a question, ruling a phase gate, merging a pull request that needs the owner, approving a deploy. What exists today: a status page, the desk, hosted on Cloudflare Pages, reads every connected project's records with one fine-grained, read-only GitHub token. Its screens include one card per project, what waits on the owner, and each project's timeline of phase runs and milestones with each step linked to its record. The owner answers questions from the desk through a link that commits the answer record; other actions happen on GitHub. In one of the projects, a sender run by GitHub Actions every 5 minutes and when workflow runs end sends Web Push alerts to the desk installed on the owner's iPhone, and opens a GitHub issue if it can no longer send. The owner reads mostly on a phone.

## The decision it serves

The interruption rule for the owner's phone and what the first screen shows.

## What each answer would change

The alert rule, whether it has a daily limit and what that is, and what sits on the first screen and what one step away.
