# Ruling needed: Where should the plan for the pull-request briefing page live?

Milestone: none (the project item is not filed yet; this question decides where its plan goes)
Asked in session: session_01QBwHGJtoNqbcm5CHZ4r84S

WHY: You ruled that where this work's plan lives comes back to you before the plan is written. The plan is the brief you rule on at the Design gate: what is in and out, who owns what, the limits and spend, how success is measured and when to stop, and the milestones. Each repository holds one plan document, which the desk's checks and screens read, and the desk's own plan fills it; the model says that plan was settled when it was approved. The model lets later work add its own milestones to that document, each marked as the new work's, but says nothing about its scope, owners, limits or value targets. None of the options is free: the first bends a stated rule and shows two of the new work's milestones as reached too early; the second waits for a change to the model's tools; the third leaves the checks blind to the plan. Until you rule, the Discovery is not opened on the desk and the brief cannot be written. The research already running carries on either way.
OPTIONS:
  A. The desk's own plan document, as later work.
     What happens: the new work's milestones go in the plan's milestone section, each marked as the new work's, as the model provides. Its scope, owners, limits and value targets go in their sections as new lines, marked the same way, beside the desk's lines, which stay word for word as approved. The desk's screens show them with the desk's own.
     Cost: the model says the approved plan is settled, and only its milestones may change later, so new lines in the other sections go against that rule as written; it would be logged for the model to settle. The checks would show two of the new work's Discovery milestones as reached before their work is done: "Success defined" at once, because the desk's own value targets are there, and "Scope, limits and owners agreed" as soon as the Critic passes the brief, whether or not the new lines exist. The automatic ready check sees the sections already filled by the desk's lines, so only the Critic's reading of the plan could catch a missing piece of the new brief; the Critic's instructions are fixed and cannot be told which lines are new without a rule change for your approval, so it would rely on the marks on each line. Rules out: nothing; the work could move to its own document later.
  B. A plan document of its own in the same repository, after a change to the model's tools to allow one per project.
     What happens: the model and its checks are changed first, under that repository's own rules (a frozen spec, its builder, its reviews), so a repository can hold one plan per project and the checks read each separately; then this plan is written in its own document. The same change answers the open lesson in Model-Lab, whose second idea hits the same limit.
     Cost: the brief waits for that change's plan, build and review, whose size is not yet known; more questions reach you, from that change as well as this work. Rules out: nothing.
  C. A plan document of its own in the same repository, with no change to the tools.
     What happens: the brief is written in a separate file beside the desk's plan, and the Critic checks it by hand.
     Cost: the checks, the timeline and the desk's screens do not read that file, so its milestones and value targets show nowhere; the Discovery's automatic brief check reads the desk's plan, not this file; and at Design each spec must name milestones from the desk's plan document, so this file's milestones would fail that check, and the plan would have to move then. Rules out: nothing, but it postpones the choice to Design.
RECOMMENDATION: B — it is the only option that keeps the desk's approved plan as approved and shows the new work's milestones truthfully, and it also settles the Model-Lab lesson. Low confidence: it costs time whose size is not known. It would change to A if you would rather start the brief now and accept the two early "reached" marks and the bent rule, both logged for the model to fix. Not offered: a new repository, since the page is to be on the desk, whose code is in this repository; and the portfolio, which holds the shared ideas, library and standing records, not a plan document the checks read.
RISK CLASS: R0   REVERSIBILITY: reversible   BLAST RADIUS: the desk's records and its plan document (A), or the model's tools in their own repository (B); nothing on the live desk changes
