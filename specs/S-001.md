## Terms used in this spec
- **Connected project:** an entry in `src/config/projects.json` (J7) that the read token can read.
  At launch there are two: Service-Desk (operating model v3: `status/`, `queue/`, `dispatch-log/`)
  and Personal-Org-Operating-Model (governed under v2.5.1, with `docs/sprints/` and
  `docs/LEDGER.md`, and no `status/`, `queue/` or `dispatch-log/`; checked 2026-10-06 at 677fe5a).
  The design is sized for up to 5.
- **Model of a project:** `v3` or `v2.5`, set in J7. It decides which records J9 reads.
  - v3 projects get the full pipeline view.
  - v2.5 projects get the **reduced view** (J9): sprint, headline and "next" from the ledger, with
    PRs, questions and CI. They have no per-item stages and no "running now", because v2.5.1
    records neither.
- **Card:** a file `queue/<item>-<gate>-<n>.md` directly under `queue/` in a v3 project, written by
  the Orchestrator. Its **answer** is `decisions/<item>/<gate>-<n>.md`, which is also the path the
  card names on its own `answer:` line (J2). Card files are kept after answering: on 2026-10-06 all
  12 cards in Service-Desk `queue/` have answer files.
- **Hold card** (from M2, AC46): a file `queue/ci-hold-<sha12>.md` in a v3 project, written by the
  Orchestrator when its loop has held for over 60 minutes because the latest governance run on the
  default branch's tip is not green (governance/checks/orchestrator_git.py:1198 and :1233–1245). It
  has no answer file: the owner fixes or re-runs the governance run. J2 says when it is open.
- **Merge card** (from M2, AC47): a file `queue/<item>-merge-conflict.md` or
  `queue/<item>-merge-by-hand.md` in a v3 project, written by the Orchestrator's merge gate when a
  finished item can't be merged without the owner (orchestrator_git.py:2737 and :2887–2910). It has
  no answer file: the owner merges the item by hand or changes it. J2 says when it is open.
- **Owner question:** a file `questions/<name>.md` (`<name>` holds no `/`) other than
  `questions/_TEMPLATE.md`, in either model, in the form of `questions/_TEMPLATE.md`
  (`# Ruling needed:`, `WHY:`, `OPTIONS:`, `RECOMMENDATION:`, `RISK CLASS:`, `DEFAULT:` and
  `TIMEOUT:`; J2).
  - **Its answer (v3 projects):** `decisions/questions/<name>.md`, whose first line is
    `Ruling: <choice>`. That is how questions are answered today:
    - Service-Desk e012edb added `decisions/questions/Q-005-sources.md`, whose line 1 is
      `Ruling: A`, and deleted `questions/Q-005-sources.md` in the same commit;
    - f45d10e did the same for `P-001-acting-route` and `P-001-planning-scope`.
  - **When it is open:** while the question file exists and no answer file exists.
  - **v2.5 projects:** there the ruling goes to the ledger, and the file is deleted
    (Personal-Org-Operating-Model f2ac482 recorded the rulings on Q-005 to Q-014 as L-0017 to L-0026
    and deleted `questions/Q-005-…` to `questions/Q-014-…`). So in v2.5 a question is open while its
    file exists.
- **Needs the owner (flagged):** exactly these four things, in a connected project.
  - An open card: a card with no answer file on the default branch, or an open hold card or merge
    card (J2, from M2).
  - An open owner question (above).
  - An open, non-draft pull request whose base is the project's default branch, except one the
    Orchestrator merges itself (head branch `item/<id>` in a v3 project: the merge gate merges item
    branches, model S-013 AC3). The owner's own PRs count: agents push under the owner's account,
    and GitHub won't let them request the owner's review (P-001-build-path.md, question 1).
    - **What the repositories show (2026-10-06, REST `pulls?state=all` and `pulls/<n>`; observed,
      C):** the two repositories hold 53 PRs (33 in Service-Desk, 20 in
      Personal-Org-Operating-Model).
      - Every one was opened by the owner's account (`shumpmaster`) against `main`, with no
        requested reviewers.
      - Every one has been merged, each by `shumpmaster`. None was merged by the Orchestrator.
      - None came from an `item/` branch.
    - So in practice every such PR waits on the owner's approval or merge.
  - A v3 status file in state `waiting-owner` whose card file is not yet on the default branch. This
    is a safety net against a missed decision, worded "waiting on you: card <gate>-<n> (card file
    not found)".
- **Activity:** anything shown but not flagged. That covers:
  - CI results.
  - Draft PRs, PRs whose base is not the default branch, and `item/` PRs in v3 projects.
  - Dispatch-log events: dispatches, outcomes, errors, retries and anomalies.
  - Sessions that run past their time limit.
  - Queue files that can't be parsed.
  - The Chief of Staff's `-notes.md` files.

  "A gate catching a problem, or an agent retrying, is activity" (PROJECT.md Part 2).
- **Open window:** a span during which the desk page is visible in the foreground on a device (the
  browser's page-visibility state is "visible").
- **Read successfully:** both of these hold.
  - The project's last poll call (J6) returned `state` `ok` or `unchanged`, and the page parsed
    it without error.
  - Every blob call that the poll's tree change needed has returned `ok`.

  An `unchanged` answer (every steady-poll request returned 304) counts: GitHub answered and
  nothing was new. These do not count: `partial`, `cant-read`, a 403 from the function, a Cloudflare
  error, a network failure and a page error (J6's `page` reason).
- **Quiet:** no flagged item in any connected project, **and** every connected project read
  successfully within the last 3 minutes.
- **Milestone accepted:** four steps, in order (P-001-build-path.md, question 0; the deploy route
  in "Toolchain and deploy route").
  1. The Reviewer's verdict on the milestone's pull request is PASS.
  2. The owner has merged it.
  3. The owner has approved desk-deploy's `preview` job for that merge, and it has deployed `main`
     to the preview.
  4. The owner has tried the preview and accepted the milestone.

  Problems found on the preview are fixed forward, in a new pull request, which also needs the
  Reviewer's PASS. MD adds its own steps before the owner accepts (AC44 steps 1–6).
- **Design lab:** MD's process A. Mockup pages the Chief of Staff publishes as private live pages,
  filled with a snapshot of real records and changed from the owner's plain-language requests and
  screenshots. No pull request or deploy; not desk code.
- **Sandbox view:** MD's process B. A view inside the desk, entered by `?sandbox`, that renders the
  chosen candidate designs against the desk's live data on the preview. It is built, reviewed and
  deployed like any other desk code.
- **Decision kind:** what sort of thing waits on the owner, read from the records: a card, an owner
  question (reversible, with a default; or irreversible, never defaulting, J2), or a pull request.
- **Unknown, stale and estimated values:** "not recorded", "not available", "not given", a value
  from a read older than 3 minutes, and a figure the desk derives rather than reads (for example a
  median over open cards' waits so far).
- **Phase and phase run** (from MD, AC50; model v3.3.0, S-023, L-0008): the model's phases are
  Discovery, Design, Build, Launch, Operate and Review. The desk shows the first four, then
  **Done**, which is not a phase: where a project stands once the owner passes its Launch gate.
  A **phase run** is one pass through a phase, labelled "<Phase> i<n>" (for example "Design i2"),
  exactly as the model's timeline names it (J11).
- **Milestone** (from MD, AC50): a phase's standard milestones (the model's checklist, the same for
  every project) and the project's own (docs/PROJECT.md section 3, each led by its plain-English
  name). Milestones are level two of the breakdown, the owner's "N+2".
- **Who has the ball** (from MD, AC49; ruling 1): who is moving a project's work right now, as the
  records the desk reads show it.
- **Queue** (from MD, AC52; ruling 6): everything that needs the owner (Terms, above) in one project,
  grouped by kind of action. There is no queue across projects.
- **Response sheet** (from MD, AC52, AC53): the sheet that opens over the queue when the owner taps
  an item: its options as choices, its facts prefilled, and, where the answer is a committed file,
  a prefilled text box.

## Join sheets

- **J1 — GitHub REST → desk function (reader).**
  - **Every request:** each `GET` goes to `https://api.github.com` with
    `Authorization: Bearer <read token>`, `Accept: application/vnd.github+json` and
    `X-GitHub-Api-Version: 2022-11-28`. When the page holds an ETag for the URL, it also carries
    `If-None-Match: <etag>`.
    - `{o}/{r}` and `{default}` come from J7 (`repo`, `defaultBranch`). Nothing is looked up to
      learn the default branch, so a steady poll needs no extra request for it.
  - **Poll call** (one per project per 60 s, J6). It makes these requests in this order:
    1. `GET /repos/{o}/{r}/branches/{default}`. From the body the function takes the head commit
       `commit.sha`, `commit.commit.tree.sha` and `commit.commit.committer.date`. This is the only
       response body the function parses whole; a compare answer is cut down to its status and
       counts (J6), and every other body it passes on as text (below).
    2. `GET /repos/{o}/{r}/pulls?state=open&per_page=100`.
    3. From M2 (AC29), for every project, two workflow-run lists for the head (M1 read
       `commits/{head}/check-runs` instead):
       - 3a. `GET /repos/{o}/{r}/actions/runs?head_sha={head}&event=push&exclude_pull_requests=true&per_page=100`;
       - 3b. `GET /repos/{o}/{r}/actions/runs?head_sha={head}&event=workflow_dispatch&exclude_pull_requests=true&per_page=100`.
    4. Only when the head differs from the head the page sent (or the page sent none):
       `GET /repos/{o}/{r}/git/trees/{treeSha}?recursive=1`.

    With one page each, a steady poll is exactly four requests (three in M1).
    - **Why workflow runs:** a fine-grained token has no Checks permission, so check runs can't be
      read on a private repository (Personal-Org-Operating-Model, P-001-m1-accept.md). Workflow
      runs need Actions: read, which a fine-grained token offers (Setup G1, G3; C).
    - **Why `workflow_dispatch` as well as `push`:** the Orchestrator pushes with the workflow's
      own token, which starts no push run, and its commit job then starts governance by
      `workflow_dispatch` (governance.yml:1–7; orchestrator.yml:459–465). So on a head the
      Orchestrator made, governance's run is a dispatch run. A push filter alone would hide it, and
      a failing governance run halts the Orchestrator's loop.
    - **Why not every event:** the API takes one `event` value per request and no exclusion.
      - Unfiltered, the list also holds the Orchestrator's scheduled runs: every 30 minutes
        (`.github/workflows/orchestrator.yml:16`), so an idle head gathers 48 a day and would pass
        3 pages in about six days.
      - It would also hold `pull_request` runs that share the head's sha when a pull request is
        merged without a merge commit. Those are review-time runs; for example governance's
        `pull_request` run at c782653 failed while its `push` run passed.
      - So scheduled and pull-request runs are not read. The latest Orchestrator run is still seen
        whenever it was a push or dispatch run (below, "activity only").
  - **Paging.** When a list response carries `Link: <…>; rel="next"`, the function follows it, up
    to 3 pages per list (300 PRs, or 300 workflow runs in each of 3a and 3b). Push runs are at most
    one per workflow per push. Dispatch runs on one head are one governance run per Orchestrator
    push plus the Orchestrator's chained runs; that these stay well under 300 is my estimate (E).
    - Each page is one request with its own ETag.
    - If a 4th page would be needed, the function returns `state: partial`, reason `too-many`. It
      can tell from the `Link` header alone, without parsing a body.
    - A tree whose JSON has `truncated: true` is detected by **the page**, which parses the tree. The
      page sets the same `partial` / `too-many` on its own record of the project. The function
      doesn't parse the tree.
    - Either way, the project is not read successfully (AC5), so a missed PR or CI run can never
      show as "Quiet".
    - Every page is requested on every poll, because a change on page 2 doesn't change page 1.
  - **Blob call** (J6): up to 25 requests, of two kinds (three from M2: blobs, history and
    compare).
    - `GET /repos/{o}/{r}/git/blobs/{sha}` with `Accept: application/vnd.github.raw+json`. If that
      returns JSON instead, the function decodes `content` from base64.
    - For owner questions and their rulings only (J2), a history request:
      `GET /repos/{o}/{r}/commits?path=<path>&sha={default}&per_page=100`.
      - **Oldest commit** (the path's creation): if the response's `Link` header has `rel="last"`,
        the function also fetches that page, and the page takes its last entry's
        `commit.committer.date`. That is at most 2 requests per path, with no limit on history
        length.
      - **Newest commit:** the first entry of page 1.
      - The function returns the raw pages, and the page reads them.
    - For open merge cards only (J2, from M2, AC47), a compare request:
      `GET /repos/{o}/{r}/compare/{tip}...{head}?per_page=1`, where `{tip}` is the card's 40-hex
      item tip and `{head}` the default-branch head sha the page last read. The function returns the
      body cut to its status and counts (J6); the page reads only its `status` (`ahead`,
      `identical`, `behind` or `diverged`; C, not in the library, confirmed by M2's join test
      against recorded answers). `per_page=1` keeps
      the commit list in the body short (C).
    - Blobs are fetched by their sha, so they never change and carry no ETag. The page keeps each
      parsed result keyed by blob sha (J6).
  - **Limits per invocation.**
    - A poll call makes at most 11 GitHub requests (from M2: the branch, 3 pages each for PRs, 3a
      and 3b, and the tree); a blob call makes at most 25. Both sit inside the 30 that J1 allows per invocation.
    - J8's key fetch adds at most 1, and redirect hops count too (F-cf-workers-02). The 50 on Free
      are never approached.
    - At most six requests wait for headers at once, and a seventh queues (F-cf-workers-03 for the
      six, A; F-cf-workers-07 for the queuing, B). So a full blob call runs in about five waves of
      six. Whether its wall time and CPU fit Free is EXP-001's measurement. If not, the blob batch
      size (one constant, `BLOB_BATCH = 25`) is lowered.
    - **EXP-001's result** (docs/handover/experiments/EXP-001-result.md): every set passed, with
      no Error 1102 or 1027, a maximum wall time of 1,938 ms and at most 25 GitHub requests per
      call. `BLOB_BATCH` stays 25, and the page's 30 s call timeout (J6) stands, about 15 times the
      longest call measured. Cloudflare showed no CPU figure for the Functions.
  - **The function parses no record content.**
    - It returns the PR pages, workflow-run pages, tree and blobs to the page as raw text (J6), and
      the page does all record parsing (J2, J9, J10).
    - The function's own work is J8's check, the branch body, the response headers (`ETag`,
      `Link`, `X-RateLimit-*`, `Retry-After`), J6's request checks, and assembling the response.
      Base64 decoding happens only if GitHub ignores the raw media type.
    - This keeps CPU per call small and independent of repository size; EXP-001 measures it anyway.
  - **CI reduction rule** (one result per head, computed on the page from all of 3a's and 3b's
    pages' `workflow_runs` arrays; the words are GitHub's `status` and `conclusion` values, which
    workflow runs share with check runs, C):
    - **Latest run per workflow:** runs are grouped by `path` (the workflow file), and only the
      run with the greatest `run_number` in each group counts. A re-run is a new attempt of the
      same run, and the list gives each run's latest attempt (C), so a run that failed and then
      passed on re-run counts as passing.
    - **Activity only, never CI:**
      - **`.github/workflows/desk-deploy.yml`** (N1): its runs wait for the owner's approval and
        may be rejected; neither says anything about the code. Its latest run is shown as activity,
        "deploy <short sha>: <what happened>":
        - `status: waiting` → "waiting for approval";
        - another status not `completed` → the status word (for example "in_progress");
        - `conclusion: success` → "deployed";
        - `conclusion: failure` → "failed or rejected": the run list gives a rejected deploy and a
          failed job the same conclusion as far as the desk can tell (C; the first rejected deploy
          confirms it), so the desk doesn't guess which;
        - any other conclusion → the conclusion word (for example "cancelled").
      - **`.github/workflows/orchestrator.yml`:** the Orchestrator's own runs, cancelled and skipped
        by design (model S-018). Its latest run is shown as activity, "Orchestrator run:
        <conclusion>", so a failed Orchestrator run is visible without colouring CI.
      - These two paths are a list in the page's code. A project whose files differ is not
        affected: paths it lacks never match.
    - Then, over the remaining runs:
    - `failing` if any run has `status: completed` and a conclusion of `failure`, `timed_out`,
      `action_required` or `startup_failure`;
    - otherwise `running` if any run's `status` is not `completed`;
    - otherwise `passing` if at least one run concluded `success`, and every other run concluded
      `success`, `neutral`, `skipped`, `cancelled` or `stale`;
    - otherwise `none`: no runs, or all of them skipped, neutral, cancelled or stale.
    - **Real samples** (`gh api` on 2026-10-08):
      - Service-Desk at e2ab9c5, a head the Orchestrator made: 3a lists nothing; 3b lists
        `governance.yml`, `workflow_dispatch`, `success` (run 292) and `orchestrator.yml`,
        `workflow_dispatch`, `success` (run 189). CI reduces to `passing` from governance; the
        Orchestrator run is activity. With a push filter alone, CI would have read `none`.
      - Service-Desk at 38722d3 (main): 3a lists `governance.yml`, `push`, `success`; 3b lists
        nothing. That reduces to `passing`. The scheduled `orchestrator.yml` run on the same head is
        not read.
      - Service-Desk at bbd7abc (PR #40's merge): 3a lists `desk-build.yml`, `desk-deploy.yml` and
        `governance.yml`, each `push`, `success`. CI is `passing` from desk-build and governance;
        the deploy is activity, "deployed".
      - Personal-Org-Operating-Model at 677fe5a: 3a lists `ci`, `push`, `success`.
    - `cancelled` counts as not failing. That is my choice (C), and it is easy to change.
  - **Awkward cases:**
    - **304 on every steady-poll request:** returns `unchanged` with nothing re-sent.
    - **401, or a 403 whose `X-RateLimit-Remaining` is not `0` (or absent) and which has no
      `Retry-After`:** `cant-read`, reason `token` (src/lib/github.js:54).
    - **Any 429, or a 403 with `X-RateLimit-Remaining: 0` or a `Retry-After`:** reason
      `rate-limit`, and `retryAfter` is set from `Retry-After`, else the reset header, else 60 s. The page doesn't poll that project again before
      then.
    - **404 on the branch:** reason `config`, "default branch <name> not found".
    - **403 on workflow runs only** (a token-kind 403, as above): CI shows "can't read CI (the read
      token needs Actions: read)", and the project stays readable. This is the case where the token
      lacks Actions: read (Setup G3 not yet done). A 401 there is the token failing, reason `token`,
      as on every other request (PR #40 review N8). (Under M1's check-runs read, this case was
      "can't read checks", which EXP-004 Q4 found on Personal-Org-Operating-Model.)
    - **GitHub 5xx or a network failure reaching GitHub:** reason `github`.
    - **Too many pages:** `partial`, reason `too-many`, set by the function. **A truncated tree:**
      the same, set by the page.
    - **Retries:** a failed or rate-limited read is never retried within an invocation, or sooner
      than the next scheduled poll.
  - A test marked `join-test: S-001/J1` covers it, with recorded GitHub responses including a
    two-page PR list, the workflow-run samples above (the e2ab9c5 dispatch case among them), a
    `waiting` and a rejected deploy run, a failed Orchestrator run, and a 403 on workflow runs.

- **J2 — Cards, answers and owner questions → read model (page side).**
  - **Where they come from:** the tree (J1) lists the paths; blobs give the text.
  - **Cards (v3).** A card is a path matching `^queue/([A-Z]+-[0-9]+)-([^/]+)-([0-9]+)\.md$`. The
    groups are `<item>`, `<gate>` and `<n>`. A gate may hold hyphens, as in `dor-fail`, but never
    `/`, so nothing under `queue/merge/` can match.
    - Not cards: `queue/README.md` (ignored), anything under `queue/merge/` (merge-gate notes,
      S-013 AC5, shown as activity), hold cards (below), and any other path under `queue/` that
      doesn't match (activity, "can't parse", never flagged, never dropped silently).
  - **Hold cards (v3, from M2, AC46).** A path matching `^queue/ci-hold-([0-9a-f]{12})\.md$`. It
    doesn't match the card pattern above (no trailing `-<n>`), so it is read here.
    - **The real form** (`hold_card`, governance/checks/orchestrator_git.py:1233–1245):
      - line 1: `# Hold card — the default branch's governance run is not green`;
      - line 3: `tip: <40-hex sha>   state: <state>   held for: <minutes> minutes`, where `<state>`
        is the Orchestrator's word for the latest governance run on that tip (`failed`, `running`,
        `absent` or `unreadable`, orchestrator_git.py:1201–1230);
      - sections `## 1. The decision` and `## 2. What to do`, the second ending "The loop reads no
        answer from this card."
    - **What the desk takes:** the title (line 1 after `# `), `tip`, `state` and `held for` from
      line 3, and section 2's text. A line that doesn't match is named in `notes`; the card is
      still flagged while open.
    - **When it is open** (the desk's version of the Orchestrator's rule, orchestrator_git.py:3175–3215,
      which keeps "the newest ci-hold card until a governance run on its commit or a descendant
      passes"):
      - **Only the newest counts.** With one hold card in the tree, it is the newest. With several,
        the page reads each one's oldest commit through J1's history request (the creation time,
        fixed once known and cached by path) and takes the latest. The others are activity,
        "replaced by a newer hold card".
      - **It is open** until the latest run of `.github/workflows/governance.yml` among J1's 3a and
        3b on the default-branch head has `status: completed` and `conclusion: success`. The head is
        always the card's commit or a descendant of it.
      - **The difference from the Orchestrator, stated:** the Orchestrator also clears it when a
        governance run passed on an intermediate commit between the card and the head. The desk
        sees only the head's runs, so in that case it keeps flagging until the head's governance
        run passes. It errs towards flagging (V1 over V2). This is my choice (C).
      - A deleted hold card file is no longer flagged.
    - **No answer, no times:** it has no answer path and no dispatch-log `card` entry, so AC16 and
      AC20 don't apply to it.
  - **Merge cards (v3, from M2, AC47).** A path matching

    - **The real form** (`MergeGate.fail`, governance/checks/orchestrator_git.py:2887–2910):
      - line 1: `# Merge card — <item> (<step>)`, where `<step>` is `conflict` or `by-hand`;
      - line 3: `item: <item>   tip: <40-hex sha>   step: <step>` (the Orchestrator reads the tip
        with `^item: [PQE]-[0-9]+ +tip: ([0-9a-f]{40})\b`, orchestrator_git.py:3031);
      - sections `## The decision`, `## Why` and `## What to do`, the last ending "The loop reads no
        answer from this card."
      - `conflict` reads "the merge conflicts: resolve it on the item branch or the default branch,
        or merge it by hand"; `by-hand` reads "the gate cannot satisfy what it needs, so the owner
        merges it by hand".
    - **What the desk takes:** the item and step from the path, the tip from line 3 (by the
      Orchestrator's own pattern), and the three sections. A card whose line 3 doesn't match is
      named in `notes` and **still flagged** (its tip unknown, so only the closed and deleted rules
      below can clear it).
    - **The Orchestrator never deletes it.** It writes the file again for a newer tip, and stops
      treating it as waiting once the tip is merged or recorded, or the item is closed
      (orchestrator_git.py:3166–3173 and :3216–3225). So the file existing is not enough.
    - **When it is open** (the Orchestrator's rule, applied by the desk):
      - the file exists on the default branch; and
      - the item's status file isn't `closed` (a `done` item is exactly one waiting to merge, so
        `done` doesn't clear it); and
      - no line of `status/merges.jsonl` has this `item` and `item_tip` equal to the card's tip
        (the gate's own merges). The page reads that file as a blob, cached by sha; and
      - the tip is not merged into the default branch by hand. The desk asks GitHub once per open
        merge card and head (J1's compare request): a `status` of `ahead` or `identical` means the
        tip is an ancestor of the head, so it is merged. That answer is final for that tip and is
        cached by tip; `behind`, `diverged`, or a failed read leave the card flagged and are asked
        again on the next head change.

    - **No answer, no times:** as for hold cards.
    - The card's text is parsed from the real form. Sample: Service-Desk `queue/P-001-stop-6.md`.

    - What the desk takes from it:
      - the title, which is the first line under `## 1. The decision`;
      - the options, each the backquoted word at the start of a line under `## 4. Options`;
      - the answer path, which is the first backquoted path on the `answer:` line.

- **J6 — Desk page ↔ desk function.** Both calls are `POST` with a JSON body, so the ETags travel in
  the body, not in a header.
  - **Request checks (D5.2, before J8's work is used for anything):**
    - **Content type:** the function answers 415 unless `Content-Type` is `application/json`. A
      JSON content type is not a "simple" request, so a cross-site page can't send one without a
      CORS preflight (C, browser behaviour).
    - **Origin:** the function answers 403 when an `Origin` header is present and differs from the
      origin of the request's own URL (scheme, host and port of `request.url`). That covers the
      preview, `needs-you` and each custom domain without a list.
    - **No CORS:** the function sends no CORS headers, so no other origin can read a response.
    - **Methods:** any method other than `POST` on `/api/*` gets 405.
  - **Poll call:** `POST /api/poll`.
    - Request body:
      `{ "project": "<name>", "head": "<sha>" | null, "etags": { "<GitHub URL>": "<etag>" } }`.
    - `etags` holds only the poll's own list URLs: the branch, up to 3 PR pages and up to 3
      workflow-run pages (from M2, up to 3 for each of J1's 3a and 3b), so **at most 10 entries,
      under 3 KB**.
    - Blobs need no ETags (J1), so the ETag state no longer grows with the repository. That
      resolves the plan review's finding 6.
  - **Poll response:**
    - `{ "project", "readAt": "<ISO UTC>",`
    - `"state": "ok" | "unchanged" | "partial" | "cant-read",`
    - `"reason": null | "token" | "rate-limit" | "github" | "config" | "too-many",`
    - `"retryAfter": <seconds> | null,`
    - `"head": { "sha", "treeSha", "committedAt" },`
    - `"etags": { url: etag },`
    - `"pulls": [ "<raw page>" | null ], "checks": [ "<raw page>" | null ],`
    - `"tree": "<raw>" | null }`

    A `null` page means 304: the page reuses what it parsed last time for that URL. `tree` is
    present only when the head changed or `head` was null.
    - From M2, `checks` holds the workflow-run pages (J1, AC29): 3a's pages, then 3b's, each
      named by its URL in the response as today. The field keeps its name, so the page's side of J6
      changes only in what it parses. When workflow runs answered 403, the
      response says so (today's `checksState: "cant-read"`), and CI shows AC29's words.
  - **Blob call:** `POST /api/blobs`.
    - Request: `{ "project", "blobs": ["<40-hex sha>", …], "history": ["<path>", …],
      "compare": [{ "base": "<40-hex tip>", "head": "<40-hex sha>" }, …] }` (`compare` from M2,
      AC47; optional).
    - **Budget:** each blob counts 1 against `BLOB_BATCH` (25), each history path counts 2,
      because J1 may fetch its last page, and each compare counts 1.
    - Response: `{ "project", "readAt", "state", "reason", "retryAfter",
      "blobs": { sha: "<raw text>" | null }, "history": { path: ["<raw page 1>", "<raw last page>"?] },
      "compare": { "<base>...<head>": "<cut body>" | null } }`.
    - **A compare answer is cut, not raw** (PR #44 review N1): GitHub's compare body carries
      `files` with their patches and a `commits` list, which can run to megabytes. The function
      reads the body only up to the first `"commits"` key, and never more than 65,536 characters
      (`COMPARE_SCAN_CHARS`), then stops the download. From that head it takes `status` (`ahead`,
      `behind`, `identical` or `diverged`) and, when found, `ahead_by`, `behind_by` and
      `total_commits`, and returns them as one small JSON object, for example
      `{"status":"ahead","ahead_by":2,"behind_by":0,"total_commits":2}`. The body is never parsed
      whole. The page reads only `status`.
    - A `null` compare is a failed read (the card stays flagged): GitHub refused it, or no status
      was found in the part read. Only a rate limit or a 401 stops the rest of the call.
    - **Refusals (400):**
      - a project name not in J7;
      - a sha that isn't 40 hex digits;
      - a history path that doesn't match `^(decisions/)?questions/[^/]+\.md$` or (from M2, AC46)
        `^queue/ci-hold-[0-9a-f]{12}\.md$`;
      - a compare `base` or `head` that isn't 40 lowercase hex digits (from M2, AC47);
      - a budget over 25.
    - The function only ever issues J1's request forms against configured repositories.
  - **The page's side.**
    - **Parsed cache:** the page keeps parsed results keyed by blob sha in local storage, and fetches
      only blobs whose sha it lacks. If storage is unavailable, it holds them in memory for the
      open window.
    - **Diffing:** it compares each new tree with the cached one to find changed paths.
    - **Which blobs it fetches:**
      - **For v3:**
        - every `status/<item>.toml`, and `governance/ROUTING.toml` (time limits, J9);
        - from M2: the newest hold card only (AC46; J2's "Only the newest counts"). With several
          hold cards in the tree, each one's history is read once to learn its creation time (and
          kept), then only the newest's blob is fetched; the older ones are never read. Also every
          merge card in the tree, and `status/merges.jsonl` when a merge card is present (AC47);
        - the two dispatch-log months, and `status/outcomes.jsonl` (M2);
        - open cards;
        - each card answer blob that has no `decision` log entry yet (J2);
        - each `decisions/questions/<name>.md` whose question is listed in AC20 (for its
          `Ruling:` line);
        - the current plan (Service-Desk only).
      - **For v2.5:** `docs/LEDGER.md`, plus the files in `docs/sprints/` other than `PROGRESS.md`

      - **History reads:** those J2 names.
    - **When a project counts as read:** only when every needed blob has arrived (AC4).
  - **Reasons the page sets itself:**
    - The function sets the reasons above.
    - The page adds three on its own record of the project, never received from the function:

      JSON. Any other line is named in `notes` and skipped.
    - **Field types (AC31, from M2).** Each value is checked against its type before use. A value of
      the wrong type is named in `notes` (file, line, field) and skipped, and the field shows "not
      recorded":
      - integers: `stage`, `card`, `plan_round`, `build_round`, `attempts`, `sessions`;
      - booleans: `confirm_used`;
      - strings: `kind`, `role`, `last_verdict`, `gate`, `spec`, `outcome`, and `dispatched_at` (an
        ISO UTC time);
      - `state`: a string, one of the six below;
      - unknown keys are ignored.

      Dispatch-log and `outcomes.jsonl` lines are checked the same way: `item`, `role`, `route`,
      `time`, `session`, `result`, `verdict`, `record`, `gate`, `word` and `error` are strings (or
      null where the sample shows null); `stage` and `card` are integers; `proxy` and `strike` are
      booleans. A line with a wrong-typed key it needs for its shape is named and skipped as a whole.

      one project's records never blanks another's box.

## Toolchain and deploy route
- **Layout.** Everything the Builder writes for the desk lives under `src/`, and deploys run from
  `src/`.
  - `src/package.json`: Node 20 or later, ES modules. Wrangler is a devDependency pinned to an exact
    version.
  - **No runtime dependencies (decided here; the Reviewer's round-2 non-blocking 2):**
    - `src/package.json` has no `dependencies` block, and the build fails if one appears.
    - The Functions and the page import only from `src/functions/`, `src/lib/` and `src/public/`.
    - So the bundle wrangler makes of `src/functions/` at deploy time contains only reviewed
      repository code. No separate `wrangler pages functions build` step is needed.
    - The deploy job installs nothing under `src/`. A package import in a Function would therefore
      fail the deploy-time bundle, which enforces the rule a second time.
  - **No lifecycle scripts:** `src/package.json` has no `preinstall`, `install`, `postinstall`,
    `preprepare`, `prepare`, `postprepare`, `prepack`, `postpack`, `prepublish`,
    `prepublishOnly`, `publish` or `postpublish` script. desk-build fails the PR otherwise.
  - `src/package-lock.json`.
  - `src/wrangler.toml`: only the keys `name`, `pages_build_output_dir = "public"` and
    `compatibility_date`; desk-build fails the PR on any other key. The
    project name is passed on the command line (below).
  - `src/functions/api/poll.js` and `src/functions/api/blobs.js`: Pages Functions, by file-based
    routing (C).
  - `src/lib/`: the record parsers, shared by the page and the tests.
  - `src/public/`: the page.
  - `src/config/projects.json` (J7).
- **Tests.** They live in `tests/desk/`, with fixtures in `tests/desk/fixtures/`, using Node's
  built-in runner.
  - **Build command:** `npm --prefix src ci && npm --prefix src run build`. The build also checks
    J7.
  - **Test command:** `npm --prefix src test`, which runs `node --test ../tests/desk/`.
  - **No live access:** the tests use the real samples quoted in J2, J9 and J10 and a fake `fetch`.
    No test needs a token or the network.
- **Who holds secrets: nobody but the owner and GitHub/Cloudflare** (PROJECT.md §4 line 115;
  AGENTS.md §1).
  - **The Builder** holds neither the Cloudflare API token nor the read token. It never deploys,
    and it never calls the live function.
  - **The read token** exists only as a Pages secret.
  - **The Cloudflare API token** exists only as a secret of the GitHub environments `preview` and
    `production`.
  - The owner sets each by hand (Setup).
- **Workflow 1, `.github/workflows/desk-build.yml`** (the Chief of Staff's).
  - **Trigger:** `pull_request`, and pushes to `main` that touch `src/**` or `tests/**`.
  - **Access:** `permissions: contents: read`, and no secrets. It uses no environment.
  - **Steps:**
    - `npm --prefix src ci --ignore-scripts`, then the build and test commands.
    - A config check (a script in the Chief of Staff's lane, `.github/scripts/`). It fails the PR if

      `compatibility_date`. It also fails if `src/package.json` has any lifecycle script (listed
      under Layout) or a `dependencies` block.
    - It uploads no artifact and hands nothing on to any other workflow.

  - **Branches:** the Builder's milestone branch, `build/builder/<task>`, is pushed to origin,

    on `pull_request` or `workflow_run`. No pull-request branch name or artifact is ever used.
  - **Access:** `permissions: contents: read` for the whole workflow.
  - **Why `main` alone isn't enough (the Reviewer's round-3 R3-B1):**
    - `main` is unprotected, and agents push under the owner's admin account. So "code on `main`
      is reviewed" isn't enforced by GitHub.
    - So **every deploy job runs in an environment whose required reviewer is the owner.** That
      covers `preview` and `production`, and `exp-002` too.
    - GitHub holds each job until the owner presses Approve, which the GitHub mobile app offers.
  - **Each approval is tied to the commit it deploys (R4-B1).**
    - **Push runs** check out exactly `${{ github.sha }}`, never "the tip of `main`".
    - **`workflow_dispatch` runs** require an input `sha`.
      - The first step receives it through `env:`, never interpolated into the shell.
      - After `git fetch origin main`, it fails unless all three of these hold (R5-B1):
        1. the input matches `^[0-9a-f]{40}$`;
        2. `git merge-base --is-ancestor "$SHA" origin/main` succeeds, so the commit is on `main`;
        3. `git diff --quiet "$SHA" origin/main -- src .github/workflows .github/deploy-tools
           .github/scripts` succeeds, so nothing deployable has changed on `main` since that commit.
      - It then checks out and deploys exactly that SHA.
      - **What this allows:** Orchestrator and `decisions/` commits landing on `main` after the
        reviewed merge don't block a dispatched preview re-deploy or the launch deploy.
      - **What it still refuses:** an unmerged commit, and an older reviewed commit whose deployable
        code newer commits have replaced.
    - **`run-name`** is `deploy ${{ github.event_name == 'push' && github.sha || inputs.sha }} —
      ${{ github.event.head_commit.message || inputs.note }}`.
      - The approval screen shows the full SHA. GitHub expressions have no substring function, but
        its first 7 characters are the short SHA on the PR page.
      - On a push from a merge, it also shows the merge commit's message, which begins
        `Merge pull request #<n>`. A dispatch carries a `note` input, in which the Chief of Staff
        names the PR.
      - Both the message and the note are hints only. The owner matches the SHA.
  - **The owner's approval rule:**
    - Approve only when the run's SHA equals the merge-commit SHA shown on the page of a pull
      request that the Reviewer passed. Fix-forward PRs need the Reviewer's PASS too.
    - Reject every other run.
    - The actor name can't separate the owner's runs from an agent's: agents act under the owner's
      account, so both show as `shumpmaster`. The SHA is the only thing to check.
    - **Production:** approve only a SHA that the preview has already deployed and that the owner
      has accepted on the preview.
    - **`exp-002`:** the owner approves it when they or the Chief of Staff asked for it. It deploys
      nothing.
  - **Concurrency:** each job has its own `concurrency` group, `desk-deploy-preview`,
    `desk-deploy-production` or `desk-deploy-exp-002`, with `cancel-in-progress: false`. So two
    approved runs never deploy over each other, and a waiting run is not silently cancelled.
  - **Every deploy job:**
    - checks out the approved SHA, as above;
    - runs no tests (desk-build already ran them on the same commit);
    - re-runs the `.github/scripts/` config check on that checkout before wrangler: the
      `wrangler.toml` keys, and no lifecycle scripts or `dependencies` in `src/package.json`;
    - installs nothing under `src/`.
  - **The wrangler install step:**
    - It installs the deploy tool in a clean directory outside `src/`, from the Chief of Staff's
      pinned `.github/deploy-tools/package.json` and its lockfile. The command is
      `npm ci --ignore-scripts --prefix .github/deploy-tools`, which pins wrangler at `<x.y.z>`
      and its transitive dependencies.
    - The registry is pinned by a committed `.github/deploy-tools/.npmrc` holding
      `registry=https://registry.npmjs.org/`, so no other registry setting can redirect the
      install.
    - Whether wrangler runs fully without its packages' install scripts is C. The first deploy
      shows it. If it doesn't, the Chief of Staff names the one package whose script must run, in
      a reviewed change to that directory.
  - **The deploy step:**
    - Its `working-directory` is `src`. It calls
      `"$GITHUB_WORKSPACE/.github/deploy-tools/node_modules/.bin/wrangler" pages deploy public
      --project-name <project> --branch <branch>`. Nothing from `src/node_modules` exists or runs.
      wrangler reads `src/wrangler.toml`, whose keys are limited as above, and bundles
      `src/functions/`.
    - `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` are in that step's `env:` only, not the
      job's.
  - **Job `preview`:**
    - It runs on every push to `main` touching `src/**`, and on dispatch, in environment `preview`.
    - It deploys to `service-desk-preview` with `--branch main`.
    - `main` is the preview project's production branch (Setup C1). So each approved deploy
      updates `https://service-desk-preview.pages.dev`, a fixed URL, behind its Access application
      (F-cf-04, A).
    - The job writes the URL to its summary. There is no pull-request comment step.
  - **Job `production`:**
    - It runs on `workflow_dispatch` only, from `main`, in environment `production`, with the owner
      as required reviewer.
    - Beyond the dispatch check above, it fails unless the most recent successful `preview` job of
      desk-deploy ran on the same SHA. It reads that with `GITHUB_TOKEN`.
    - Its job-level block is `permissions: { contents: read, actions: read }`. A job-level block
      replaces the workflow-level one, so both are listed.
    - It deploys to `needs-you`, a direct-upload project (EXP-002), with `--branch` set to its
      production branch as EXP-002 records.
    - It is used at M3 and never run before AC28. The owner approves it only after disabling
      Operations-Hub's `needs-you-page` workflow, which would otherwise redeploy the old page over
      it within an hour (AC28, Setup C8).
  - **Job `exp-002`:** it runs on `workflow_dispatch` only, in environment `preview` (owner
    approval). It runs the same pinned wrangler's `pages project list`, read-only, with the token in
    the step's `env:` only.
  - **Possible later hardening, not relied on — option (b):** a ruleset on `main` blocking direct
    pushes to `src/**` and `.github/**`. Whether rulesets are available on this repository's plan
    is C. The owner's approval gate above is the control.
  - **What is still trusted, stated plainly:**
    - **The Reviewer's check:** the Reviewer's reading of `src/package.json`, `src/wrangler.toml`
      and `src/package-lock.json` on each pull request is a security control, not just a quality
      check. desk-build's config check backs it up for the keys and scripts it knows.
    - **wrangler's own dependencies:** wrangler and its transitive dependencies are trusted by
      pinning only, through the Chief of Staff's lockfile. Nobody reviews their code.
    - **The approval click:** the owner's click is the last gate. A mistaken approval of an
      unreviewed push would deploy it.
    - **The gate itself is not airtight (R4-B2).** Agents act under the owner's admin account. An
      agent could, through the API, remove an environment's required reviewer or change its secrets,
      and GitHub would show the change as the owner's.
      - The environment gate stops accidents and unreviewed runs. It doesn't stop a credential that
        can administer the repository.
      - The **recommended backstop** is CS9: at every milestone acceptance, the Chief of Staff shows
        the owner both environments' protection settings, and every audit-log entry for environment
        changes since the last milestone.
      - The **alternative** is to narrow the agents' credential to one without Administration
        permission.
      - The owner chose the backstop, (a) (closed owner question 4, P-001-s001-owner-questions.md).
- **Milestone acceptance:**
  1. The Reviewer passes the milestone's pull request.
  2. The owner merges it.
  3. The owner approves desk-deploy's `preview` job, which deploys `main` to the preview.
  4. The owner tries the preview and accepts the milestone.

  A problem found on the preview is fixed by a fix-forward pull request, not by reopening the
  merged one.

    - the Reviewer checks every AC of the milestone, not a sample;

    environments (R4-B2, CS9).

    deploys without that approval.
  - **What is left:**

      lane, guarded by `surface_guard`, and only the owner merges it.

      a security control.
    - Option (b), a ruleset on `main`, is possible later hardening; its availability is C.
