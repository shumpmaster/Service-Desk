## Terms used in this spec
- **Connected project:** an entry in the desk's repository list (`config/projects.json`, J7), with
  the read token able to read it. At launch: Service-Desk and Personal-Org-Operating-Model.
  Sized for up to 5.
- **Card:** a file `queue/<item>-<gate>-<n>.md` in a connected project. Its **answer** is the file
  `decisions/<item>/<gate>-<n>.md` in the same repository. Evidence for the pairing:
  `queue/Q-003-failure-1.md` (PROJECT.md:507) and the answer files `decisions/P-001/dor-fail-1.md`,
  `decisions/P-001/failure-5.md` (this pack); the pairing rule is inferred (C) and is fixed in J2.
- **Open card:** a card with no answer file on the default branch. Whether a card file is kept
  or deleted once answered is not known to this spec (owner question 7), so the rules hold either
  way: an answer file makes its card answered whether or not the card file still exists, and a
  card's raised time is taken from the repository's history of the card path (J2), not from the
  file being present.
- **Needs the owner (flagged):** an open card, or an open pull request with a review requested
  from the owner's GitHub login. Nothing else is flagged (PROJECT.md §8 "Needs the owner"; Part 2
  "Only flag what needs a human").
- **Activity:** anything shown but not flagged, from exactly these sources: check runs on the
  default branch head (J1), open PRs not awaiting the owner (J1), dispatch-log entries (J9), and
  queue files that can't be parsed or were withdrawn (J2). An agent retrying appears here as a new
  dispatch-log entry for the same item and role (J9); the desk has no other source for retries.
  Agent sessions' own records are S-002's.
- **Open window:** a span during which the desk page is visible in the foreground on a device
  (the browser's page-visibility state is "visible").
- **Read successfully:** a call to the desk function for that project (J6) returned `state` `ok`
  or `unchanged`, and, during a cold load, every batch up to `more: false` has returned. An
  `unchanged` answer (all three steady-poll requests returned 304, J1) is a successful read: GitHub
  answered and reported nothing new. `cant-read`, a 403 from the function, a Cloudflare error and a
  network failure are not.
- **Quiet:** no flagged item in any connected project, **and** every connected project read
  successfully within the last 3 minutes.

## Acceptance criteria (scenarios; draft, not yet approved by the owner)
*These go to the owner on the scenario card after the Critic's review and the freeze gate. No
ruling in `decisions/` approves them yet, and the open questions below are unanswered.*
Each criterion is a plain scenario. "Within 5 minutes" is V1's figure. Screen width for "phone" is
360 CSS pixels; for "desktop", 1280.

**Seeing what needs you (D2, D3.1)**
- AC1 [trace: V1 → AC1] — When a card is committed to a connected project's default branch while
  the desk is open on the owner's phone, then within 5 minutes the project's box shows it as
  waiting on the owner and the box moves to the top of the Universe screen.
- AC2 [trace: V1 → AC2] — When the owner opens the desk after it was closed, then until every
  connected project has been read once since opening, the screen says "Checking…" and never
  "Quiet"; once all are read, every open card in every connected project is shown.
- AC3 [trace: V1 → AC3] — When a connected project can't be read (token rejected or expired,
  GitHub rate limit, GitHub or Cloudflare error, or no successful read for 3 minutes; an
  "unchanged" answer is a successful read, see Terms), then its
  box says "Can't read since HH:MM" with the reason, sorts above every box except those with
  flagged items, and the screen as a whole does not say "Quiet".
- AC4 [trace: V2 → AC4] — When a connected project has a failing check run on its default
  branch head (J1), a new dispatch-log entry (J9; this includes a repeat dispatch of the same item
  and role, which is how an agent retrying shows), or an open pull request with no review requested
  from the owner's login (J1), then the desk shows it as activity in that project's box and does
  **not** flag it, count it as waiting, or move the box up for it. (A failing default branch still
  orders the box by AC6's third rank; that is not a flag.)
- AC5 [trace: V2 → AC5] — When a card's answer file is committed (by any route), then within 5
  minutes the desk stops flagging that card while open, and on next opening it is not flagged.
- AC6 [trace: V4 → AC6] — When the owner looks at the Universe screen, then each connected
  project has one box showing its state (flagged count, or "Can't read", or quiet), its headline,
  its current sprint and its main-branch CI result, ordered worst first: flagged, then
  can't-read, then main branch failing, then the rest by name.
- AC7 [trace: V4 → AC7] — When the desk runs on the preview for 7 consecutive days before launch,
  then each day the Chief of Staff compares it with the Operations-Hub page and finds no item the
  old page shows as needing the owner that the desk does not flag ("at least as correct", §1).
  Differences are logged in `docs/LEDGER.md`. The Chief of Staff judges each one: it is
  "explained" only if its ledger entry cites the repository record showing that the item did not
  in fact need the owner at the time of the comparison (for example, the answer file's commit
  before it). Any other difference is unexplained and resets the count to zero. If the owner
  disputes a judgement, the owner's ruling stands.

**Reading and answering (D3.2, D4.1)**

- AC11 [trace: V4 → AC11] — When a connected project's `webCommitsToDefault` is `false` in

  offers the new branch and proposes its name (F-gh-07 (2)); the owner opens the pull request and
  merges it. The card stops being flagged only when the answer file is on the default branch

**Team, pipeline, planning, time (D3.3, D3.4, D4.2, D3.5)**

- AC13 [trace: V4 → AC13] — When the owner opens "Work ahead", then it lists the open,

  automatically; the Chief of Staff carries it out (owner's ruling of 2026-10-04).

**Trust, measurement and upkeep (D5, V1–V3 measurement)**
- AC15 [trace: V4 → AC15] — When any request reaches the desk's function without a valid
  `Cf-Access-Jwt-Assertion` for the owner's email address (missing, expired, wrong audience,

  `pages.dev` address and every custom domain prompt for Access login before anything is served.
  The Reviewer's security review of the login and the read token's handling (D5.2) has passed

- AC16 [trace: V1 → AC16, V2 → AC16] — When the desk is used during a week, then on the device in
  use it records each open window's start and end, and for each flagged item the time it was first

  offers a prefilled link that commits the previous week's figures to
  `docs/metrics/<YYYY>-W<ww>.md` in Service-Desk, in J5's form. Nothing of this is stored on

- AC17 [trace: V4 → AC17] — When the owner approves launch (and S-002 is accepted), then the
  `needs-you` production deployment serves the desk at its `pages.dev` address and custom domains,
  the previous Operations-Hub deployment remains available by rollback, and Operations-Hub's
  repository is archived by the owner.
- AC18 [trace: V3 → AC18] — When the owner wants to add a connected project, then the operating

- AC19 [trace: V3 → AC19] — When the desk's open windows add up to 16 hours in a day, across all
  devices, with 5 connected projects, then the function stays within the Free plan: fewer than
  10,000 function requests that day (our own margin, a tenth of Free's 100,000), no Error 1027,

  100,000 (worked case in "Facts relied on").

## Join sheets

- **J1 — GitHub REST → desk function (reader).** The function sends, per connected project, at
  most 30 outbound requests per invocation (fixed batch size; under the brief's 40 and leaving 20
  of Free's 50 for redirect hops), each `GET` with `Authorization: Bearer <read token>`,
  `Accept: application/vnd.github+json`, and `If-None-Match: <etag>` when it holds one. A steady
  poll is exactly three requests: the default branch head
  (`GET /repos/{o}/{r}/branches/{default}`), open pull requests (`GET /repos/{o}/{r}/pulls?state=open`),
  and check runs on the head (`GET /repos/{o}/{r}/commits/{sha}/check-runs`). Only when one of
  these changes does it read records (J2). ETags are held by the page and sent back with each call
  (J6), so the function stores nothing.
  Awkward cases: 304 on all three (nothing read, returns "unchanged"); 401/403 (token expired or
  missing permission: project marked can't-read, reason "token"); 403/429 with rate-limit headers
  (reason "rate-limit", next poll waits until the reset time); GitHub 5xx or a network failure
  reaching GitHub (reason "github"); 404 on a records directory (treat as empty, not as an
  error); redirect hops count against 50 (F-cf-workers-02); a cold load needs more than 30
  requests, so the page makes several batched calls and the project stays "Checking…" until all
  return.
  Two limits apply to one batch, and they don't conflict: the batch holds at most 30 requests in
  total (the subrequest cap), and at most six of them wait for headers at any moment (the
  connection cap; a seventh queues, F-cf-workers-07, B). So a full batch of 30 runs as about five
  waves of six, and its wall time is roughly five GitHub round trips. Whether that wall time and
  the batch's CPU fit Free is EXP-001's measurement (O3); if not, the batch size (one constant)
  is lowered.
  Retries: a failed or rate-limited read is never retried within an invocation or sooner than
  the next scheduled poll; after 403/429 with rate-limit headers the page waits until the reset.
  Every retry is still one request to the function and to GitHub, and is counted in AC19's
  arithmetic.
  A test marked `join-test: S-001/J1` covers it.

- **J2 — Repository records → read model (per project).** Paths read on the default branch:
  `queue/*.md` (cards) and `decisions/<item>/*.md` (answers). The status, sprint and dispatch-log
  files are read at the paths named in `config/projects.json` (J7) and parsed per J9. A card file name (without `.md`) is split by: `<item>` = the leading match of
  `^[A-Z]+-[0-9]+`; `<n>` = the trailing match of `-([0-9]+)$`; `<gate>` = what lies between,
  without its edge hyphens. Its answer is `decisions/<item>/<gate>-<n>.md`. The answer's verdict is the text
  after `Decision: ` on its first line.
  Examples: `queue/Q-003-failure-1.md` → item `Q-003`, gate `failure`, n `1` → answer
  `decisions/Q-003/failure-1.md`. `queue/P-001-dor-fail-2.md` → item `P-001`, gate `dor-fail`,
  n `2` → `decisions/P-001/dor-fail-2.md` (exists in this pack, verdict `resubmit`).
  Raised time: the commit time of the oldest commit on the default branch that touched the card
  path (`GET /repos/{o}/{r}/commits?path=queue/<file>&sha=<default>`, oldest entry; history of
  a deleted path is still listed), read once per card and kept with the page's ETags. Answered
  time: the same for the answer path. Cards are found from `queue/*.md` and also from every
  answer file under `decisions/` (an answer `decisions/<item>/<gate>-<n>.md` implies the card
  `queue/<item>-<gate>-<n>.md`), so an answered card whose file was deleted is still listed for
  AC14. A directory under `decisions/` whose name doesn't match `^[A-Z]+-[0-9]+$` (for example
  `decisions/questions/`) holds no card answers and is skipped. For Service-Desk only, the file names under `docs/planning/` are also listed (J4).
  Awkward cases: a gate containing hyphens (`dor-fail`, handled by taking item and n from the
  ends); a card file deleted after its answer exists (answered, not withdrawn); an answer whose
  card path has no history (listed with raised time "not recorded", never guessed); a queue file not matching the pattern (shown as activity with a "can't parse" note,
  never flagged, never silently dropped); an answer file with extra lines after the first
  (`decisions/P-001/dor-fail-2.md` has a `Proxy:` line and prose: only line 1 is read); an answer
  committed before the card (still counts as answered); a card file deleted without an answer
  (no longer flagged; shown in activity as "withdrawn").
  A test marked `join-test: S-001/J2` covers it.

- **J3 — Desk page → GitHub new-file page (card answer).** URL:
  `https://github.com/<owner>/<repo>/new/<branch>?filename=<path>&<contentParam>=<content>`, every
  parameter percent-encoded (UTF-8). `<branch>` is always the default branch (J1), also when
  `webCommitsToDefault` is `false` (AC11: the owner picks "new branch" in GitHub's dialog).
  `<contentParam>` is the repository's `contentParam` in `config/projects.json` (J7; `value`
  unless EXP-004 records another name); it is omitted when `contentPrefill` is `false` (AC10). `<path>` = `decisions/<item>/<gate>-<n>.md`. `<content>` =
  `Decision: <option>\n` where `<option>` is the card's option word exactly as the card lists it,
  then, if the owner typed a note, a blank line and the note. Example for card
  `queue/P-001-dor-4.md`, option `build`, no note:
  `https://github.com/<owner>/Service-Desk/new/main?filename=decisions%2FP-001%2Fdor-4.md&value=Decision%3A%20build%0A`.
  The `filename` parameter is described by GitHub (F-gh-05, B). The content parameter is
  undocumented (C); its name is config, not spec text, so EXP-004's finding changes
  `config/projects.json` only and never this spec.
  Awkward cases: a note with `&`, `#`, `%`, emoji or newlines (encoded; checked by round trip);
  total URL over 6,000 characters (AC10 fallback); an answer file that already exists (GitHub
  refuses or the owner edits; the desk shows "already answered: <verdict>" before offering the
  link); repository whose default branch is not `main` (taken from J1's branch read).
  A test marked `join-test: S-001/J3` covers it.

- **J4 — Desk page → planning record → Chief of Staff.** File
  `docs/planning/<YYYY-MM-DD>T<HHMM>Z-<nn>.md` in Service-Desk, committed by the owner through a
  J3-form link. `<nn>` is always present and always two digits: `01` for the first plan in that
  minute, `02` for the next, up to `99`. The page picks the lowest `<nn>` not already among the
  file names J2 lists for `docs/planning/`.
  **Ordering rule:** the current plan is the file in `docs/planning/` whose name is greatest when
  names are compared byte by byte (plain ASCII order). Every name has the same length and the same
  fixed-width fields, so this order is time order, and within a minute `-01` < `-02` < … < `-99`.
  Example: `2026-11-02T0930Z-01.md` < `2026-11-02T0930Z-02.md` < `2026-11-02T0931Z-01.md`; the
  current plan is `2026-11-02T0931Z-01.md`. Files in `docs/planning/` not matching
  `^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{4}Z-[0-9]{2}\.md$` are ignored for ordering and listed in
  activity as "can't parse".
  Content:
  ```
  Plan: <YYYY-MM-DD>T<HHMM>Z-<nn>
  Supersedes: <previous plan file name, or none>

  | Order | Project | Item | Not before (UTC) |
  |---|---|---|---|
  | 1 | Service-Desk | P-002 | 2026-11-02T09:00Z |
  | 2 | Personal-Org-Operating-Model | M-014 | — |
  ```
  Awkward cases: an item finished between drafting and committing (kept in the record; the Chief
  of Staff skips it and notes it in the ledger); two plans recorded in the same minute (the second
  link gets `-02`, the ordering rule makes it current; the join test checks `-01`/`-02` and a
  minute boundary); two links drafted with the same name before either was committed (GitHub
  refuses the second because the file exists; the page, on its next read, offers the link again
  with the next free `<nn>`); an empty plan (allowed:
  means "no ordering preference"); a project name with spaces (not possible for repository names;
  rejected by the page).
  A test marked `join-test: S-001/J4` covers it.

- **J5 — Device record → weekly metrics file → Chief of Staff's weekly check.** Stored on the
  device in the browser's local storage under key `desk-metrics-v1`. Committed weekly to
  `docs/metrics/<YYYY>-W<ww>.md` (ISO week, e.g. `2026-W46`) in Service-Desk. Content:
  ```
  Week: 2026-W46   Device: phone
  ## Open windows (UTC)
  | Start | End |
  |---|---|
  | 2026-11-10T07:02:11Z | 2026-11-10T07:09:40Z |
  ## First shown
  | Project | Item | First shown (UTC) |
  |---|---|---|
  | Service-Desk | queue/P-002-dor-1.md | 2026-11-10T07:03:05Z |
  ## Didn't need me
  | Project | Item | Marked (UTC) |
  |---|---|---|
  ```
  The Chief of Staff's V1 count: cards whose commit time falls inside an open window and whose
  first-shown time is more than 5 minutes later, or absent while windows continued. V2 count: rows
  under "Didn't need me". Awkward cases: two devices in one week (one file per device:
  `<YYYY>-W<ww>-<device>.md`); a window still open at the week's end (split at Monday 00:00 UTC);
  local storage cleared (the file says "records from <date>"); the owner skips a week (next
  offer covers every un-committed week, one file each); over-long record for one link (AC10 copy
  fallback).
  A test marked `join-test: S-001/J5` covers it.

- **J6 — Desk page ↔ desk function.** `GET /api/project/<name>?batch=<k>` with header
  `X-Desk-Etags: <base64 JSON {url: etag}>`; response JSON:
  `{ "project": "<name>", "readAt": "<ISO UTC>", "state": "ok" | "unchanged" | "cant-read",
  "reason": null | "token" | "rate-limit" | "github", "retryAfter": <seconds|null>,
  "etags": {url: etag}, "more": <bool>, "cards": [{ "path", "item", "gate", "n", "title",
  "options": [..], "raisedAt", "answeredAt": null | "<ISO>", "verdict": null | "<word>" }],
  "unparsed": ["<queue path>"], "prs": [{ "number", "title", "url", "ownerReviewRequested": <bool> }],
  "ci": { "sha", "conclusion" }, "pipeline": <J9 object>,
  "plans": ["<file name under docs/planning/>"] }` (`plans` is present for Service-Desk only, J4). (The top-level field is `state`, so
  it doesn't collide with J9's status file.) `more: true` means the page must call again with
  `batch=k+1` before the project counts as read (AC2).
  Reasons: the function sets `token`, `rate-limit` and `github` (J1). The page sets two more on
  its own record of the project, never received from the function: `cloudflare` when the
  function call returns a 5xx or a Cloudflare error page (including Error 1027 and 1102), and
  `network` when the call fails to complete. Both show in AC3's "Can't read since HH:MM" with the
  reason in words. A queue file that can't be parsed is not a can't-read reason; it goes in
  `unparsed` (J2).
  Awkward cases: function returns 403 (Access JWT invalid: page shows "Signed out", not "Quiet");
  network failure (`network`, counts toward AC3's 3 minutes); `etags` header too large (page
  drops the oldest and accepts a full read).
  A test marked `join-test: S-001/J6` covers it.

- **J7 — `config/projects.json` → function and page.** Committed in Service-Desk, read at build.
  Form: `[{ "name": "Service-Desk", "repo": "<owner>/Service-Desk", "webCommitsToDefault": true,
  "contentPrefill": true, "contentParam": "value", "paths": { "status": "<path>", "sprint":
  "<path>", "dispatchLog": "<path>" } }]`, at most 5 entries. `webCommitsToDefault`,
  `contentPrefill` and `contentParam` for each launch repository are EXP-004's recorded results;
  the paths are the ones J9's samples come from. Awkward cases: 6 entries (build fails with message, AC18);
  a repository the token can't read (AC3 at run time, not a build failure); a missing path entry
  (that panel says "not configured").
  A test marked `join-test: S-001/J7` covers it.

- **J8 — Cloudflare Access → desk function.** Header `Cf-Access-Jwt-Assertion`, validated with
  the team's public keys for signature, expiry, the application's audience tag, and `email` equal
  to the owner's address (F-auth-04, A). The owner's address and audience tag are settings the
  owner enters by hand. Validation runs on every request, before any GitHub call. Fetching the
  team's public keys is at most one outbound request per invocation (none when the isolate still
  holds them); it counts against Free's 50, inside the 20 J1 leaves free. Its CPU (signature
  verification) is part of every call's CPU and is measured in EXP-001. Awkward cases in AC15. A test marked `join-test: S-001/J8` covers it.

- **J9 — Status, sprint and dispatch-log files → read model (pipeline).** **Incomplete: blocks
  freeze** (see "Before freeze"). The desk's side is fixed here; the source side is not, because
  no sample of these three files is in the Definer's pack and the spec will not guess a format.
  *Desk side (fixed).* The function returns, per project, J6's `pipeline` object:
  ```
  { "stage":    { "value": "Shape" | "Build" | "Run" | null, "recordedAt": "<ISO>" | null },
    "headline": { "value": "<text>" | null,                   "recordedAt": "<ISO>" | null },
    "sprint":   { "value": "<text>" | null,                   "recordedAt": "<ISO>" | null },
    "atWork":   { "item": "<id>", "role": "<role>", "since": "<ISO>", "recordedAt": "<ISO>" } | null,
    "next":     { "item": "<id>", "recordedAt": "<ISO>" } | null,
    "dispatches": [{ "item", "role", "at": "<ISO>", "outcome": "<word>" | null }],
    "notes": ["<file>: <what couldn't be read>"] }
  ```
  `recordedAt` is the commit time of the latest commit on the default branch that touched the
  source file (`GET /repos/{o}/{r}/commits?path=<path>&sha=<default>&per_page=1`), so it doesn't
  depend on the file's format. `atWork` = the latest `dispatches` entry with `outcome: null`.
  `next` = the first item in the status file's order of open items that has no `dispatches`
  entry. A repeat entry for an item and role that already have one is shown as "retry" (AC4).
  `dispatches` holds the last 20 entries.
  *Source side (to be quoted before freeze).* For each of the three files: its path in each launch
  repository, one real sample committed as a fixture under the Check author's tests, and the exact
  rule that yields each field above (for example: the line or heading it is read from, and the
  date form). If the samples show a field isn't recorded, that field's rule is "always null" and
  the screen says "not recorded"; AC12 is then amended before freeze, not left to the Builder.
  Awkward cases (fixed now): a file missing or its path not configured (field null, note
  "not configured" or "not found"; the project is not can't-read); a line that doesn't match its
  rule (skipped, named in `notes`, never silently dropped); a dispatch entry with an outcome but no
  matching start (shown as it stands); two entries with no outcome (the latest is `atWork`, the
  other is listed with "no outcome recorded").
  A test marked `join-test: S-001/J9` covers it, using the real samples.

## Facts relied on (each with evidence)
- Pages Functions run on Workers and count against the Workers quota; identical runtime limits
  are not documented — evidence: library/facts/F-cf-06.md:4 (A). Hence EXP-001 measures on a
  Pages project.
- Free plan: 100,000 requests a day; Error 1027 beyond — evidence: library/F-cf-workers-05.md:8
  (A). AC19's arithmetic is our own estimate (E), and rests on these **assumptions**, each of which
  the Chief of Staff can check against Cloudflare's request count during AC7's seven days:
  - A1: open windows total at most 16 hours a day across all devices. Two devices open at once
    count twice.
  - A2: one function request per project per 60-second poll, and no retry sooner than the next
    poll (J1). Retries after a 403, 429 or Cloudflare error therefore don't add requests, but each
    one is counted in the poll total.
  - A3: a cold load needs about 30 to 120 GitHub requests per project (see the GitHub fact
    below), which at J1's 30 per batch is 1 to 4 batched calls; there are at most 10 openings a
    day across all devices. That is 5 × 4 × 10 = 200. The real batch count is EXP-001's figure.
  - A4: a changed head makes the project's records be read again (J1, J2), which in the worst
    case is the same work as a cold load of that project: at most 4 batched calls. The first of
    them is the poll that saw the change, already counted in the 4,800, so a change adds at most
    3 more. At most 100 changes a day across all projects: 100 × 3 = 300.
  Total for AC19's 16 window-hours: 4,800 (5 projects × 60 polls × 16 hours) + 200 + 300 = 5,300,
  under the 10,000 margin.
  Worked case outside AC19 (A1 broken): two devices each open for the full 16 hours make 32
  window-hours. Polls double to 9,600; openings and changes are already day totals across devices
  and don't double (if they did, 9,600 + 400 + 600 = 10,600). The total is 10,100 to 10,600, which
  **fails** the 10,000 margin. It is about a tenth of Free's 100,000, so there is still no Error
  1027: at 300 requests per window-hour, Free's limit is reached only after about 331 window-hours
  in a day. If the Chief of Staff's check during AC7 shows A1 broken, that is reported to the
  owner, who either accepts a wider margin or asks for a longer poll interval when several
  devices are open.
- Free plan: 10 ms CPU per request, network waits excluded; Error 1102 beyond — evidence:
  library/F-cf-workers-01.md:8 (A). Occasional overages tolerated — library/F-cf-workers-08.md:9 (B).
- 50 external subrequests per invocation on Free; redirect hops count — evidence:
  library/F-cf-workers-02.md:8 (A).
- Six connections waiting for headers at once; a seventh queues — evidence:
  library/F-cf-workers-03.md:8 (A), library/F-cf-workers-07.md:9 (B).
- Free-plan HTTP wall-time limit: not filed — evidence: library/F-cf-workers-03.md:8 (NOT filed).
  EXP-001 measures it.
- A 304 with an Authorization header doesn't count against GitHub's primary limit; PAT limit
  5,000/h — evidence: library/Q-004-facts.md:9, :8 (A). Steady load 3 × 5 × 60 = 900/h (E,
  PAT-Q004-1, library/Q-004-facts.md:18). This holds even when no request returns 304, so a project
  that keeps failing (for example, a rejected token, polled each minute) stays inside it. Cold
  loads are full reads and do count. Each one needs about 30 to 120 requests per project (the
  per-card commit-time reads for AC14 dominate, E). Three openings in one hour is then at most
  3 × 5 × 120 = 1,800 on top of the 900, still under 5,000. A changed head's re-read (A4) sends
  the ETags the page holds, so only files that actually changed are full reads; it is bounded by
  the same 120 per project but in practice is a handful (the new card or answer, its commit-time
  read, and the file listings).
- Webhooks can be minutes late and aren't redelivered, so the design polls — evidence:
  library/Q-004-facts.md:6, :14, :15 (A/B).
- `?filename=` prefills the new-file name; no content parameter documented — evidence:
  library/F-gh-05.md:8 (B). Owner's own use of content-prefilled links from phone browser and app:
  docs/PROJECT.md:318-320 (C, observed by the owner). EXP-004 confirms per repository.
- Over-long query links on other GitHub pages return 414; no limit documented for new-file —
  evidence: library/F-gh-06.md:8 (A). The 6,000-character cap in AC10 is our own margin (E),
  checked in EXP-004.
- Commit step offers current or new branch; push rulesets may block creating a file; protected
  branches block web edits — evidence: library/F-gh-07.md:8 (A), library/F-gh-10.md:9 (A).
- Access: validate the JWT with the public key, prefer the header — library/F-auth-04.md:8 (A).
  A One-time-PIN-only policy lets anyone in; policies can name emails — library/F-auth-02.md:8 (A).
  Pages' "Enable access policy" covers previews only; `*.pages.dev` and each custom domain need

- A production deployment (Git or `wrangler pages deploy`) changes what `pages.dev` and custom
  domains serve; rollback is instant — library/facts/F-cf-02.md:4 (A). A project can't switch

## Risks and mitigations
- **CPU per cold-load batch exceeds 10 ms (O3).** EXP-001 measures it in Define, before freeze; fallback
  per the owner's ruling (decisions/questions/P-001-o3-define.md): smaller batches (the batch size
  is one constant), else the $5 Paid plan with a new ceiling from the owner.
- **`needs-you` is Git-integrated (O5).** EXP-002, in Define, before freeze; fallback per the owner's ruling
  (decisions/questions/P-001-o5-define.md): a new Pages project and a permanent redirect.
- **GitHub drops the content parameter.** AC10's copy fallback; the flag in J7 lets the owner
  switch a repository to it without a rebuild of logic.
- **A missed card while the desk shows "Quiet" (the owner's worst case).** AC2 and AC3 make
  "Quiet" require a fresh successful read of every project; parse failures show, never vanish (J2).
- **Too many agents for T1.** Build runs with at most two builder or reviewer agents at once
  (PROJECT.md §5); the Orchestrator script does not count. More needs the owner's T2 ruling.
- **Read token leaks.** It is fine-grained, read-only, limited to the connected repositories
  (L-F5), held only as a Cloudflare secret the owner sets by hand, and never sent to the page or a
  model (PROJECT.md §5); D5.2 reviews it.
- **Touching the live page before launch.** The preview is a separate Pages project
  (`service-desk-preview`, created by the owner); nothing deploys to `needs-you` before AC17
  (L-0115).
