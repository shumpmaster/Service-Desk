# Research question — Q-018

*Drafted by the Chief of Staff; checked by the Critic for gaps and neutral phrasing (D-032, D-055).*

## The question

How many changes of each kind arrive per day and per week in each repository the desk reads?

The desk reads three project repositories, shumpmaster/Service-Desk, shumpmaster/Personal-Org-Operating-Model and shumpmaster/Model-Lab, and one portfolio repository, shumpmaster/portfolio (src/config/projects.json). Service-Desk's merged pull requests were counted by week up to 2026-11-01 by two methods that agree (research/Q-016-memo.md, area D; research/Q-016-source-check.md).

Period, days and weeks: the eight complete weeks from 2026-09-07 to 2026-11-01, with 2026-11-02 up to 12:00 UTC reported separately as partial; or from a repository's first record if it is younger. Use UTC days and Monday-to-Sunday weeks, to match the earlier counts, and say whether any peak moves when days are taken in the owner's zone (America/Chicago, src/config/projects.json).

What may be read:
- Service-Desk and Model-Lab are public; Personal-Org-Operating-Model and the portfolio are private, so their GitHub pages cannot be fetched.
- For Model-Lab and the portfolio, read only: dates, authors, pull-request and commit numbers, titles, labels, branch names and the list of changed file paths. Do not read file contents, diffs, descriptions, comments or commit message bodies. For Service-Desk and Personal-Org-Operating-Model, the same, plus descriptions where needed to tell a kind apart.
- Counting needs a method that reads every record to the end: the GitHub API's paginated lists, or the git history of each default branch. Do not count from a summary of a page. Give a count only where every page was read; otherwise write "not counted" and why. Counts a Researcher cannot make (no shell, or a private repository) will be made by a role with a shell, using the methods in research/Q-016-source-check.md; say which counts those are. The same limits on what may be read apply to whoever makes the counts.

For each repository, and in total, count:
- pull requests merged, opened, still open at the end, and closed without merging;
- commits that reach the default branch without a pull request (for example, records committed straight to the default branch, or commits by automated workflows), and how they were told apart (for example, a commit on the default branch's first-parent line that is not the merge of a numbered pull request);
- deploys or releases, naming the source (the Releases page, deploy workflow runs), or "none found" with where it was looked for;
- the kinds of merged pull request (for example: the product's code, records only, governance or rules, settings or workflows), how each kind was told apart, and how many were "kind not determined";
- per day and per week, with the busiest and quietest of each, and whether peaks in different repositories fall on the same days;
- how many merged pull requests and other changes needed the owner (the owner merged it, approved it, or answered it, as shown by its merge record or review), how many landed without the owner, and how many "cannot tell".

Re-take Service-Desk's merged count to the new end time and say whether it agrees with the earlier one.

## The decision it serves

Whether reading changes one at a time, in a group, or only by exception is feasible at the volumes found. The counts feed the cost of each; they do not settle it.

## What each answer would change

Low and steady volume keeps reading one at a time in view; high or bursty volume sets a ceiling on it and makes grouping or exceptions necessary at peaks; a large share of changes outside pull requests means an approach limited to pull requests misses them; the share that needs the owner sets how much is a decision and how much is news.
