# Ruling needed: the card fix's tests ask for a record of the old behaviour that the pipeline cannot make, so which way should the card fix go?

Milestone: M4

WHY: The card fix still has not been built, and the next card you get on it will need your word. Its tests need a record of how the desk behaves today, made before any code is changed, so the new behaviour can be compared with the old. The spec says to prove that ordering from the build branch's git history. The pipeline cannot do that. Its Builder works in a plain folder with no git history, it hands back all its changes at once, and the checks run on a fresh copy with no history. So no Builder can pass those tests, however good its work. Since the rebuild: the Builder correctly refused to fake the record, the checks passed on an empty build, and the Reviewer failed it (FAIL, nothing built). Sent back, the Builder used all 50 of its turns, changed no file, and ended in an error. The next timer run tries it again. A stop card comes after the third failed round, or a failure card if two tries in a row end in errors. Answering `rebuild` again would spend more rounds on the same wall, so I am asking now which way to go, before either card comes.
OPTIONS:
  A. Fix only how the old behaviour is recorded, in a new spec. The Check author records the old behaviour from the unchanged code before anything is built, and keeps it with the locked tests, which the Builder cannot change. That protects the record without git history. The git-history test goes; every other criterion carries over unchanged. Your word on the card: `criteria-wrong` on a stop card, which is not a strike. A failure card does not offer it, so there it is `re-specify`, which is counted as a strike. Cost: a new spec, a criteria card for you, freezing and new tests, then the build again. About a day of the pipeline's time, and one more card.
  B. Change the pipeline instead. Builders would get a git copy of their branch and could commit in steps, and the checks would keep that history. That is a change to the operating model, not this desk, and a large one; the card fix waits for it, likely for weeks.
  C. Build the card fix outside the pipeline, in a session with git and a shell, as the desk itself was first built. How it then rejoins the pipeline's records (its rounds, the merge gate) has to be worked out first, and the builder-is-never-the-judge rule still needs a separate review.
  D. Keep going as it is: answer `rebuild` again at the card. No grounds: nothing has changed, so it fails again the same way.
RECOMMENDATION: A, because the fault is one definition in the spec, not the Builder or the pipeline, and A fixes just that within the pipeline's normal path. I raise B in the operating model as a lesson either way.
RISK CLASS: R0 (the question); it leads to a new spec, the pipeline's normal path   REVERSIBILITY: reversible   BLAST RADIUS: the card fix only; nothing on the live desk changes
DEFAULT: none   TIMEOUT: none (your answer here sets the word I recommend on the card, and only you answer the card)

A risk with A, in fairness: the Builder's second try ran out of turns before changing a file. With the record fixed it should spend its turns building, but nineteen criteria are a lot for one 50-turn session. If it runs out again, I will bring you that as a separate question.
